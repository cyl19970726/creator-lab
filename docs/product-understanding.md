# Agent Workflow：产品认知、核心机制与设计推导

**我们正在构建一种让 Agent 的业务方法在真实工作中形成、接受检验、持续演化并稳定服务的工作范式。** 产品要承载这个过程：让方法能够执行，让执行留下有用的事实，让评价能够支持判断，让判断能够改变下一版方法，并让有效方法持续服务业务。工作台是人与这套能力交互的界面，CLI／tool 是 Agent 的操作入口，两者都不能代替产品本身的机制。

本页按“为什么相信这种方法 → 方法怎样产生和演化 → 产品必须承担什么 → 怎样组织使用 → 文档如何分工”展开。它是设计推导，不是功能实现说明。正式目标在[产品定义](../vendor/agent-workflow/docs/product.md)，交互合同在[工作台定义](../vendor/agent-workflow/docs/workbench-presentation.md)，当前事实只查[建设状态](../vendor/agent-workflow/docs/harness-roadmap.md)。已确认要求、综合解释和具体方案在文中分别说明。

## 第一章 产品认知：我们相信怎样的工作范式

### 1. 从一次完成业务，到形成持续有用的方法

用户最初直接在 Codex 会话里做内容，随后要求从第一版开始就由 workflow 真实完成业务。如果主持 Agent 在流程之外补齐研究、改好稿件，成品虽然存在，却没有验证这套 workflow 下次能否完成工作。这个经历说明：业务效果必须归属于真实执行的方法，临时介入必须被看见。

宏观目标是把真实业务做成可执行、可评价、可持续改进的 workflow，并用于不同的 FDE 客户业务。内容创作是第一项验证业务。微观目标同时包括：完成这次业务、理解这次过程、改善下一次做法、持续使用已经有效的方法，以及让其他人或 Agent 能继续接手。它们不能被缩成“把某轮代码改完”或“做出一张完整流程图”。

我的综合理解是：用户希望把依赖长会话、个人记忆和临时补救的工作，逐步变成可持续使用的业务能力。资产、历史、版本、评价和工作台应共同支持这种转变。减少人工纠偏与重复搭建的收益仍需实际验证，不能由记录数量推断。

### 2. 核心范式：结构化的方法，合同内的自主执行，基于证据的演化

我们并不假设一开始就能设计出最佳流程。先从业务目的形成一条最小、完整、能够真实执行的方法；让 Agent 在明确输入、职责、工具范围、产物与结束条件内完成工作；再通过实际产物和执行证据理解方法的效果。需要改变时，由人或受托认知 Agent 提出有依据的改法，验证后决定采用、继续查证或不改。

这里同时相信两件事：Agent 需要判断和探索空间，业务又需要清楚的责任、资产和执行边界。确定的传递、存取、路由和记录适合由程序承担；研究、表达、诊断等需要判断的工作交给 Agent。步骤按独立交付、审阅和返工边界划分，不能把每一次工具调用或每一个角色都机械变成一个流程节点。

这意味着 workflow 既是**完成业务的可执行方法**，也是**可以被研究和改进的对象**。它的结构、节点分工、上下文、工具、skill、评价标准都可能成为有证据的修改对象。调优不只是改 Prompt，稳定服务也不是停止学习。

方法依据见[设计指南](../vendor/agent-workflow/docs/designing-workflows.md)与[调优循环](../vendor/agent-workflow/docs/tuning-loop.md)。当前改进主要由人或受托 Agent 驱动，不能把这个范式写成已经实现的全自动优化器。

### 3. workflow、skill、tool 和 harness 分别承担什么

| 概念 | 在这种范式中的责任 | 不能混同的部分 |
| --- | --- | --- |
| workflow | 将业务目的组织为阶段、步骤、资产依赖、审阅、分支、返工和停止条件，形成准确的可执行方法版本 | 一次运行、某份作品、某个 skill 都不是整个 workflow |
| skill | 向 Agent 提供可复用的方法知识：什么时候用、怎样判断和行动、需要哪些工具与参考、如何验证及何时停止；可包含脚本、schema、样例和资产 | 保存一份 SKILL.md 不等于方法有效，也不等于模型参数被训练 |
| Agent | 在其责任与授权范围内理解上下文、运用 skill 和工具、作出判断并生成产物 | 自主性不等于可以任意改历史、越过权限或替用户宣布接受 |
| CLI／tool | 提供准确查询和持久动作，让 Agent 读取具体证据、运行任务、记录评价或修改方法 | 调用了工具不证明原因判断正确；界面也不应另造一套动作语义 |
| harness 与共享存储 | 承载身份、资产版本、上下文装配、执行与记录、权限及回执，使事实可恢复、可追踪 | 保存全部历史不等于形成知识；环境可控不保证业务质量 |
| 认知与评价角色 | 围绕目标使用成果、区分问题层次、提出假设、评价收益与退化，决定值得推进什么 | 独立评价是证据；实施者自测、Agent 意见与用户接受分别表达 |
| 工作台 | 让人理解上述对象和过程，阅读实际内容、作决定并继续工作 | 前端展示不能制造缺失的执行、评价或采用机制 |

业务 skill 可以服务某个节点；调优 skill 可以服务维护 workflow 的操作者；本项目的产品认知 skill 服务产品负责人。这是不同责任，并不是所有技能都要变成流程图上的节点。修改 skill 后，它可能影响多个步骤或多个 workflow，因此也要识别使用关系和复验范围。

### 4. 首版方法怎样产生

有两种起点。有历史时，从用户意图、真实产物、尝试、反馈和失败中恢复完整案例；没有历史时，从新的业务要求出发，做足以影响设计的最小探索。两者都汇到业务目的、成功标准和一条可执行的资产路径。

接着推导“阶段要达到什么 → 每一步拿什么、作什么判断、交出什么 → 哪些地方需要审阅、返工或停止”。在步骤内部选择 Agent、skill、工具或确定性程序，同时设计怎样检验关键产物。首版可以很简单，也可以先使用候选 skill；不能等流程全部成熟才开始真实工作。

既有做法不必原样照搬。历史中的探索和绕路需要区分为必要探索、可以复用的方法和可以避免的返工。首版保留设计理由和未知，真实试跑再检验这些假设。参见[从意图或历史设计工作流](../vendor/agent-workflow/docs/designing-workflows.md)。

### 5. 完整生命周期：研发与稳定服务持续相连

生命周期描述方法怎样从假设走向有范围的稳定使用，再由新的证据进入下一轮。它不是菜单顺序，也不是每个案例必须重走一遍的向导。

![Workflow 从业务目的、首版设计和真实运行走向评价、调优、候选验证与稳定服务，再由业务反馈触发下一轮。](diagrams/workflow-paradigm-20261007/workflow-lifecycle-v2.svg)

[展开生命周期图](diagrams/workflow-paradigm-20261007/workflow-lifecycle-v2.html)。图表达目标范式，不表示所有阶段已自动化；下表补充每次转换所需的判断。

| 阶段 | 这一阶段真正改变什么 | 转入下一阶段需要什么依据 |
| --- | --- | --- |
| 明确目的与设计方法 | 将业务要求变成阶段、步骤、资产、评价与结束条件，形成 v1 的假设与理由 | 最小资产路径可执行，关键输入和判据足够明确 |
| 开始真实运行 | 准确方法与输入作用于具体 Case，生成阶段产物、真实路径、配置及失败记录 | 有可阅读的成果或可定位的失败；不能由宿主补做掩盖缺口 |
| 阅读评价与诊断 | 判断哪里好、哪里不好、相对提升及仍不满意，区分输入、方法、判者、环境与交接问题 | 有足够证据支持某个原因假设，或明确还缺什么证据 |
| 调优与形成候选 | 修改有理由改变的主要因素，并记录受影响的 skill、节点、资产或规则 | 候选与原版的差异可解释，预期收益和可能退化可检验 |
| 比较验证与迭代决定 | 用同条件或有说明的条件、代表性案例检验改法，而非只增加版本号 | 说明改善、失败、成本、适用范围与未知；决定采用、继续试验、回退或停止 |
| 稳定服务 | 在已采用的方法和范围内持续处理真实业务，积累成果、异常、人工负担与反馈 | 持续观察实际效果；发布候选不自动替换生产方法 |
| 周期复盘与再次调优 | 结合一段时期的案例，判断问题是否反复发生、条件是否变化、方法是否仍值得用 | 可以继续原方法、限制范围、回退，或依据新假设回到设计与调优 |

**稳定版生产与候选版研发可以并行。** 一次运行内修稿，解决本次作品；方法版本修改，改变以后怎样工作；评价者校准，改变如何判断；可选的模型后训练则是另一种后续探索。四者不能混成“迭代了一次”。一周只是观察窗口的例子，严重问题可以提前处理，没有新问题也不必制造新版。

### 6. 一个 skill 怎样开发出来

skill 开发是把可以复用的操作与判断提炼成 Agent 能使用的方法包，并不断通过实际工作校正它。既可从已有实践提炼，也可为新任务先提出草案；两条路都需要试用，不能把一次成功直接写成永久规则。

![Skill 从真实任务与案例出发，经过方法草案、执行观察、知识提炼、打包和独立试用，在实际使用反馈中持续修订。](diagrams/workflow-paradigm-20261007/skill-development.svg)

[展开 skill 开发图](diagrams/workflow-paradigm-20261007/skill-development.html)。候选方法可以较早写成 skill；“已打包”和“经过验证可复用”是不同状态。

过程应回答：什么触发使用 → 需要恢复什么目标和材料 → 哪些判断改变路线 → 用什么动作完成 → 什么结果算有效 → 哪些条件下不适用。必要脚本、参考资料、schema 和样例跟随包版本保存；要验证完整包实际送达，也要验证 Agent 的行为和业务结果。两种验证不能互相替代。

在 workflow 中使用的 skill，应能追溯到本次准确版本。skill 的修改可能来自运行失败、用户反馈、跨案例差异，也可能来自更好的做法；经过试用再判断是否适合扩大使用。日志是提炼的证据，skill 是经过选择和论证的知识，二者之间需要认知工作，并不会自动转换。

本次 `product-cognition` 就暴露了这个区别：前一版格式通过，独立案例试用也能产出“认知→界面”，但没有检验是否讲清产品核心工作机制。用户的新反馈揭示了试用覆盖的缺口，需要修正方法和评价任务。这不能以“检查已通过”结案。

### 7. 用户连续请求如何落在这套范式中

| 已明确的请求 | 它在补足什么关系 |
| --- | --- |
| 从一开始用 workflow 真做业务 | 业务成果与真实执行方法之间的归属，防止宿主救场掩盖方法问题 |
| 每轮说明好坏、提升与不满意 | 从成果到判断、从判断到下一处改法的依据 |
| Space 面向长期业务目的与多个版本 | 保持业务目的的连续性，同时允许方法变化 |
| 保存资产、会话、模型、Prompt、工具配置 | 让问题可以追到准确输入、生产过程和条件，而非猜原因 |
| 同一方法跑多个题目、稳定后集中复盘 | 从个案成功走向适用范围与常态效果的判断 |
| 认知 Agent 主动使用、判断、提出需求 | 让 Agent 承担持续理解与取舍，不让用户不断补齐产品思考 |
| 完整方法图与就近资产阅读 | 将方法、执行和结果的关系变成人能理解和操作的环境 |
| workflow 标题展开多个二级任务 | 让同一个长期工作对象的设计、运行、调优与服务都可直接进入 |

前七项依据现行[产品定义](../vendor/agent-workflow/docs/product.md)与已记录反馈，最后一项是本轮明确的导航要求。对其背后动机的解释仍应随使用证据修正。

### 8. 成功标准与重要边界

业务使用者关心成果可用；方法维护者关心能否反复完成、为何改善；认知负责人关心是否沿目标推进、遗漏了什么；不同责任可以由同一人承担。用户保有业务偏好和最终采用判断，独立评价者提供证据，执行者不能凭测试通过替代这些判断。

成功要分别观察：当次成果是否满足用途；代表案例上的可靠性、质量、人工负担与时间费用；改法是否带来可解释改善；离开或换人后能否继续工作；第二业务能否主要提供领域方法、工具、标准和阅读器就复用共性能力。全套记录齐全却仍需人重做或解释，说明产品机制或使用方式仍有问题。

当前先验证 CONTENT。研究、分析和创作继续独立；多 workflow 协作、B3、第二业务迁移、模型后训练和临时 VM 编排不因此自动进入当前建设范围。通用与专业、自主与可控、透明与易用、稳定生产与实验，是持续取舍，不能用更多页面或更强模型统一替代判断。

## 第二章 从认知推导产品责任与核心机制

这一层说明产品必须承担什么，先于前端、路由和技术模块划分。具体实现可以变化，但如果这些关系没有成立，界面就只能展示孤立信息。

### 从生命周期推出必须持续存在的东西

| 认知依据 | 产品需要承担的责任与机制 | 要保留的结果及后续用途 |
| --- | --- | --- |
| 方法从业务目的与假设产生 | 关联目标、标准、设计理由、阶段与资产路径，允许无运行时理解方法 | 首版也有理由，后续变化能够区分目标改变与方法失效 |
| Agent 在明确边界内自主工作 | 让节点职责、输入、上下文、skill、工具和结束条件可定义、装配并记录 | 判断方法声明与实际执行是否一致，知道该改哪个层次 |
| 真实业务应由方法实际完成 | 准确版本、部署条件、Case 与输入形成运行；记录节点实例、资产和介入 | 成果有归属，失败可见，历史可读不被误认成历史可重跑 |
| 评价需要真实内容和明确条件 | 阶段与最终资产都能被阅读、评价和比较，保留判者、标准与分歧 | 技术成功、业务质量、用户接受分别判断；支持诊断而非只给分 |
| 改进需要检验因果 | 问题与假设连接改动、候选、基线、案例集合和比较 | 可解释为什么改、改得怎样；控制变量或说明条件变化 |
| 稳定服务与研发并行 | 正在查看、已发布、可执行、候选和当前采用分别表达；采用有范围和明确决定 | 试验不会静默改生产，必要时限制范围或回退 |
| 经验要影响后续工作才有价值 | 资产可以跨案例引用，经过判断的知识进入 skill／配置，保留来源和使用关系 | 避免重复搬运；修改经验后知道需复验哪些消费者 |
| 稳定使用产生新证据 | 按范围记录业务、失败、人工负担、评价覆盖和反馈，形成复盘决定 | 决定继续使用或再调优，不用零散成功记录宣称成熟 |
| 人与 Agent 都需继续工作 | 通过工作台和 CLI／tool 读写同一批事实与动作，保存判断和接手位置 | 认知不依赖单个聊天，界面和 Agent 不各自维护一套状态 |

### 这些责任如何由共同对象连接

Space 维持长期业务目的。同一 workflow 的不同准确版本表达方法变化；skill 是方法可能使用的依赖。Case 表达一次业务要求，可以由多个版本、多次运行处理。一次运行绑定准确方法、输入和执行条件；节点实例产生可追溯的资产。评价针对准确对象和用途；比较连接明确条件下的结果；iteration 将问题、改动和验证联系起来；采用决定哪些版本在什么范围服务。

因此不能按存储表逐项造菜单，也不能只保存最后一份稿件。来源、前驱、生产、消费、评价、修订和采用是不同关系：资产先后出现，不等于有因果关系；最新稿不等于已接受稿；候选分数更高，也不自动成为生产方法。正式对象合同见[产品定义](../vendor/agent-workflow/docs/product.md)，执行与资产关系见[流程与资产](../vendor/agent-workflow/docs/workflow-process-assets.md)。

### 从机制转到使用结构

人进入产品时，并不总处于同一阶段。日常完成业务时，中心是案例、输入与成果；开发和维护方法时，中心是一个 workflow 的生命周期；跨案例找资料时，中心是资产及其用途。因此形成三个可以互相到达的工作方向。它们是对任务和共同对象的组织，而不是三个互不相干的后台。

workflow 是会长期演化的工作对象，设计、运行、调优、版本、服务和复盘是围绕它反复发生的任务。由此可以推导出：在稳定工作流标题下展开二级任务导航；准确版本和 Case 是任务内的观察范围。这里才进入前端结构。

## 第三章 使用设计：从信息层级到具体交互


### 第一层 产品形态和外壳

用户需要反复进入、同时管理多份业务和方法，并在阅读、执行与比较之间切换。由此比较整体形态：

| 形态 | 适合什么 | 单独采用时的缺口 |
| --- | --- | --- |
| 单一聊天或固定步骤向导 | 表达模糊要求、辅助首次建业务或方法 | 缺少稳定对象位置，难以承载长期资产使用、并行生产与复盘 |
| 所有人都从完整方法图进入 | 方法理解、节点配置、准确运行诊断 | 日常找成果仍需跨过开发概念，直接业务任务不够清楚 |
| 只按案例或作品组织 | 日常完成业务和阅读成果 | 方法定义、跨案例改进和版本演进容易藏在详情深处 |
| 共享 Space 的持续工作台，按任务直接进入 | 兼顾业务生产、方法开发和资产使用 | 需要严格维护共同身份与返回上下文，避免三个入口变成三套互不相干的产品 |

因此建议采用**以业务 Space 为范围的持续工作台，左侧稳定导航，右侧随任务变化的主工作区**。日常默认从案例与产物进入；开发者从工作流进入；跨案例查找与复用从资产库进入。持续导航应便于反复切换，横向导航也可以承载同样结构；左侧栏是结合本轮用户提出的工作台样式选择的方案，并非所有工具产品都必须使用。

左侧保持当前 Space 与主要入口；右侧承担实际工作。顶部只展示当前任务的标题、范围和重要状态。详情在工作区内展开，长文和比较可扩大阅读。低频设置与运行诊断留在辅助位置，不争夺日常成果的注意力。

```text
┌────────────────┬───────────────────────────────────────────┐
│ 当前业务 Space │ 当前任务标题 / 所处范围 / 必要状态与主操作 │
│                ├───────────────────────────────────────────┤
│ 案例与产物     │ 本入口的列表、画布或正文                   │
│ ▾ 工作流标题   │                                           │
│   生命周期任务 │                                           │
│ 资产库         │ 选中对象 → 原地详情 / 扩大阅读 / 对照      │
│                │                                           │
│ 设置与帮助     │ 返回后保留原来的对象、视图和筛选           │
└────────────────┴───────────────────────────────────────────┘
```

Space 切换只在存在多个可访问业务时承担真实选择，不为单 Space 增加空层级。整体视觉采用安静的工具界面：导航弱于主内容，正文有足够字号与宽度，颜色表达少量明确状态。方法图和案例图使用相同的阅读与返回方式；不靠重新换主题解决信息结构问题。

首次进入尚无方法的 Space，先看到业务目的、成功标准、已有样例和“形成第一版方法”的起点，不能要求用户对着空图猜下一步。已有可执行方法时，日常进入案例列表并提供新建业务；直接打开某个方法或资产链接时仍进入准确对象。再次进入优先恢复上次工作范围，不无故跳回一个与当前任务无关的统计首页。

### 第二层 左侧导航放什么

| 入口 | 为何独立存在 | 默认主体 | 不放在这个层级的内容 |
| --- | --- | --- | --- |
| 案例与产物 | 高频任务是完成一项业务、找到成果和待处理事项 | 按业务题目组织的案例列表；CONTENT 可以显示为选题与产物 | run、attempt、manifest 等技术对象不是平级菜单 |
| 可展开的工作流标题 | 同一个方法对象需要长期设计、运行、调优、服务和复盘 | 展开的二级任务决定主体；版本是当前任务的范围 | 不把每一个技术版本永久塞进左栏，也不将整个生命周期压成一个开发页 |
| 资产库 | 素材与中间成果可能脱离当前案例被查找、比较和复用 | 可搜索筛选的资产集合 | 不复制每份资产到不同工作台的独立存储 |
| 设置与帮助 | 低频管理 Space 信息、接入和操作说明 | 与权限相符的设置及帮助 | 不把模型凭据、原始日志默认露给日常用户 |

用户本轮明确要求工作流标题可以 toggle 展开二级任务。单一 CONTENT 可显示为“工作流 · CONTENT”；如果以后有多个主业务 workflow，各自以可读标题承载自己的任务，而不是先把所有技术版本铺成菜单。展开与收起只改变导航显示，不切换方法、不取消工作，也不丢当前内容。直接进入某个二级任务时展开其父标题，重新进入恢复原范围。

这层结构来自“一个长期工作对象拥有多种反复发生的任务”。具体二级名称是下节提出的编排方案，可以按任务走查调整。评价仍就近出现在被评对象旁，跨案例的评价和调优可从工作流下汇总进入；不必因此把全部评价迁到一个独立后台。

### 第三层 案例与产物的主体

#### 案例列表

第一眼回答：做了哪些事、已有哪份可读成果、哪些需要处理、下一步是什么。主要操作是新建业务，其次是打开案例和筛选待处理事项。列表用业务名称、结果摘要、业务处理状态和更新时间帮助辨认，准确 ID 按需展开。

最新运行失败时，案例仍显示此前可用的成果与这次失败；不能让“最新”覆盖“可用”。排序可以优先待处理和最近活跃，但不要将最新稿默认当成被接受或应交付的稿件。

#### 新建业务

按工作内容组织输入：要求与用途、目标读者或使用者、材料与约束。允许从资产库选择准确版本，也允许导入当前支持的材料。清楚表达所用方法与是否可执行；有已采用且可用的方法时减少重复选择，无采用版本时明确选择候选而不自动采用。

发起前让人检查本次要求、材料和方法，显式启动后保留可返回的案例位置。配置高级参数属于可展开信息。普通委托不要求填写 A/B 假设；修改已冻结输入应形成清楚的新输入版本或运行，不覆盖过去。

#### 案例详情与案例画布

默认中心是“这次输入了什么，得到了什么，现在怎样处理”。案例画布先呈现关键输入、主要成果与关系；需要理解形成过程时，再展开研究、各轮稿件和意见。技术节点的控制流可从这里进入准确运行视图，不要求业务使用者先读懂全部节点。

主成果旁直接提供对应意见、前稿、处理建议与下一步动作。阅读一份稿件后能回到同一案例和轮次；查看来源时不丢失当前阅读对象。没有主成果时，说明还在运行、等待材料还是失败，并展示已有中间成果。

#### 结果处理

区分继续修订、选定成果、接受、导出和交付。每个动作要表达作用对象和后果。Agent 的处理建议保存为 Agent 意见；它不是用户接受，也不应伪装成流程内某个节点的终审。

交付后的反馈回到原成果和案例，才能用于以后改进。业务闭环应到可用成果及其处理决定，不能把“模型请求成功”或“保存了一条意见”单独作为结束。

### 第四层 工作流展开后的二级任务与主体

二级任务应表达完整生命周期，而不只是图的四种显示模式。方法图、运行图、演进图、列表与阅读器是完成任务时使用的表现方式。同一任务可能同时需要图和正文，不能用可视化组件反推任务数量。

```text
案例与产物
▾ 工作流 · CONTENT
  目标与设计
  运行与案例
  评价与调优
  版本与验证
  稳定服务
  复盘与再调优
资产库
```

| 二级任务（编排方案） | 主体和默认信息 | 应完成的判断及后续联系 |
| --- | --- | --- |
| 目标与设计 | 业务目的、成功标准、阶段和资产路径、首版理由与完整方法图；节点展开 skill、工具、配置和输入输出 | 理解为什么这样做及尚未验证的假设，形成可运行方法；无 run 时也成立 |
| 运行与案例 | 当前方法上的 Case 与真实运行，选中后显示实际路径、轮次、资产和失败 | 理解一次业务发生什么，从问题到对应评价，再回到案例处理成果 |
| 评价与调优 | 阶段／最终产物、四问、trace、分歧、问题和原因假设 | 区分修本次作品、补材料、改方法或校准判者；有依据的改法进入候选验证 |
| 版本与验证 | 前驱与改动理由、受影响 skill／步骤、基线和候选、案例范围、比较和采用决定 | 判断收益、退化和适用范围；决定采用、继续试验或停止，而非只浏览版本时间线 |
| 稳定服务 | 当前采用方法、适用范围、持续业务、关键阶段资产、异常与人工负担 | 持续完成业务并保留反馈；日常动作也可由案例入口直达，候选不干扰生产 |
| 复盘与再调优 | 明确窗口内的案例、评价覆盖、反复问题、新条件与既有决定 | 形成继续使用、限定范围、回退或开启新改法的判断；再回到设计或调优 |

正在查看、当前采用、候选和可执行状态在任务内清楚表达。准确部署版本和历史版本可以不同，不能把能看历史误写成能立即重跑。案例、资产或问题进入某个二级任务时携带原范围，返回保留阅读位置；方法图、案例图和版本图各表达自身关系。

Agent 侧同样沿这些业务语义工作：按目的与范围取证，选择准确对象，作出判断，调用已支持动作并保存结果。人可以通过图和正文理解，Agent 可以通过 CLI／tool 读写，二者共同遵守前章的机制；不会因为前端增加了一个“调优”菜单，系统就自动获得调优能力。

### 第五层 资产库的主体

资产库服务“我想找某类材料或成果”，无需先知道它属于哪个 run。提供业务名称、类型、来源、产生阶段、相关案例及可用状态；按任务选择列表、缩略图或专用阅读器，避免所有内容都变成 JSON。

筛选围绕真实需要：版本、案例、节点阶段、时间、人工选定或评价状态。查看资产可阅读内容、比较准确版本、展开来源和使用关系，并引用到新的业务输入。名称帮助人识别，准确身份保证关系不串。

复用保留原来源和新用途，不修改旧内容。资产被淘汰可能只针对某次用途，不应仅凭一次评价就变成全局不可用。所谓“最好”也需要相同目的和可比较标准；当前没有校准证据时，不先做一个看似精确的排行榜。

#### 辅助入口：设置与帮助

主体按业务信息、执行接入和操作说明组织。业务信息说明这个 Space 服务什么目的、适用范围与成功标准，修改目标要留下时间与版本，不能静默改写历史判断。执行接入说明当前可用能力和影响范围；具体某版方法的模型、Prompt 与工具配置仍在方法上下文查看，不混成一个全局开关。

帮助优先解释当前任务中的术语和继续方式，并能返回原案例、方法或资产。没有多用户权限、多个 Space 或某类接入实现时，不展示假定可用的管理按钮；也不以“设置未完善”为由阻塞已支持的正常业务。

### 第六层 详情阅读与就近判断

短配置和轻操作用侧面详情，完整文章、长报告、大图及双稿比较提供扩大阅读。先给内容与必要结论，再按需展开证据、关系和技术追溯；不要让一大段机器结论和标识占满首屏，把真正的稿件挤到下面。

正文、画面、对应意见、来源与关系按业务类型组织。比较先让人知道两边是什么、为什么比较、条件有何变化，再并看内容与各自评价。保存的摘要应能扫描到收益、代价、未知和处理决定，完整依据仍可展开。

返回应恢复原案例、版本、轮次、筛选和视图。跨入口跳转尽量携带这些范围，不用用户记编号再次搜索。正在填写的反馈不应被后台刷新覆盖。

### 第七层 对象与状态支撑这些界面

Space 持有业务目的；方法版本描述允许怎样做；Case 表达一次业务要求；准确输入与方法形成一次 Run；Run 中的节点实例产生 Asset；评价针对准确资产；比较连接明确条件下的结果；方法改动关联问题、验证与采用决定。

这条关系说明为什么三个入口应共享事实。一个 Case 可经多个方法和多次运行产生多份结果；一份资产可用于多个后续案例；一次差评既可能要求修这份稿，也可能支持修改未来的方法，两者要分清。产品对象不是必须逐项新建一张表的要求，优先复用已有合同。

| 状态 | 用户应得到的反馈与可继续的工作 |
| --- | --- |
| 尚无方法或案例 | 明确产品用途和起点，不显示大量没有解释的空表 |
| 加载中 | 保留所选范围，说明正在读取哪类内容；不先将空数据误报为没有成果 |
| 正在执行 | 表达当前阶段、已完成产物、可用操作和返回位置 |
| 部分完成或失败 | 同时表达失败位置与已有成果；处理建议可以保存，恢复或重跑仅按真实能力提供 |
| 需要人处理 | 说明需要决定什么、针对哪份内容、作决定后会怎样 |
| 多个候选或历史并存 | 可读名称、用途与状态足以区分；归档历史不占据日常列表，也不悄悄破坏所需证据 |
| 离开后重开 | 从持久记录恢复业务处理状态、建议和下一步，而非从聊天摘要猜测 |

## 第四章 文档怎样编排，接下来先判断什么

### 上一版为什么没有把认知推到设计

上一版虽然写了目标、场景和三个循环，实际仍围绕“前端为什么不好用”组织答案。生命周期停在场景表，缺少阶段之间的转换依据及其所需机制；随后直接给出侧栏、主体和阅读器。认知章变成了界面方案的前言，未真正约束产品设计。

审阅也沿用了同样的范围：检查章节是否齐全、场景是否覆盖、界面是否从外到内展开，却没有从“一个新业务如何变成稳定方法”反向走完整条链。因此几位 Agent 同意、文档构建通过和另一案例试用，都没有发现这个共同盲点。

修正方式是先走通一项业务如何形成方法、如何运行和判断、如何修改与采用、如何稳定服务再复盘；逐段追问谁负责、留下什么、下一段凭什么继续。然后再推导产品责任、对象关系和导航。工作流标题的 toggle 正是在这一层级推导中应被发现的结构，而不是事后加一个控件。

### 整个文档集合应按决策依赖编排

| 阅读层次 | 要回答的问题 | 主要文档职责 |
| --- | --- | --- |
| 产品认知与推导 | 为什么做、相信什么范式、方法怎样形成与演化、由此需要什么 | 本页负责连贯论证与关键假设；不承担实时状态 |
| 正式产品定义 | 已确认的目标、原则、职责、生命周期、对象与边界是什么 | [product.md](../vendor/agent-workflow/docs/product.md)维护规范性结论；深层范式应先于界面摘要 |
| 方法开发指南 | 一位 Agent 或开发者实际怎样设计、评估和优化 workflow／skill | [设计](../vendor/agent-workflow/docs/designing-workflows.md)、[评估](../vendor/agent-workflow/docs/evaluating-workflows.md)、[优化](../vendor/agent-workflow/docs/optimizing-workflows.md)讲方法；[调优循环](../vendor/agent-workflow/docs/tuning-loop.md)连接执行步骤 |
| 使用与交互定义 | 用户怎样进入各任务、阅读与操作，Agent 怎样用同一套事实 | [工作台定义](../vendor/agent-workflow/docs/workbench-presentation.md)组织入口、默认主体、动作和返回；不把页签当作全部生命周期 |
| 技术架构与接口 | 上述责任由哪些包、服务、合同和扩展承担 | [architecture.md](../vendor/agent-workflow/docs/architecture.md)及专门接口文档解释实现；代码布局不能反推产品目标 |
| 当前状态与实施记录 | 哪些已经成立、依据是什么、哪些仍缺失 | [harness-roadmap.md](../vendor/agent-workflow/docs/harness-roadmap.md)维护唯一当前状态；日期化记录保存当时证据 |
| 领域业务接入 | 共性范式在创作等业务里如何具体化 | [创作文档](../workbenches/creation/docs/README.md)提供领域流程、skill、工具、标准和阅读器；不重复建设共享底座 |

这是一份内容编排原则，不要求读者每次从头读完全部文档。正式定义保留简洁规则，本页解释为何作这些选择，开发指南解释怎么做。后续维护应在对应层改正文，避免每次反馈都在尾部叠加一个补丁小节。旧文档里与当前事实冲突的实现声明需要定点核实，不能仅按文档日期决定真伪。

### 本轮结束点与下一步认知

本轮交付是范式、生命周期、产品机制和使用结构之间的完整推导，以及对应图示和文档编排；不实施新导航、不增加业务功能，也不发起新模型运行。前一版“先改案例前端”的排序只能作为当时的阶段建议，不能反过来决定整个产品的定义。

接下来的设计核对应沿两条路径：一项新业务怎样形成首版方法并进入真实运行；一个已采用方法怎样持续服务、积累反馈，再触发有理由的改进。每一步都指出需要的事实、判断、动作和保留结果，再检查现有能力是已有、部分成立还是缺失。最后才决定实施次序。

现有准确版本、资产、运行、评价与图阅读等有效能力应继续复用；当前哪些已经验证，以建设状态和具体证据为准。不能因整体重新思考便全部重建，也不能因局部跑通便宣布范式已经完整实现。认知 skill 同步要求检查这些推导关系，而不是只检查章节与页面是否齐全。
