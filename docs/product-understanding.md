# Workflow Space：产品认知与逐层设计

这份说明先建立产品认知，再推导产品设计，最后对照现有能力决定建设顺序。**核心理解是：让真实业务形成能反复使用、能依据结果改进、能被继续接手的方法，使每次工作的成果和经验有机会改善后续工作。** 这句话是对已确认需求的综合解释；它需要由实际效果验证。

产品要求以[产品定义](../vendor/agent-workflow/docs/product.md)为准，屏幕合同在[工作台定义](../vendor/agent-workflow/docs/workbench-presentation.md)，当前实现状态以[建设路线](../vendor/agent-workflow/docs/harness-roadmap.md)为准。本页承担认知依据、设计理由与取舍的说明，不建立另一套实时任务状态；以下方案不等同于已经实现或全部得到用户确认。

## 第一章 产品认知：我们究竟要改变什么

### 1. 起点、转变与更深的目的

用户最初直接在 Codex 会话里做内容，随后希望从第一版开始就由 workflow 真实完成业务。这个转变很关键：如果主 Agent 在流程之外不断补材料、改稿和救场，最后拿到作品，也仍然不知道这套方法下一次能否完成同样的工作。[现行产品定义](../vendor/agent-workflow/docs/product.md)已记录这一动机与历史问题。

因此，直接价值首先是业务成果可用。更深一层，是形成可以反复运行、解释、检验和改进的做事方法；再往外，是把这些共性能力用于不同客户业务，减少每个 FDE 项目重新搭建执行、资产、评价和迭代机制的工作。内容创作提供第一组真实问题与验证样本，不能因为第一项业务是写文章，就将底座永久定义为文章管理后台。

我的综合推断是：用户希望减少对某一个长会话、某一个操作者的记忆和临时补救能力的依赖，让业务能力持续存在于可使用、可理解的工作环境中。这不是“完全取消人”，也还不能宣称已经降低了人工成本。若换一个人或开启新会话后仍必须重新解释全部背景、手工拼接资料，这个更深目标就没有实现。

### 2. 宏观目标如何落到具体任务

| 层次 | 目标与性质 | 它要求我们关注什么 |
| --- | --- | --- |
| 长期业务目标 | **已确认方向**：把真实业务做成可执行、可评价、可持续改进的 workflow，并用于 FDE 客户业务 | 交付是否有价值、方法能否持续使用、第二业务能否复用；不能只看功能与版本数量 |
| 持续产品责任 | **对需求的综合解释**：让业务生产、资产使用、方法改进及接手都基于一致事实，形成持续工作环境 | 日常业务和方法开发同时成立；资产、历史和判断跨越一次运行继续有用 |
| 使用者当次目标 | **已明确场景**：表达要求，找到材料，拿到并读懂成果，处理问题，决定如何使用 | 一次任务结束于可用成果及处理决定；不能只结束于启动成功或状态变绿 |
| 方法维护者当次目标 | **已明确场景**：知道怎样做、为何失效、值得改什么，判断是否采用改动 | 同一案例上的变化、跨案例适用性、代价及退化分别判断 |
| 认知负责人的目标 | **已明确职责**：保持全局理解，主动使用、发现与解释问题，提出有依据的下一步并复验 | 不等用户逐个指出缺项，不把执行完成摘要当成业务完成，也不为了持续迭代而制造需求 |
| 当前建设目标 | **本页建议**：让已有真实业务能力形成连贯、可理解、可返回的使用任务 | 先完成案例和方法两种任务的直接入口与衔接，具体取舍在第三章说明 |

这些层次相互约束：本轮界面改动必须帮助某个具体任务，任务完成必须服务业务价值；长期通用性又不能使眼下内容业务失去所需的专业阅读和判断。宏观目标不是口号，微观目标也不是脱离目的的按钮清单。

### 3. 连续请求背后的共同意图

下表左列来自已记录的用户要求；右列是对它为什么重要的解释。技术与界面诉求仍然需要被尊重，但不能只完成表面名词。相关原始动机整理在[为什么需要这套底座](../vendor/agent-workflow/docs/product.md#为什么需要这套底座)和[认知职责](../vendor/agent-workflow/docs/cognition-execution-loop.md)。

| 用户反复要求什么 | 可以据此理解的深层意图 | 只做表面会漏掉什么 |
| --- | --- | --- |
| 从一开始就用 workflow 真做业务 | 验证并积累一套可继续工作的生产方法 | 有成品，但实际工作仍由外部主 Agent 补做，无法判断流程效果 |
| 每轮说清好、坏、提升与仍不满意 | 需要可解释的进步及有范围的判断 | 只有通过率或分数，无法决定改动是否值得采用 |
| Space 围绕业务目的组织多个方法版本 | 业务目的比某次执行和某个版本活得更久 | 变成按数据库表展示的工具，历史有了但关系要靠人补 |
| 资产、会话、模型、Prompt、工具配置可追溯 | 人与 Agent 有依据地定位问题，恢复上下文和复用成果 | 只有文件列表和日志数量，仍不知道为什么产生这份结果 |
| 完整方法图与阶段资产就近查看 | 降低理解方法、结果和形成过程的负担 | 图虽然大，却看不到真实内容，或只有运行后才知道方法定义 |
| 同一版本处理多个案例、稳定使用后集中复盘 | 判断适用范围和常态效果，让生产与研发并行 | 每次都从试验开始，或拿一次成功声称方法成熟 |
| 认知 session 主动思考、执行 session 回报 | 把发现问题、解释原因和安排下一步的认知负担交给 Agent 持续承担 | 只自动转发消息或自动检查测试，仍由用户补齐全部产品思考 |
| 通用能力归入 agent-workflow，业务直接使用 | 将有价值的共性方法与基础能力用于其他业务 | 每换业务重造平台，或为了通用性抹去业务内容与判断标准 |
| 前端需要真正作为用户使用 | 用户要获得理解、判断和操作能力 | 页面元素齐全，却还需记 ID、翻聊天、猜入口和手工解释结果 |

例如“希望看到每个节点的模型、Prompt、工具”背后，可以推断有理解方法和诊断执行的需要；不能据此推出日常用户打开案例时也要先看全部配置。“流程图作为中心”明确约束工作流开发视图，也不意味着所有业务阅读任务都必须先经过方法图。这就是认知如何约束设计的作用范围。

### 4. 价值怎样产生，又怎样积累

一次业务的价值来自合适的输入经过方法，形成满足用途的成果并得到使用；执行记录只说明发生过什么。评价把成果与目标联系起来，人工或 Agent 的处理决定说明本次如何继续。

跨次价值需要多一步转换：从多个案例的成果、失败、人工介入和反馈中，区分偶发问题与方法问题，形成原因假设；修改方法后比较改善、退化与代价；适合的变化再进入日常使用。只有后续任务用上了资产、改法或整理后的知识，积累才产生实际价值。数据库保存了更多历史，不等于系统已经学会了什么。

这里有三个相互联系的循环：

- **业务循环**：要求与材料 → 真实执行 → 阅读评价 → 本次处理与交付 → 使用反馈，目标是完成这件事。
- **方法循环**：案例证据 → 原因假设 → 候选改法 → 比较验证 → 采用、限定使用或不改，目标是改善以后怎样做事。
- **产品认知循环**：理解业务与角色 → 使用整个产品 → 发现任务缺口和新机会 → 推导设计与实施 → 再使用并修正认识，目标是改善承载前两者的产品。

同一份差评可能只支持修改这份稿，未必支持升级方法；多次相似失误才可能形成更强的共性依据。产品不好用也不能一概归因于模型不好。负责认知的 Agent 需要判断问题属于哪一层，并允许有效的方法继续运行、没有新证据时暂不修改。

### 5. 谁使用，谁判断，谁承担责任

业务使用者应当获得可用成果，知道当前该处理什么；方法开发者应当依据实际案例改善做事方法；认知 Agent 应当从同一份事实理解效果、发现问题并选择值得推进的改动。减少查聊天、记技术编号、手工拼接上下文和反复救场，是据此提出的收益假设，应在真实使用中观察是否实现。

| 责任 | 进入时关心什么 | 产品应承担什么 |
| --- | --- | --- |
| 提出业务与使用成果的人 | 要求是否表达清楚、产物在哪、是否可用、下一步是什么 | 以业务题目和成果组织信息，减少执行细节的先决知识 |
| 构建和维护方法的人 | 为什么是这些节点、用什么配置、哪里失效、改版影响什么 | 完整方法、准确运行与资产证据、变更和验证关系 |
| 评价与作决定的人 | 哪份内容、按什么标准、依据什么、与谁比较、应怎样处理 | 在准确对象旁阅读和评价，保留分歧及决定来源 |
| 负责认知和方向的 Agent | 业务目标与全局缺口是什么，新证据改变了什么判断 | 可查询的共同事实、可接手的结论及一致的动作接口 |

这些责任可以由同一人切换承担，不能据此凭空建设四套账号或四个后台。业务内的作者、核查者等执行节点也不等于负责整体产品判断的认知 Agent。

人仍提供业务偏好、重要约束与最终采用判断；认知 Agent 应主动恢复目标、使用成果、发现遗漏并提出取舍；执行 Agent 完成有边界的实现和业务动作；独立评价提供另一份判断证据。Agent 可承担越来越多工作，但“有权限执行”“评价通过”“用户接受”是不同含义，不能相互替代。

### 6. 完整生命周期里，人到底在做什么

| 场景与触发 | 用户要完成的任务和决定 | 不可缺少的产品责任 |
| --- | --- | --- |
| 从零明确业务 | 决定服务谁、交付什么、何谓可用、哪些判断由人承担 | 保存业务目的、样例和适用边界，支持形成第一版方法的依据 |
| 构建第一版方法 | 理解职责、输入输出、工具与配置，选择可验证的做法 | 没有运行也能理解方法及设计理由；发布、可执行、采用分别表达 |
| 首次试跑 | 选择案例与准确材料，检查输入怎样经过流程产生结果 | 方法与运行可关联，实际轮次和资产可追踪 |
| 正常完成业务 | 提出要求、复用资料、启动、处理成果 | 普通业务不强迫先建立实验计划；明确所用方法与输入 |
| 运行中断或结果不合格 | 找到已有成果和具体问题，决定补材料、修稿、重跑或暂存 | 业务状态与技术状态分开；失败不抹去过程稿，不承诺不存在的恢复能力 |
| 阅读与交付 | 完整阅读，比较版本，结合意见决定使用哪份成果 | 准确关联内容、评价与选定结果；接受、导出、外发分别记录 |
| 查找和复用资产 | 找到某阶段或某案例的材料，判断适用性并用于新任务 | 跨案例保留准确版本、来源与用途；复用不依赖下载后重新上传 |
| 稳定使用一段时间 | 连续做多个任务、处理待办和异常，不反复配置方法 | 清楚的采用版本与例外，日常生产和候选试验可以并存 |
| 集中复盘和评价 | 比较一段时期的关键资产，判断共性问题是否值得改方法 | 按明确范围关联案例和成果，保留失败、未评价与样本差异 |
| 方法演化与采用 | 从问题推到改法，验证改善和退化，决定采用、继续试验或不改 | 保存问题、变更、验证与决定的关系，不能只有版本时间线 |
| 离开后回来或换人接手 | 恢复目的、对象、当前判断及下一步 | 持久结论、稳定定位和一致状态；无需翻完整聊天 |

资产、评价和接手贯穿多个阶段。这些场景不是必须依次完成的向导：稳定版可持续生产，候选版同时试验；单份稿件的问题也可能只需修稿，不需要升级方法。

这些任务需要几个稳定关系：业务目的贯穿多个方法版本；一项业务案例可以有多次尝试；每次尝试绑定准确输入与方法并留下资产；评价针对具体对象与用途；改法应能找到问题、验证和采用依据。先明确这些含义，才能决定哪些内容要放在一起，哪些动作必须分开。正式对象合同见[产品定义](../vendor/agent-workflow/docs/product.md)。

### 7. 哪些张力决定产品边界

| 需要同时成立的两件事 | 当前判断原则 |
| --- | --- |
| 稳定生产与持续实验 | 日常使用的准确方法与正在验证的候选分开；实验有新结果不自动改变生产方法 |
| 充分理解与低使用负担 | 提供完整可追溯信息，但按当前任务组织默认内容；可展开不等于一开始全部展示 |
| Agent 自主工作与人的判断 | 在已授权目标和边界内主动推进，保留来源、未知和介入记录；不把代理意见写成人的决定 |
| 通用底座与业务专业性 | 底座提供共性对象、执行、资产与迭代机制；业务提供方法、工具、标准和专业阅读器 |
| 完整产品思考与阶段交付 | 现在就解释完整生命周期，建设时按有意义的完整任务分期，不让阶段范围冒充整个产品 |
| 保留事实与形成可用知识 | 历史可追溯，工作中装配必要上下文；另行整理经过判断的经验，不每次堆入全部会话 |

明确边界：研究、分析和创作三个工作台独立，不新增必经顺序；先验证单一 CONTENT 的完整使用，多 workflow 协作、B3 与第二业务复用属于后续范围。临时 VM 编排已暂缓。完全自动学习、后训练、完整可视化编排器和复杂账号体系，都不能仅因长远可能有价值便成为当前前提。

### 8. 怎样知道这个产品真的有价值

| 要证明的判断 | 需要观察什么 | 什么会使我们修正认知 |
| --- | --- | --- |
| 一次业务确实完成 | 成果满足具体用途，用户能读懂并决定处理方式；人工补救如实记录 | 工作流显示成功，但成果仍由宿主重做，或没人能使用 |
| 方法能反复使用 | 代表性案例上的可用结果、失败、人工介入、时间与费用，以及适用范围 | 只在一个题目上成功，换输入就失效，或维护负担超过收益 |
| 改进有依据且有效 | 变化与问题关联，可比较的结果说明收益、退化和未知，采用理由清楚 | 版本增加但效果不明，评价反复反转却没有校准，越改越需要人纠偏 |
| 工作环境可以持续和接手 | 离开或换人后恢复目的、当前方法、成果与下一步，完成真实任务 | 全部记录存在，但仍需原操作者解释；找到信息的负担没有降低 |
| 共性能力能复用 | 第二业务主要提供自己的流程、schema、工具、标准与阅读器，即可用共性能力 | 换业务需重写存储、执行与前端核心，或通用表达容纳不了业务事实 |
| 认知 Agent 能承担认知责任 | 主动发现有价值的机会或问题，依据证据取舍，并在复验后修正理解 | 只是读状态和派任务，产品方向与明显缺口仍持续依赖用户指出 |

这里不预设好看的通过率或节省比例，标准需按业务确定。已有局部技术通过不能代替这些证据。FDE 收费方式、市场规模、客户购买理由及第二业务收益目前也没有足够材料，不在本章虚构商业结论。

### 9. 从认知得到的设计要求

现在才能得出后续设计必须满足的要求：业务使用者应直接进入案例与成果；方法开发者应直接理解和改进方法；资产跨案例存在并可复用；所有视角围绕同一业务目的和准确事实；异常、历史和接手是正常使用的一部分；单次处理、方法采用和用户接受分别表达。

这解释了此前前端为什么会持续令人不满意的一个主要原因：设计围绕技术对象和局部验收推进，没有始终从上述完整任务反推信息顺序与动作。结果即使能看到图、版本和记录，用户仍需自己拼出“现在在做什么、结果在哪里、我该判断什么”。这是基于此前反馈和使用观察的归因，不表示信息架构能解决全部问题；内容质量、故障与阅读细节仍需各自验证。

因此下面才进入产品设计。稳定侧栏、各入口数量、图与列表的分工都是对这些要求的方案，需要通过任务走查继续校正。

## 第二章 产品设计：从整体形态逐层推到操作

### 第一层 产品形态和外壳

用户需要反复进入、同时管理多份业务和方法，并在阅读、执行与比较之间切换。由此比较整体形态：

| 形态 | 适合什么 | 单独采用时的缺口 |
| --- | --- | --- |
| 单一聊天或固定步骤向导 | 表达模糊要求、辅助首次建业务或方法 | 缺少稳定对象位置，难以承载长期资产使用、并行生产与复盘 |
| 所有人都从完整方法图进入 | 方法理解、节点配置、准确运行诊断 | 日常找成果仍需跨过开发概念，直接业务任务不够清楚 |
| 只按案例或作品组织 | 日常完成业务和阅读成果 | 方法定义、跨案例改进和版本演进容易藏在详情深处 |
| 共享 Space 的持续工作台，按任务直接进入 | 兼顾业务生产、方法开发和资产使用 | 需要严格维护共同身份与返回上下文，避免三个入口变成三套互不相干的产品 |

因此建议采用**以业务 Space 为范围的持续工作台，左侧稳定导航，右侧随任务变化的主工作区**。日常默认从案例与产物进入；开发者从工作流进入；跨案例查找与复用从资产库进入。持续导航应便于反复切换，横向导航也可以承载同样结构；左侧栏是结合本轮用户提出的工作台样式选择的方案，并非所有工具产品都必须使用。

左侧保持当前 Space 与主要入口；右侧承担实际工作。顶部只展示当前任务的标题、范围和重要状态。详情在工作区内展开，长文和比较可扩大阅读。低频设置与运行诊断留在辅助位置，不争夺日常成果的注意力。

```text
┌────────────────┬───────────────────────────────────────────┐
│ 当前业务 Space │ 当前任务标题 / 所处范围 / 必要状态与主操作 │
│                ├───────────────────────────────────────────┤
│ 案例与产物     │ 本入口的列表、画布或正文                   │
│ 工作流开发     │                                           │
│ 资产库         │ 选中对象 → 原地详情 / 扩大阅读 / 对照      │
│                │                                           │
│ 设置与帮助     │ 返回后保留原来的对象、视图和筛选           │
└────────────────┴───────────────────────────────────────────┘
```

Space 切换只在存在多个可访问业务时承担真实选择，不为单 Space 增加空层级。整体视觉采用安静的工具界面：导航弱于主内容，正文有足够字号与宽度，颜色表达少量明确状态。方法图和案例图使用相同的阅读与返回方式；不靠重新换主题解决信息结构问题。

首次进入尚无方法的 Space，先看到业务目的、成功标准、已有样例和“形成第一版方法”的起点，不能要求用户对着空图猜下一步。已有可执行方法时，日常进入案例列表并提供新建业务；直接打开某个方法或资产链接时仍进入准确对象。再次进入优先恢复上次工作范围，不无故跳回一个与当前任务无关的统计首页。

### 第二层 左侧导航放什么

| 入口 | 为何独立存在 | 默认主体 | 不放在这个层级的内容 |
| --- | --- | --- | --- |
| 案例与产物 | 高频任务是完成一项业务、找到成果和待处理事项 | 按业务题目组织的案例列表；CONTENT 可以显示为选题与产物 | run、attempt、manifest 等技术对象不是平级菜单 |
| 工作流开发 | 理解、调试、运营观察和改进方法是另一种明确工作 | 可读的方法身份及其定义、运行、运营与演进视图 | 不把每一个技术版本永久塞进左栏 |
| 资产库 | 素材与中间成果可能脱离当前案例被查找、比较和复用 | 可搜索筛选的资产集合 | 不复制每份资产到不同工作台的独立存储 |
| 设置与帮助 | 低频管理 Space 信息、接入和操作说明 | 与权限相符的设置及帮助 | 不把模型凭据、原始日志默认露给日常用户 |

评价优先放在被评对象旁，版本演进放在工作流开发内。只有出现独立的跨案例审阅岗位与队列任务时，才考虑增加审阅入口。认知 Agent 的建议应附在问题、案例或改法上；当前不因它存在就新增一个装满原始聊天的主菜单。

### 第三层 案例与产物的主体

#### 案例列表

第一眼回答：做了哪些事、已有哪份可读成果、哪些需要处理、下一步是什么。主要操作是新建业务，其次是打开案例和筛选待处理事项。列表用业务名称、结果摘要、业务处理状态和更新时间帮助辨认，准确 ID 按需展开。

最新运行失败时，案例仍显示此前可用的成果与这次失败；不能让“最新”覆盖“可用”。排序可以优先待处理和最近活跃，但不要将最新稿默认当成被接受或应交付的稿件。

#### 新建业务

按工作内容组织输入：要求与用途、目标读者或使用者、材料与约束。允许从资产库选择准确版本，也允许导入当前支持的材料。清楚表达所用方法与是否可执行；有已采用且可用的方法时减少重复选择，无采用版本时明确选择候选而不自动采用。

发起前让人检查本次要求、材料和方法，显式启动后保留可返回的案例位置。配置高级参数属于可展开信息。普通委托不要求填写 A/B 假设；修改已冻结输入应形成清楚的新输入版本或运行，不覆盖过去。

#### 案例详情与案例画布

默认中心是“这次输入了什么，得到了什么，现在怎样处理”。案例画布先呈现关键输入、主要成果与关系；需要理解形成过程时，再展开研究、各轮稿件和意见。技术节点的控制流可从这里进入准确运行视图，不要求业务使用者先读懂全部节点。

主成果旁直接提供对应意见、前稿、处理建议与下一步动作。阅读一份稿件后能回到同一案例和轮次；查看来源时不丢失当前阅读对象。没有主成果时，说明还在运行、等待材料还是失败，并展示已有中间成果。

#### 结果处理

区分继续修订、选定成果、接受、导出和交付。每个动作要表达作用对象和后果。Agent 的处理建议保存为 Agent 意见；它不是用户接受，也不应伪装成流程内某个节点的终审。

交付后的反馈回到原成果和案例，才能用于以后改进。业务闭环应到可用成果及其处理决定，不能把“模型请求成功”或“保存了一条意见”单独作为结束。

### 第四层 工作流开发的主体

同一工作流内保留四种工作视图。选择器以业务可读的名称和变更用途区分版本，旁边清楚表达正在查看、当前采用、候选和可执行状态。准确部署版本和历史版本可以不同，不能把能看历史误写成能立即重跑。

| 视图 | 主体和默认信息 | 主要任务与联系 |
| --- | --- | --- |
| 方法定义 | 完整流程图、设计目的、节点职责与输入输出；点击节点先看合同和配置 | 无运行也能理解方法。编辑或发布形成准确候选；首期可由 Agent 与 CLI 修改，不要求先建设拖拽编辑器 |
| 运行过程 | 某次准确执行的实际路径、节点轮次、状态和产物 | 定位失败与返工，追到输入、稿件和意见，再回到对应案例；技术重试与业务改稿分开 |
| 运营观察 | 所选版本与时间范围内的业务表现、异常及关键阶段资产 | 判断是否有共性问题；明确样本、未评价和失败，不能从一个案例推总体质量 |
| 版本演进 | 方法前驱、变更理由、受影响节点、验证和采用决定 | 从某次改动进入准确案例与对照，再返回原版本；保持旧版生产与候选试验的区别 |

日常任务进入开发视图时，应携带原案例或资产上下文；开发者从问题追到产物，也应能回到原假设。工作流图、案例图和版本图表达不同关系，不能把它们混成一张包含所有内容的巨图。

### 第五层 资产库的主体

资产库服务“我想找某类材料或成果”，无需先知道它属于哪个 run。提供业务名称、类型、来源、产生阶段、相关案例及可用状态；按任务选择列表、缩略图或专用阅读器，避免所有内容都变成 JSON。

筛选围绕真实需要：版本、案例、节点阶段、时间、人工选定或评价状态。查看资产可阅读内容、比较准确版本、展开来源和使用关系，并引用到新的业务输入。名称帮助人识别，准确身份保证关系不串。

复用保留原来源和新用途，不修改旧内容。资产被淘汰可能只针对某次用途，不应仅凭一次评价就变成全局不可用。所谓“最好”也需要相同目的和可比较标准；当前没有校准证据时，不先做一个看似精确的排行榜。

#### 辅助入口：设置与帮助

主体按业务信息、执行接入和操作说明组织。业务信息说明这个 Space 服务什么目的、适用范围与成功标准，修改目标要留下时间与版本，不能静默改写历史判断。执行接入说明当前可用能力和影响范围；具体某版方法的模型、Prompt 与工具配置仍在方法上下文查看，不混成一个全局开关。

帮助优先解释当前任务中的术语和继续方式，并能返回原案例、方法或资产。没有多用户权限、多个 Space 或某类接入实现时，不展示假定可用的管理按钮；也不以“设置未完善”为由阻塞已支持的正常业务。

### 第六层 详情阅读与就近判断

短配置和轻操作用侧面详情，完整文章、长报告、大图及双稿比较提供扩大阅读。先给内容与必要结论，再按需展开证据、关系和技术追溯；不要让一大段机器结论和标识占满首屏，把真正的稿件挤到下面。

正文、画面、对应意见、来源与关系按业务类型组织。比较先让人知道两边是什么、为什么比较、条件有何变化，再并看内容与各自评价。保存的摘要应能扫描到收益、代价、未知和处理决定，完整依据仍可展开。

返回应恢复原案例、版本、轮次、筛选和视图。跨入口跳转尽量携带这些范围，不用用户记编号再次搜索。正在填写的反馈不应被后台刷新覆盖。

### 第七层 对象与状态支撑这些界面

Space 持有业务目的；方法版本描述允许怎样做；Case 表达一次业务要求；准确输入与方法形成一次 Run；Run 中的节点实例产生 Asset；评价针对准确资产；比较连接明确条件下的结果；方法改动关联问题、验证与采用决定。

这条关系说明为什么三个入口应共享事实。一个 Case 可经多个方法和多次运行产生多份结果；一份资产可用于多个后续案例；一次差评既可能要求修这份稿，也可能支持修改未来的方法，两者要分清。产品对象不是必须逐项新建一张表的要求，优先复用已有合同。

| 状态 | 用户应得到的反馈与可继续的工作 |
| --- | --- |
| 尚无方法或案例 | 明确产品用途和起点，不显示大量没有解释的空表 |
| 加载中 | 保留所选范围，说明正在读取哪类内容；不先将空数据误报为没有成果 |
| 正在执行 | 表达当前阶段、已完成产物、可用操作和返回位置 |
| 部分完成或失败 | 同时表达失败位置与已有成果；处理建议可以保存，恢复或重跑仅按真实能力提供 |
| 需要人处理 | 说明需要决定什么、针对哪份内容、作决定后会怎样 |
| 多个候选或历史并存 | 可读名称、用途与状态足以区分；归档历史不占据日常列表，也不悄悄破坏所需证据 |
| 离开后重开 | 从持久记录恢复业务处理状态、建议和下一步，而非从聊天摘要猜测 |

## 第三章 对照现状决定下一阶段

### 现有能力该保留什么

应保留已经形成的准确方法身份、输入快照、运行与节点记录、资产正文和关系，以及评价、比较和 iteration 的存储。它们支持三个入口共用事实。现有完整方法图、稿件阅读器、对应意见、准确双稿和迭代读回是可继续组织的能力，不应因整体体验需要改进而全部推倒重建。

截至 2026-10-07 的[建设记录](../vendor/agent-workflow/docs/harness-roadmap.md)明确：MiMo 有界对照和单案例路径已完成，内容仍未收敛；普通 Kimi/GLM Case 已真实发起，主编响应解析失败，已有四项产物保留，失败稿处理建议和重开仍待最终验收。因此不能继续说“完全不能新建业务”，也不能说日常业务闭环已经完成。

新的案例与产物入口、案例关系画布属于已明确的产品方向，尚不能因文档存在而算作实现。跨案例资产使用、稳定运营复盘、完整交付与反馈、第二业务复用仍需要按实际任务逐项建设与验证。

### 下一阶段为什么这样取舍

当前要改善的是“人能理解并完成真实业务，同时开发者能据此改进方法”。据此比较几个方向：

| 方向 | 解决的问题与依据 | 当前取舍 |
| --- | --- | --- |
| 把案例与产物任务组织完整 | 已有能力仍要求人沿技术对象寻找成果；用户最新明确要求日常从案例进入 | 优先解决整体使用结构，复用已存在及正在收尾的普通业务能力 |
| 继续扩充方法图细节 | 帮助开发者理解配置和运行 | 保留并补影响任务的断点，但它不能替代日常业务入口 |
| 改进审阅建议的一致性 | 已有真实改稿意见前后反转的证据，影响内容质量 | 保留为明确的方法假设；单独验证收益和误伤，不能用它替代产品结构建设 |
| 建完整运营看板和自动评分 | 支持多案例稳定使用后的集中判断 | 场景和对象关系现在就考虑；完整实现与评分校准在有代表性案例后推进，不用空图填满界面 |

建议的第一段交付是：**在稳定工作台外壳中，业务使用者能从案例找到输入、成果、对应意见及处理状态，完成当前支持的业务动作，并在重新进入时继续；方法开发者仍能直接进入完整方法与准确运行。** 这比“再跑一个案例”更具体地定义了产品成果，也比“重做整个前端”更有边界。

当前已授权新案例的失败处理和重开收尾可以作为这段设计的真实样本，不必为验证界面再消耗一次相同模型运行。技术解析故障按影响处理，但它不能独自决定整个产品的下一轮范围。完整交付动作、资产复用与周期复盘继续在全局模型中保留，按任务依赖逐步接入。

这份排序是基于当前目的、场景和证据提出的方案；用户新增的业务优先级或实际使用反证可以改变它。更换配色、增加首页统计、自动采用或全面可视化编辑，都不是当前已证明的先决条件。

### 怎样验证整体设计成立

| 使用任务 | 应观察到的结果 | 不足以证明通过的现象 |
| --- | --- | --- |
| 日常用户找最近一件业务 | 不记技术编号就能找到输入、主要成果和待处理事项 | 有案例选择器，但仍需从聊天取得 run ID |
| 阅读失败任务的已有稿件并留下处理建议 | 失败原因和可读成果并存，建议绑定准确对象，刷新后可恢复 | 运行显示红色或数据库里有一条意见 |
| 开发者理解未运行的方法 | 能解释节点为何存在、需要什么、怎样返工和停止 | 图能显示，但点开只有空产物 |
| 从成果追问原因再返回 | 能找到准确输入、对应意见和产生轮次，返回不丢上下文 | 相关页面分别存在 |
| 判断一次方法改动 | 能解释改了什么、比较了什么、收益与退化、为何采用或未采用 | 出现新版本、比较分数变高或测试通过 |
| 跨案例复用一项材料 | 找到准确资产、理解适用性并直接用于新任务，来源保留 | 只能下载后重新上传，或只保留文件名 |
| 稳定使用后集中复盘 | 选定范围并解释反复问题，知道样本差异和未评价项 | 单个成功案例或没有真实样本的统计图 |

每轮选择与其改动相称的任务验证，不要求每次跑全套。技术检查、使用任务、内容质量与用户接受分别说明。认知 Agent 应把新证据怎样改变了原先理解写清楚，而不是只报告检查完成。

### 维护方式

本页形成设计推导；确认后的产品规则回到产品定义和工作台定义，实施变化回到建设路线。不要同时维护相互竞争的“唯一状态”。此前文档里旧入口、旧前端状态与最新建设记录冲突时，以准确当前现场核对并在所属文档修正，不用复制整套历史来回避冲突。

本项目的 `.agents/skills/product-cognition/` 提供上述认知方法。它要求从完整产品推到具体设计，再从实际使用返回修正理解；它不要求所有产品都采用左侧栏，也不自动授权任何实施、模型调用或数据清理。
