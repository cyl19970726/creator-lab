# 关键决定与状态：让布局支持正确行动

[返回产品设计](README.md) · [整体布局](layout.md) · [认知依据](../product-understanding/decisions-and-evidence.md) · [反例走查](walkthroughs.md)

本页把已有布局继续推导到内容、状态和动作。**这是可审阅的设计提案，没有实现新的前端或运行能力。** 保留 Space → workflow → 准确版本的外层结构；下列信息放在它所影响的决定旁，不因发现新关系就增设一级菜单。

信息应放入现有 Archify 画布、选择详情及相应的检索／阅读区域；本页不规定另一套展示组件。当前逐页说明见[页面线框与推导原则](wireframes.md)。

## 1. 从外壳到主体，怎样逐层承载这些判断

| 层级 | 常驻什么 | 为什么放在这里 |
| --- | --- | --- |
| Space | 业务目标与用途；当前工作对象；业务案例入口 | 委托人先完成业务，不必先理解实验管理 |
| Workflow 跨版本入口 | 版本总览、真实遗传关系、服务与复盘 | 方法比较与持续业务表现不能被某一版的页面范围限制 |
| 当前准确版本 | 设计目标与改动、方法与产出、案例与资产、评价与分析、调优与后继 | 连续认识这一版，不需在不同模块手工拼版本身份 |
| 版本主体顶部 | 查看版本；适用目标；采用范围及记录；当前可执行状态 | 防止把正在查看、应当使用和能够运行混为一谈；无采用范围时直说未采用 |
| 主体内部 | 当前判断所需的证据范围、缺口和下一步 | 对账、运行核对和采用说明属于任务内容，不另造顶层导航 |
| 节点／资产／评价详情 | 具体内容、准确身份、来源依据、返回位置 | 从结论下钻到事实，再回到原问题 |

侧栏中的“案例与资产”仍以实际历史为默认；“评价与分析”内部提供“验证覆盖”与原始评价的连续阅读。两处引用同一 run 与计划记录。点击计划未开始项只看待验证要求，不能伪造一个实际 Case 运行图。

## 2. 方法与产出图：先看交付关系，再核对自主空间

默认图保留关键 Agent、预期资产、控制关系和返工／结束条件。选中一个节点后，右侧按下面顺序展开：

```text
作者 · 负责交出可供审阅的稿件

设计声明
  输入：业务要求、已提供来源    输出：稿件及依据
  可自行决定：组织与表达路线
  不足时：返回缺失材料；本例不允许联网补源
  结束／升级条件：按该版合同说明
  方法：Prompt、tools、可选 skill、执行器与资源约束

执行绑定
  这一准确版本＋入口当前可否执行？
  绑定实现与已核验资源；未核验项明确保留

本次记录（选择 run 后出现）
  实际交付的材料范围与有效配置
  与设计不同的条件、可观察的选择和人工介入
  输出／缺口 → 打开实际资产或待处理决定
```

这是示意内容，不替业务制定统一授权宽度。没有运行时，只显示前两层；没有配置证据时显示未知，不给“完全一致”标记。节点自主探索不要求逐步写思考过程，也不拆成大量工具节点。只有影响业务判断的选择、边界变更和产物需要可追溯。

出现缺口时，详情应回答“缺什么、谁能决定、哪些工作可以继续、决定影响哪次执行”。具体暂停／恢复按钮只在执行器支持时提供；否则明确结束当前尝试并准备后续尝试。已保存输入不能被编辑为“它当时就有这些材料”。

## 3. 版本证据主体：实际使用与计划验证分开，对同一事实连续下钻

以下为模拟内容布局，数字来自本页下方的固定样例，不能当成产品实测。

```text
CONTENT / v2                          查看 v2 · 尚未采用
设计目标：检验改动 H                   执行可用性：另行核对

评价与分析
  范围：验证计划 P · 准确输入和条件 · 截至 T
  [读综合分析]  [验证覆盖]  [原始评价]

  v2 计划 2 项：完成未评 1，未开始 1
  失败和未评均保留；此处尚不能判断 v2 可替代 v1

  验证计划项：
  Case A / v2 / 计划 1 项，实际 run 1 → R3 完成，尚未评价 → 读成果
  Case B / v2 / 计划 1 项，实际 run 0 → 未开始            → 读计划要求

  [对照 v1 在本计划中的证据] [查看 v2 全部已记录运行]
```

固定样例 P 在 A、B 两个 Case 上分别要求 v1、v2 各一次，共四个计划项：

| 计划项 | 准确关联的尝试 | 状态与解释 |
| --- | --- | --- |
| A × v1 × 第 1 次 | R1 | 执行失败，保留中间资产；不是“评价不合格” |
| A × v2 × 第 1 次 | R3 | 执行完成，尚未评价 |
| B × v1 × 第 1 次 | R4 | 执行完成，有评价；评价内容另外阅读，不预设优秀 |
| B × v2 × 第 1 次 | 无 | 未开始，不能从结果列表中消失 |

另有 A 在 v1 的 R2，执行完成且有评价，但没有归入 P。于是 P 是 **4 个计划项，3 项已启动，2 项执行完成，1 项有评价**；v1 的全部已记录实际运行却是 **2 个 Case、3 次 run（R1、R2、R4）**。v2 的实际记录是 **1 个 Case、1 次 run（R3）**，B 还只是待验证项。R2 不能因为成功就静默替代 R1；若要把它纳入分析，说明新范围与理由，保留原计划证据。

主体应明确准确版本／入口、截止时间、筛选、分页及可见范围。默认保留失败和未评，主动筛选后显示排除了什么。材料不足、没有启动、无成果、尚未评价、评价存在但范围不适用，都不能折成一个零分或绿色完成比例。

计划覆盖完整也不自动代表业务覆盖充分。综合分析另说明代表哪些业务、标准、输入与条件；目标或评价标准改变时，保留旧评价适用范围，指出需要补验的部分。评分规则继续待定义。

## 4. Case 资产图：边也有证据详情

实际资产图沿用列表、关系图和按 run 聚焦的结构。默认边用业务语言表达，点击后显示依据：

| 可见关系 | 详情需要读到什么 | 不应出现的暗示 |
| --- | --- | --- |
| 交付给节点 | 准确资产／投影版本、交付范围、节点与 run | 已交付就是 Agent 已理解全文 |
| 工具读取记录 | 读取事件、返回范围与来源 | 无此事件就是没得到材料 |
| 声明依赖／引用 | 由输出声明还是合同映射产生，指向哪份材料 | 一条声明边等于引用已被核查 |
| 经核查的来源支持（具体记录方式待设计） | 核查者、具体片段、来源、意见及适用范围 | 局部核查等于全部正确 |
| 生产／修订／评价 | 准确生产者、前稿或评价对象及依据 | 时间接近就是因果，预期产物就是实际产物 |

预期图继续表达“打算读什么”；实际图表达“观察或记录了什么”。不为追求连通而补造关系。缺失信息影响质量归因时，从该节点关联待查问题，而不是让操作者猜。

## 5. 调优与采用：结论必须有作用对象和后果

“调优与后续版本”主体按问题 → 证据 → 原因假设 → 改动 → 验证 → 决定连续排列。同一条决定可从前版与后版进入。以下几种情况要产生不同的下一步，不能都变成“生成 v3”：

| 当前判断 | 下一步及留存信息 |
| --- | --- |
| 计划缺项或评价缺失 | 补足影响决定的证据，保留现有版本及未知；是否值得继续验证由负责人判断 |
| 目标或标准改变 | 明确新的要求及旧证据适用范围；按影响补验，不抹掉旧结果 |
| 改善可能来自输入／部署变化 | 核对执行条件，收窄原因判断；需要时设计能区分原因的尝试 |
| 候选没有优势或代价不值得 | 保留不采用／停止投入的理由；继续可用的旧方法 |
| 问题在共享底座 | 关联 dogfood issue 与原业务复验；不伪装成 Prompt 已解决 |
| 证据足以支持限定范围的采用 | 由有权者作决定；说明范围、证据和未来业务如何使用 |

采用前在同一主体给出可检查摘要：目标版本、适用范围、替代的决定、证据与未知、决定者、开始生效的条件。**这里的适用范围及派发消费方式是待落实的提案；当前具名 slot 指针不能自动实现它。** 不添加一个看似有效、实际不影响新业务的“采用成功”按钮。

新业务发起处消费这一决定，而不是只展示它。建议先支持明确选择与单一适用关系；复杂规则有真实需求后再扩展，不先建设通用规则引擎。

| 发起时的组合状态 | 主体表达与可继续的动作 |
| --- | --- |
| 适用采用版明确且可执行 | 展示最终准确版本及选择依据；检查本次输入后启动 |
| 适用采用版明确但不可执行 | 保留 Case 与材料，说明缺失条件；等待恢复，或由有权者显式改派；可执行候选不自动接管 |
| 没有采用决定，或多个范围冲突 | 要求明确选择；说明本次是候选试跑还是有记录的业务例外，不偷偷新增采用决定 |
| 采用决定已变化，但旧 run 正在执行 | 保留旧 run 绑定；后续任务按新决定处理，不能把运行中的版本换掉 |

“采用”与“启动”是不同动作。开始时保存最终版本与选择依据；业务反馈关联当时的决定和成果，才能在服务与复盘中知道哪些采用范围值得继续、收窄或回退。

## 6. 下一项验收同时覆盖理解、执行与业务价值

先沿同一组静态线框推演三条任务：读懂准确版本和缺失验证；辨认节点材料不足时的授权边界与下一动作；辨认采用版不可执行而候选可执行时怎样处理新委托。这里检查信息和行为设计是否足以支持决定，不能证明实际节点会发现缺口、停止或升级，也不能只检查版本菜单齐全。当前不新增可操作原型。

这轮设计走查通过后，选择当前 CONTENT 上的一段真实任务验证：workflow 实际完成了什么、用户仍做了哪些解释和救场、产物能否用于原用途。优先修妨碍该任务或使判断失真的缺口，不因本页列出了很多信息就按栏位数量排期。UI 可理解、执行合同得到遵守、业务结果有效分别报告。本轮仅修订认知与设计文档，没有新跑业务；后续需要真实任务才能验证执行与价值。
