# 场景走查与下一步

[返回产品设计](README.md) · [布局首稿](layout.md) · [认知验证方法](../product-understanding/review-and-validation.md)

2026-10-09 当前以[页面线框与推导原则](wireframes.md)解释布局与连续操作，沿用现有 Archify 基础。此前[合成原型的走查](prototype-round.md)保留为历史观察，原型已停止推进。下文保留任务及失败条件，不将书面推演改写成实测。

以下是用于检验设计的书面任务推演，**不是产品已支持或实际使用通过的声明**。版本、Case 与观察窗口均为示例。不能因为每一行都有一个页面名称，就认定任务已经成立；线框用于检查信息与动作的设计，实际产品仍需验证它们是否可理解、可发现，以及结果是否有用。

## 优先走查：完整认识一版方法及其后继

任务不是“找到设计页、找到评价页”，而是回答：这版为什么存在、怎样做、实际做过什么、哪些证据说明效果，以及下一版为什么这样改。

使用一个明确标为模拟的反例集合：Case A 在 v1 有 R1、R2 两次运行，在 v2 有 R3；R1 失败但留下中间资产，R2 有结果和评价，R3 完成但尚未评价。评分规则保持未定义。先只从前端取得信息，完成后再用 CLI 对照事实，分别报告界面遗漏与底层缺失。下面的验证计划反例继续扩充同一集合。

| 用户需要完成的判断 | 预期入口与连续动作 | 必须保留的范围与结果 |
| --- | --- | --- |
| 理解目标与版本动机 | 业务目标与问题 → 版本总览 → v1 的设计目标与改动 | 看清首版设计依据；进入 v2 时能回到前版问题及证据 |
| 理解完整方法与预期成果 | 当前版本的方法与产出图 | 关键 Agent 默认可见会产生什么资产及下游用途；没有运行也能理解方法 |
| 读全这一版的 Case | v1 → 案例与资产 → Case A | 只统计一个 Case，但列出 R1、R2 两次及失败；v2 对应同一 Case 只列 R3 |
| 读懂实际资产关系 | Case 的资产列表与关系图，选择运行或跨运行观察 | 全部有权限的已保存资产可遍历；关系带准确来源；预期但未生成的资产不能冒充实际产物 |
| 看评价并形成判断 | 评价与分析 → 原评价、资产和准确运行 | 能区分不同判者、标准与材料范围；未评或评分未定义不展示为零分 |
| 理解下一版怎样产生 | 调优与后续版本 → 问题、原因假设、改动、候选和验证 | Evaluator 结论、分析判断、版本产生与采用是不同事实；可以不改或转项目问题 |
| 跨版追溯并回来 | 版本遗传图谱 → v1→v2 的边 → 原 Case／评价 → 返回 | 可解释继承理由；回到原版本、运行和阅读位置，不依赖手记 ID |

**会推翻布局的观察：** 一个版本的 Case 列表夹入另一版的运行；只显示最新资产却宣称全部；原始意见无法追回；下一版只有版本号没有改动依据；Agent 必须在 UI 之外补查才能理解，却把结论写成前端已表达清楚。失败时先修范围与关系，再调整菜单。

下面先检查三项会改变决定的反例，再用首次形成方法、并行服务和项目改进场景检查起点、并行情况及跨层依赖。

## 三个必须并列走查的决定

这些任务在线框阶段只推演识别情况、取得材料并选择下一步所需的设计；它们不证明操作者实际能完成，更不证明 Agent 能发现缺口、执行器能暂停，或采用已自动影响派发。

| 反例与固定材料 | 操作者要回答什么 | 会推翻设计的表现 |
| --- | --- | --- |
| 验证计划 P 要求 A、B 在 v1、v2 各一次；关联 A/v1/R1 失败、A/v2/R3 未评、B/v1/R4 有评价、B/v2 未开始；A/v1/R2 有评价但在 P 之外 | 为什么现有成功成果不足以判断 v2 可替代 v1？P 是 4 项、3 项启动、2 项完成、1 项有评价；v1 历史却是 2 个 Case、3 次 run | 把未开始项隐藏；把 R2 静默替代 R1；把未评算低分；混淆实际 Case 数与待验证集合 |
| 当前 CONTENT 工作台入口的节点发现现有材料不足，本次不允许联网；输入资产图上有一条来自绑定的“交付”边 | 缺什么、能自行处理到哪、需要谁决定、追加材料会影响哪次执行？交付边能支持什么结论？ | Agent 需私下补源才能完成设计中的成功路径；修改旧输入冒充原材料齐全；把输入绑定当成已正确引用 |
| 某范围采用 v1，但 v1 当前不可执行；v2 候选可执行，有新委托到来 | 正常应使用哪版、阻塞在哪里、可等待还是需显式改派、哪些旧 run 不受影响？ | 自动换成 v2；仅写“已采用”却解释不了下次用哪版；为改变未来采用而改写在途 run |

具体主体、边的详情和动作提案见[关键决定与状态](decisions-and-states.md)。该页及本表中的样例均为模拟，不冒充实际业务覆盖或实验结果。

## 场景一：没有历史的新业务，怎样形成首版

起点：操作者有一个业务目的和少量样例，尚无完整方法，也未明确所有成功标准。目标：形成有理由的可执行 v1，完成首个真实 Case，知道成果怎样处理以及哪些假设需要修改。

| 连续任务 | 布局中的位置与必要信息 | 保存什么，后续怎样继续 |
| --- | --- | --- |
| 表达目的与未知 | 尚无 workflow 时从 Space 初建主体开始；要求、样例、约束、标准与未决问题 | 可恢复的业务理解归 Space；材料不足时知道补什么，不只留下聊天 |
| 形成并检查方法 | 创建具名方法草案后出现 workflow 导航并进入方法与产出图；已有草案则直接继续；展示设计理由与完整图、资产交接及评价停止规则 | 首版与假设；关联原业务目标，执行缺口可关联项目依赖，不生成假定可用的按钮 |
| 准备第一项业务 | 首版关联的新 Case；具体要求、准确材料、方法与运行条件 | 冻结输入和准确执行对象，发起前可检查 |
| 阅读实际工作 | Case 主体呈现成果，按需展开中间资产与准确运行图 | 技术状态、业务评价与人工介入分开；可从失败处继续判断 |
| 处理成果与方法 | 修本次作品留在 Case；方法问题带证据进入调优与后续版本 | 可用成果及处理决定；首版可直接验证采用，也可继续实验或停止 |

**会推翻这版布局的观察：** 操作者仍需在工作台外重新拼装目标、图、节点方法和试跑条件；无法知道首版为何这样设计；缺材料与缺基础能力混在一起；拿到结果却找不到形成它的方法。任一情况都要求回头修任务或对象关系，不能只改菜单名称。

## 场景二：稳定业务与候选研发同时进行

起点：v1 在明确范围内持续处理 Case A、B；维护者在研究 v2。目标：日常业务继续，v2 在明确条件下验证，比较后由有权者作决定。

| 连续任务 | 布局中的位置与必要信息 | 必须保持的边界 |
| --- | --- | --- |
| 开始或处理业务 A | 全部业务案例；所用方法、输入、结果和待处理项 | 打开研发页不改变 A 的方法与状态 |
| 从 B 的不足发起研究 | B 的成果与评价 → 调优与后续版本；带入准确对象和问题 | 不默认所有不足都该升级 workflow，也不把 B 复制为新实验对象 |
| 构造与试跑 v2 | 同一调优任务 → 方法与产出图 → 返回验证；假设、差异、案例与条件 | 新候选不静默替换当前采用版；原始输入及尝试保留 |
| 比较并决定 | 调优与后续版本；完整产物、改善与退化、条件变化、代价 | 技术通过、评价意见、发布和采用分别表达 |
| 继续服务并观察 | 服务与复盘；采用范围、观察窗口、案例及评价覆盖 | 方法无变化也可继续；只看了少量成功案例就不能宣布稳定 |

**会推翻这版布局的观察：** 操作者在三个入口重复找同一个 Case；无法分辨“查看 v2”和“业务采用 v2”；比较只剩分数而看不到原文；从某次运行返回后丢了原问题与验证集合。

## 场景三：真实任务发现底座问题，修复后如何回来

起点：一个 Case 的资产交接失败。原因可能是当前输入配置，也可能是共享存储缺陷。目标：查明影响、让可以继续的业务继续、将项目问题交给适当负责人，并在交付后复验原任务。

| 连续任务 | 布局中的位置与必要信息 | 可观察的结束条件 |
| --- | --- | --- |
| 区分原因与范围 | 原 Case → 准确运行与资产；实际输入、配置和失败证据 | 有证据的原因判断，或明确缺什么证据；不先把错误全归于 Prompt |
| 分流处理 | 配置调整进入相应方法任务；共享缺口关联项目 issue | 项目责任、影响和优先级另行判断；发现不等于立即建设 |
| 处理当前阻塞 | 原 Case 显示影响步骤、可用成果及临时处置 | 非阻塞部分继续，阻塞部分明确等待或有记录的替代处理 |
| 项目交付返回 | 原 Case 与受影响候选可见交付依据及待复验状态 | 按实际能力开展复验，记录有效环境与输入；不能凭 issue 关闭宣布恢复 |
| 保存复验结论 | 原任务的结果、项目引用和相关验证保持关联 | 失败仍留待处理；成功也不自动采用其他 workflow 候选 |

**会推翻这版布局的观察：** 找到 issue 却找不到它阻塞哪些任务；共享修复没有回到业务的入口；复验失败但界面显示整个问题已解决。此时缺的是跨层状态和责任的表达，新增一个“项目问题”菜单未必有效。

## 还要补查哪些边界

| 场景 | 需要检验的设计关系 |
| --- | --- |
| 上次运行失败，但以前有可用成果 | Case 同时保留失败信息和原成果，不用“最新”覆盖“可用” |
| 从资产库复用一份材料到新业务 | 读内容与来源，引用准确版本，保留原来源和新用途；不能静默改变旧资产 |
| 离开后换人接手或直接打开链接 | 恢复目的、对象、方法、问题与下一步；无需靠私人会话摘要猜测 |
| 评价意见相互矛盾 | 展示用途、标准、判者和证据，必要时校准评价；不机械取平均当结论 |
| 查看历史方法，运行环境已不可用 | 历史仍可读，执行动作按真实能力表达；不把归档版本伪装成可重跑 |

## 当前交付与后续检验

用[静态线框](wireframes.md)说明完整版本认知路径及三个决定反例，再用首次形成、并行服务和项目复验检查起点与依赖。复用 Archify 画布、准确对象和返回语义，各页说明内容、关系、选择后的详情与结果；不把制作演示前端作为本轮必要步骤。图中样例均为说明设计，不冒充真实运行。

观察操作者能否找到入口、理解范围、完成决定和返回原对象；记录具体阻碍及原因假设。再对照现有能力形成建设取舍：复用哪些完整能力、修改哪些交互、哪些缺口需项目建设。后续选择一段真实 CONTENT 业务检查运行行为、成果用途和人工介入；版本阅读通过不能代替这项验证。当前书面稿不提前宣布优先改哪一个前端页面，也不把“认知已完善”当作一次性验收结论。
