# 产品设计：从认知逐层推导使用方式

从 [产品架构](../../vendor/agent-workflow/docs/product-architecture.md)进入 [前端与交互导览](../../vendor/agent-workflow/docs/interaction-design.md)，再阅读本组的具体布局、线框、状态与走查；正式交互要求仍由 vendor 的合同维护。

[产品认知](../product-understanding.md)解释目标、范式、生命周期、责任与边界。本目录在这些依据上决定整体形态、信息层级、导航、各主体和连续操作。设计也会暴露认知中的缺口，应回到对应章节修订；不是等认知绝对完备后才允许画草图。

## 当前推进范围与设计检查方式

2026-10-09，目标／版本展示、方法预期资产图和只读 CLI 已完成一批工程接入，但 Space 仍缺少实质业务理解，版本说明也未解释设计缘由。当前先完成“形成并保存 Space 业务理解 → 推导首版方案 → 关联准确版本”，再随真实 Case、评价和迭代逐段构造、使用产品。当前阶段与验收以[建设路线](../../vendor/agent-workflow/docs/harness-roadmap.md#下一步按什么顺序推进)为准；已有图和阅读能力继续复用。

以下是每一阶段适用的设计检查方式，不要求先完成全部页面再使用：

1. **用线框检验结构。** 从业务目的到任务、对象和责任，检查布局是否支持两条并行过程：日常完成业务，持续形成和改进方法。每页同时说明进入理由、主体、点击详情和下一步。
2. **沿关键场景核对连续性。** 从设计目标到方法产出、全部 Case 与资产关系、评价分析和后继版本；加入计划未开始、材料不足、采用版不可执行的反例，再检查首次形成方法与项目复验。用线框指出所需内容，不新增一套演示前端。
3. **对照现有工作台核实基础。** 已有的 Archify 图、节点选择、详情与阅读能力直接沿用；预期资产入图、完整 Case 范围和演化关系分别说明需要怎样补充。Agent 经前端取得的认识与 CLI 核对分开，底层可查不代表界面表达清楚。
4. **对照现有能力选一段实现。** 把各动作标为可复用、需调整、缺失或尚未核实，并附证据；再比较收益、依赖与代价，选择一个有业务意义的完整任务。当前实现事实写回建设状态，不另造平行路线图。
5. **交付后回到同一任务实用。** 阅读真实成果与过程，观察是否满足用途、Agent 是否在边界内完成、用户做了多少解释和救场，再判断改进是否值得。新业务形成首版与第二业务复用保留为独立价值假设，不能靠版本图完整宣布通过。技术检查只证明其覆盖的技术部分。

本阶段重点修正 P01 业务目标与 P03 版本设计的内容及承接关系，让人能理解、保存并继续形成首版；其他线框保留作后续阶段参考。静态线框不能证明实际可用性，历史合成走查也不能证明真实执行效果。
