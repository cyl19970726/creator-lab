# 整体布局：围绕业务目标与 Workflow 版本组织证据

[返回产品设计](README.md) · [页面线框](wireframes.md) · [认知依据](../product-understanding/responsibilities-and-objects.md) · [关键决定与状态](decisions-and-states.md) · [场景走查](walkthroughs.md)

**用户在 2026-10-08 进一步明确：Space 对应一个业务目标；每个 workflow 版本有设计目标、产生动机、完整方法、实际跑过的案例与评价，经过分析和调优产生下一版。** 整体工作台应让人顺着这些关系认识方法、判断效果并决定下一步。

**布局沿用已确认的 Archify 主画布与点击对象后展开详情。** 现有工作台已经建立这项基础；本轮补充它应承载的业务关系、对象范围和入口，不重新发明卡片式流程。流程、资产关系和版本演化使用画布；检索及覆盖对账使用列表；长文进入同一阅读区。逐页表现与理由见[静态线框](wireframes.md)，本轮不再推进可操作低保真。

上一稿已有版本、历史和资产关系的表达，但没有把“完整认识一版方法及其演化”持续落实为本轮设计的验收任务。字段存在不足以证明用户能连续回答“为什么有它、它做过什么、效果怎样、为何改成下一版”；需要用具体路径检验，不能把这个问题简单写成旧稿完全没有版本。下文据此重推结构；具体名称与排列是提案，评分机制尚未定义，产品功能没有因文档更新而实现。

## 1. 先推导完整的工作对象

Space 保存持续业务目标、要解决的问题、使用情境、约束与成功标准。Workflow 表达为该目标工作的可演化方法；准确版本是一次明确方案，包含节点、Prompt／tools、可选 skill、资产合同与执行配置。每版必须能够独立解释自己的目标、来源和适用范围。

首版来自业务目的、已有材料和设计假设；后继版来自有依据的发现与改法。一次改进可以涉及方法、输入、评价方式或项目依赖，不预设每次都必须增加版本。Case 是一项具体业务要求，可以由不同版本反复处理；每次 run 绑定准确版本、输入和条件，并留下资产、失败和介入记录。评价针对准确对象，分析把这些证据组织成原因判断；候选改动再接受验证与采用判断。

```text
业务目标（Space）
  → 首版的设计目标与方法
  → 准确版本 × Case × 输入 → 实际运行与资产
  → Evaluator 评价 + 用户反馈 + 执行证据
  → 分析原因、提出改法 → 后继候选版本 → 比较验证与采用判断
                                      ↘ 不改 / 暂缓 / 回退 / 项目问题
```

这是因果关系，不是固定向导。稳定版继续完成业务，候选可以同时试验。版本谱系也不一定是一条直线：真实分支、失败候选和被采用路径都应保留；关系依据是实际前驱与改动记录，不能按创建时间自动连线。

## 2. 左栏怎样承载这些关系

左栏首先保持业务范围，然后明确正在研究的准确版本，再提供该版本的几个固定入口。版本总览和遗传图谱负责跨版本判断。日常跨版本找业务、复用资产和持续服务另有入口，但读取同一批事实。

```text
Space：内容创作
业务目标与问题

▾ 工作流 · CONTENT
  版本总览
  版本遗传图谱
  ▾ 当前查看：v2 · 改善论证结构    [切换版本]
      设计目标与改动
      方法与产出图
      案例与资产
      评价与分析
      调优与后续版本
  服务与复盘

全部业务案例
资产库
设置与帮助
```

v2 及其名称仅是结构示例。**工作流标题可展开、版本是核心工作对象属于已确认方向；这里的具体菜单名称和分组仍待走查。** “切换版本”应可搜索、辨认并切换准确版本；版本多时不把全部版本及其子项永久铺满侧栏。进入新版本后保留同类任务，如从 v1 的评价切到 v2 的评价，同时清楚更新范围。

“设计目标与改动”讲这一版为什么存在；“业务目标与问题”讲 Space 长期为什么存在，两者关联而不互相覆盖。版本的案例入口仅列该版实际处理过的 Case；“全部业务案例”从业务要求出发查看跨版本历史。两个入口是相同对象的不同范围，不能生成两套 Case 状态。

计划要求但尚未开始的 Case／尝试在“评价与分析”的验证覆盖中对账，不混入实际运行数；从计划项进入时明确尚无 run。版本主体还要标出证据范围、截止时间与未知，详见[关键决定与状态](decisions-and-states.md)。

“设计目标与改动”记录本版的来路，“调优与后续版本”记录从本版证据出发的后续判断；同一条 v1→v2 变更可从 v1 的后继入口或 v2 的动机入口阅读，共用一份记录。

右侧顶部持续展示版本号、可读名称、版本身份及查看／采用／执行可用性。中间承担当前任务的图、正文或比较，侧面详情按选择出现。切版本不会采用它，折叠导航不会取消任务；深链接恢复版本、Case、run 或评价对象及返回位置。

## 3. 每个主体放什么，为什么

| 入口 | 默认主体必须让人知道什么 | 从这里怎样继续 |
| --- | --- | --- |
| 业务目标与问题 | Space 服务谁、要解决什么、什么成果有用、约束与尚未确定的标准 | 查看这些目标对应的方法与未解决问题；无 workflow 时由此形成首版 |
| 版本总览 | 可读版本号与名称、设计动机、前驱、采用与可执行状态、跑过的案例与结果覆盖 | 进入准确版本；按明确对象比较或进入遗传图谱；无评分规则时明确待定义 |
| 当前版本 → 设计目标与改动 | 这版解决什么；首版的设计假设，或从哪版的哪些问题和证据产生；具体改了什么及预期收益 | 打开原问题、原案例、相关评价和变更节点；查看验证结果是否支持当初动机 |
| 当前版本 → 方法与产出图 | 完整流程、关键 Agent／程序职责、预期资产、预期使用关系、自主空间及返工／升级／停止规则 | 点 Agent 区分设计声明、执行绑定及本次记录；点预期资产看合同并查看相关实际产物 |
| 当前版本 → 案例与资产 | 本版实际跑过的完整 Case 集合，每例的运行次数、结果与失败、评价覆盖 | 打开 Case 查看本版全部运行和资产关系；可明确切换到该 Case 的跨版本历史 |
| 当前版本 → 评价与分析 | 哪些对象被谁以什么标准评价；计划与实际覆盖、未开始与未评；有范围的综合分析及未知 | 下钻原评价、准确成果与过程；判断该补证据、调优还是校准标准 |
| 当前版本 → 调优与后续版本 | 从评价发现什么，原因假设是什么，为何选择这处改动，产生了哪版候选，验证结论是什么 | 到候选版本看差异与案例，到遗传图谱追溯全局；无改法也能保存继续使用或不改的理由 |
| 版本遗传图谱 | 版本及真实分支、前驱与后继；边上是修改动机、关联问题和验证依据 | 点版本进该版；点边看完整“评价→分析→改动→验证”记录，不只看时间线 |
| 服务与复盘 | 当前采用范围、真实业务表现、窗口与评价覆盖、重复问题、人工负担 | 打开业务 Case，或形成跨案例的方法改进／项目问题；不干扰并行候选 |
| 全部业务案例／资产库 | 从一次业务要求或一份材料出发，不要求先知道生产它的版本 | 沿关系回到准确版本、运行、评价；复用时保留来源与新用途 |

版本号应有稳定、可读的业务标识；底层准确 ID、内容指纹、部署身份仍可追溯。版本号不能只用难辨认的时间戳，也不应把部署更新误当成业务方法一定改善。具体编号规则留待实现设计确定，历史身份不被重新编号覆盖。

尚无 workflow 的 Space，先从业务目标与问题保存目的、样例、标准及未知；开始设计具名方法后才出现对应工作流导航，草案与可运行版本分别表达。首项委托可以先关联准确草案并保存材料；首版具备执行条件后再明确绑定可执行版本、显式启动，不能把保存委托冒充运行。随后沿本页的案例、评价与调优路径回看。日常业务从全部业务案例进入，研发者可直接进入准确版本；再次进入恢复原位置。既有研究、分析与创作不因此形成强制的先后链。

## 4. 需要三种图，分别解释三类关系

### 方法与预期产出图：这一版打算怎样工作

完整方法图在关键 Agent 旁直接表达它会产出什么，以及下游怎样使用这些资产。例如研究产生研究报告，作者消费报告并产出稿件，冷读与核查读取稿件并产出各自意见，主编依据稿件与意见作出下一步判断。这些是业务合同的示例，具体以该版声明为准。

控制边表达执行、分支、循环与停止；资产边表达生产、消费和评价关系。两者用可辨认的标记区分，避免把“读取报告”误画成“必定在此后执行”。输出资产类型或角色应默认可见；工具调用细节与非关键产物按需展开。没跑过的版本也能看清预期产物，不能靠实际运行才能补全方法理解。

节点详情进一步表达自主决定的范围与遇到材料不足时的处理；选择 run 后再核对实际条件。准确版本不等于全部外部资源已封存，工具可用也不等于获准任意使用。设计与执行的三层对照及冲突处理见[关键决定与状态](decisions-and-states.md)。

### Case 资产关系图：具体发生了什么

进入 Case 时先显示当前版本范围内的全部运行与资产，包含输入、阶段产物、过程稿、评价意见和失败时已保存的内容；另有明确入口切到该 Case 的跨版本历史。资产同时有列表和关系图，便于确认没有遗漏，再按运行、轮次、角色或状态聚焦。

图上的节点是准确资产，边区分生产、交付、读取记录、声明依赖／引用、修订、评价及有依据的派生关系。边的详情说明它来自绑定、工具事件、合同映射还是独立核查，不能一律表达为模型已经理解并使用。生产节点可回到准确 run、Agent 和 workflow 版本；同一原料被多次交付保留同一身份。方法中的预期输出不是已存在资产，失败节点没有生成的资产应显示未产生或未知，不能造占位“成品”。

例如 Case A 在 v1 跑两次、v2 跑一次：v1 的 Case 页先列两次，v2 先列一次；跨版本视图列三次并分组。Case 数、run 数、重试数分别表达，不能以其中一次成功吞掉其他失败，也不能只列最新一稿冒充全部资产。大量资产可筛选和分层，但界面要说明当前范围与尚未展示的数量／分页。

### 版本遗传图谱：方法为什么这样演化

节点是准确 workflow 版本；边是有依据的派生或变更关系，连接原问题、证据、改动动机与验证记录。图中可辨认首版、分支、候选、弃用和采用范围；部署可用性与方法采用分别表达。缺失祖先或原因显示未知或已归档，不补造故事。

“v1 → v2”只说明继承关系仍不够。点开该边应能知道：哪个 Case 或跨案例观察提出问题、Evaluator 实际说了什么、认知 Agent 怎样分析、改了哪些节点／Prompt／tools／skill、对应验证支持到什么程度。共享存储或 SDK 的项目变更作为相关依赖和执行条件，不伪装成 workflow 版本的父节点。

## 5. Evaluator、分析与评分怎样放

先保留三个不同层次：对准确资产／运行／案例的评价；对某个 workflow 版本的综合分析；据此作出的调优和采用决定。Evaluator 意见是分析材料，分析者还需要结合用户目标、真实内容、失败与执行条件判断原因。不能从一个分数自动推出下一版，更不能默认独立评价通过就已获用户采用。

“评价与分析”应展示评价对象与材料范围、判者及方法、标准版本、原始结论、证据和分歧；版本综合结论说明纳入哪些案例与运行、排除了什么、哪些没有评价。不同输入、判者、标准或环境会限制比较，不能只并排两条分数。

该版实际运行记录与验证计划各有分母：计划中没有启动的项也应可见，不被“全部实际案例”掩盖。目标和评价标准改变时说明旧证据仍适用于哪里，缺哪些新证据。完整对账的[模拟主体与样例](decisions-and-states.md)用于检验这些差别，不预设总评分公式。

**Workflow 评分机制尚未与用户定义。** 当前可以设计评分所在的位置及其依据入口，显示“评分机制待定义”，不能自定维度、权重、平均分或通过阈值。已有四问、单次评价和运行成功率不能直接冒充版本总评分；未评不等于零分。后续需讨论评价对象、代表性案例、重复运行、失败如何纳入、判者校准与综合规则。

“调优与后续版本”承接评价与分析的结果，保存问题、竞争原因假设、选择的改动及理由、预期效果与风险、关联候选、验证和决定。这形成可追溯的解释链，也允许结论是不改、补材料、校准判者或提出 dogfood issue。

## 6. Agent 怎样参与认知

| 使用方式 | 从哪里取得信息 | 要证明什么 |
| --- | --- | --- |
| 业务执行节点 | 按任务合同得到输入，使用其 Prompt、tools、skill 和已支持执行器 | 是否在职责内完成工作并留下准确产物，不因此自动获得全 Space 权限 |
| 方法／产品认知 Agent | 使用认知与分析方法，经 skill＋CLI／tool 读取有权限的版本、案例、资产、评价与关系 | 能否形成有依据的理解和改进建议，信息与前端来自同一事实 |
| 代用户使用前端的 Agent | 真正从用户可见入口进入，选择版本，阅读方法图、Case、资产关系与评价 | 用户从这个界面能获得哪些信息、能否理解并继续任务，缺什么或在哪里受阻 |

后两项可以由同一个 Agent 在不同工作阶段承担，但证据来源要区分。前端走查先只按用户可获得的信息完成任务，留下通过界面得到的理解和无法回答的问题；再用 CLI 核对底层事实，区分数据没有保存、接口没提供、前端没展示或表达难懂。CLI 找到的信息不能回填成“前端已可理解”。

用户需要的是代理人有机会接触同样的材料、经历同样的交互并形成可核对的认知；主观判断不保证与本人完全相同。Agent 可以提出不同解释，但要指出证据与分歧。这种角色既验证前端，也应阅读业务成果，不能只做页面是否能打开的检查。

## 7. 当前实现究竟覆盖了哪些

2026-10-08 对现行 4397 工作台作只读浏览，并核对共享 UI、图生成与 CLI 源码。以下区分可复用能力与用户所需完整任务；没有发起运行、写评价或改变采用。

| 用户所需 | 当前已有证据 | 仍缺的部分 |
| --- | --- | --- |
| Space 的业务目标 | 左栏展示 Space 名称与 purpose | 完整目标、问题、约束与标准的阅读入口及其与方法设计的联系 |
| 每版版本号、设计目标与动机 | 版本选择存在；历史卡片有 revision、changeReason、前驱和计数；定义页有用途 | 主要入口仍以同名加时间辨认；目标、修复问题与来源证据没有组成版本说明 |
| 选版本查看实际 Case | “运行过程”下可读取该版本的案例，Case 下可选择运行；工作流视角按版本过滤 | 完整案例集合及状态、评价和资产概貌缺少清楚的版本主体；需逐层选多次 |
| Case 的全部资产及关系图 | 单 run 过程图、输入输出阅读；单资产详情可查生产者、依赖、前稿、评价及消费者 | Case 多次 run 的完整资产浏览和可聚焦关系图未形成；单资产邻域不等于 Case 全貌 |
| 完整方法图及预期资产 | 方法图与节点详情已有；端口和资产绑定可在详情读取 | 默认图只传入方法节点与控制边，未画出关键预期资产与数据依赖 |
| workflow 版本的评价与分析 | 四问、比较、问题、计划证据与部分 iteration 可读 | 围绕准确版本汇集全部评价、范围与原因分析的完整栏目；总评分机制待用户定义 |
| 从评价到下一版本 | predecessor、changeReason、iteration 及相关 ID 已保存 | 评价→分析→选择改动→后继版本→验证的可阅读因果链仍不完整 |
| 版本遗传图谱 | 版本历史展示前驱文字及局部变更信息 | 新共享前端尚无跨版本关系图，历史卡片不能替代它 |
| Agent 获取同一事实 | creation 的 content-space CLI 可查运行、过程、资产邻域、验证和比较 | 通用认知 skill 与所需完整版本取证路径仍需核对补齐，不能由 CLI 命令存在推定已经接通 |
| Agent 代用户认知 | 本轮实际按 UI 查看了方法与入口；此前也有局部实用验收 | 尚未按上述完整版本任务持续验证；技术或局部路径通过不足以证明认知完整 |

实现依据：[共享界面](../../vendor/agent-workflow/packages/workbench-ui/src/workbench.tsx)、[路由选择](../../vendor/agent-workflow/packages/workbench-ui/src/selection.ts)、[计划证据](../../vendor/agent-workflow/packages/workbench-ui/src/plan-action.tsx)、[方法图生成](../../vendor/agent-workflow/packages/spaces/archify-render.ts)、[Space API](../../vendor/agent-workflow/packages/space-api/server.ts)、[操作者查询](../../vendor/agent-workflow/packages/spaces/operator.ts)、[业务 CLI](../../workbenches/creation/scripts/content-space.ts)。当前状态统一同步至[建设状态](../../vendor/agent-workflow/docs/harness-roadmap.md)，本表保留这次核验时点的设计依据。

## 8. 还需补齐的判断与下一步

已有认知串起了核心对象。本轮继续推导了合同内自主的运行边界、定义／实现／执行的区分、关系边的证据强度、实际运行与验证计划的不同范围，以及采用怎样影响新委托。这些规则已接入[关键决定与状态](decisions-and-states.md)，仍是待检验的设计。

当前通过[静态线框](wireframes.md)说明**准确版本的完整认知路径**，加上计划缺项、节点材料不足、采用版不可执行三个反例，以及从零形成首版。沿用已有 Archify 画布与详情，不继续制作可操作低保真。后续建设再选择真实 CONTENT 任务，分别检验操作者理解、runtime 执行、成果用途和人工负担；评分公式保持待讨论。

以下共用交互细则继续适用，入口名称和默认范围以上述版本模型为准。

## 案例与产物的主体

### 案例列表

第一眼回答：做了哪些事、已有哪份可读成果、哪些需要处理、下一步是什么。主要操作是新建业务，其次是打开案例和筛选待处理事项。列表用业务名称、结果摘要、业务处理状态和更新时间帮助辨认，准确 ID 按需展开。

最新运行失败时，案例仍显示此前可用的成果与这次失败；不能让“最新”覆盖“可用”。排序可以优先待处理和最近活跃，但不要将最新稿默认当成被接受或应交付的稿件。

### 新建业务

按工作内容组织输入：要求与用途、目标读者或使用者、材料与约束。允许从资产库选择准确版本，也允许导入当前支持的材料。清楚表达所用方法与是否可执行；有已采用且可用的方法时减少重复选择，无采用版本时明确选择候选而不自动采用。

若适用采用版已不可执行，保留要求与材料，说明缺失条件；候选可执行也不能静默接管。没有匹配采用范围或范围冲突时需明确本次选择。当前采用记录本身不会替新任务选版本，业务入口应怎样消费它属于本轮[派发设计提案](decisions-and-states.md)，不是已实现行为。

发起前让人检查本次要求、材料和方法，显式启动后保留可返回的案例位置。配置高级参数属于可展开信息。普通委托不要求填写 A/B 假设；修改已冻结输入应形成清楚的新输入版本或运行，不覆盖过去。

### 案例详情与案例画布

默认中心是“这次输入了什么，得到了什么，现在怎样处理”。案例画布先呈现关键输入、主要成果与关系；需要理解形成过程时，再展开研究、各轮稿件和意见。技术节点的控制流可从这里进入准确运行视图，不要求业务使用者先读懂全部节点。

主成果旁直接提供对应意见、前稿、处理建议与下一步动作。阅读一份稿件后能回到同一案例和轮次；查看来源时不丢失当前阅读对象。没有主成果时，说明还在运行、等待材料还是失败，并展示已有中间成果。

### 结果处理

区分继续修订、选定成果、接受、导出和交付。每个动作要表达作用对象和后果。Agent 的处理建议保存为 Agent 意见；它不是用户接受，也不应伪装成流程内某个节点的终审。

交付后的反馈回到原成果和案例，才能用于以后改进。业务闭环应到可用成果及其处理决定，不能把“模型请求成功”或“保存了一条意见”单独作为结束。

## 资产库的主体

资产控制台的设计起点是执行和迭代需要可靠的资产事实。统一存储负责准确保存、引用和向节点提供资产；控制台让人理解与操作这些事实，Agent 则通过 CLI／tool 使用它们。因此应先确定生产、版本、输入和复用关系，再决定界面怎样呈现；只改善文件列表样式无法解决存取与交接的不稳定。

资产库服务“我想找某类材料或成果”，无需先知道它属于哪个 run。提供业务名称、类型、来源、产生阶段、相关案例及可用状态；按任务选择列表、缩略图或专用阅读器，避免所有内容都变成 JSON。

筛选围绕真实需要：版本、案例、节点阶段、时间、人工选定或评价状态。查看资产可阅读内容、比较准确版本、展开来源和使用关系，并引用到新的业务输入。名称帮助人识别，准确身份保证关系不串。

复用保留原来源和新用途，不修改旧内容。资产被淘汰可能只针对某次用途，不应仅凭一次评价就变成全局不可用。所谓“最好”也需要相同目的和可比较标准；当前没有校准证据时，不先做一个看似精确的排行榜。

### 辅助入口：设置与帮助

主体按业务信息、执行接入和操作说明组织。业务信息说明这个 Space 服务什么目的、适用范围与成功标准，修改目标要留下时间与版本，不能静默改写历史判断。执行接入说明当前可用能力和影响范围；具体某版方法的模型、Prompt 与工具配置仍在方法上下文查看，不混成一个全局开关。

帮助优先解释当前任务中的术语和继续方式，并能返回原案例、方法或资产。没有多用户权限、多个 Space 或某类接入实现时，不展示假定可用的管理按钮；也不以“设置未完善”为由阻塞已支持的正常业务。

## 详情阅读与就近判断

短配置和轻操作用侧面详情，完整文章、长报告、大图及双稿比较提供扩大阅读。先给内容与必要结论，再按需展开证据、关系和技术追溯；不要让一大段机器结论和标识占满首屏，把真正的稿件挤到下面。

正文、画面、对应意见、来源与关系按业务类型组织。比较先让人知道两边是什么、为什么比较、条件有何变化，再并看内容与各自评价。保存的摘要应能扫描到收益、代价、未知和处理决定，完整依据仍可展开。

返回应恢复原案例、版本、轮次、筛选和视图。跨入口跳转尽量携带这些范围，不用用户记编号再次搜索。正在填写的反馈不应被后台刷新覆盖。

## 贯穿任务的状态与返回

[场景、责任与对象](../product-understanding/responsibilities-and-objects.md)已经明确对象关系。这里检查同一个任务在不同状态下如何继续，避免正常路径成立，遇到空白、失败或重新进入就中断。

| 状态 | 用户应得到的反馈与可继续的工作 |
| --- | --- |
| 尚无方法或案例 | 明确产品用途和起点，不显示大量没有解释的空表 |
| 加载中 | 保留所选范围，说明正在读取哪类内容；不先将空数据误报为没有成果 |
| 正在执行 | 表达当前阶段、已完成产物、可用操作和返回位置 |
| 部分完成或失败 | 同时表达失败位置与已有成果；处理建议可以保存，恢复或重跑仅按真实能力提供 |
| 需要人处理 | 说明需要决定什么、针对哪份内容、作决定后会怎样 |
| 多个候选或历史并存 | 可读名称、用途与状态足以区分；归档历史不占据日常列表，也不悄悄破坏所需证据 |
| 离开后重开 | 从持久记录恢复业务处理状态、建议和下一步，而非从聊天摘要猜测 |
