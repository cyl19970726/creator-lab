# Workflow 调优与项目 Dogfood

[返回产品认知](../product-understanding.md) · [进入产品设计](../product-design/README.md)

真实任务既能帮助我们理解“这项业务怎样做得更好”，也能帮助我们理解“agent-workflow 项目还应具备什么能力”。这两类认知共享观察来源，却进入不同的改进流程。用户将第二类称为 **dogfood issue**；统一存储层和 Agent SDK 接入就是这类项目认知的例子。

| 区分 | Workflow 调优 | Agent Workflow 项目的 dogfood issue |
| --- | --- | --- |
| 要改变什么 | 当前业务方法及其可配置执行方案 | 产品／共享底座的能力、可靠性、接口或使用方式 |
| 常见例子 | 改 Prompt、节点职责、流程、返工规则、输入装配；组合已有工具或 skill | 缺少统一资产存取、需要新的 SDK 接入、共享执行记录不完整、控制台无法支持必要任务 |
| 由谁承接 | 当前 workflow 的维护者，在现有能力和授权内形成候选 | 所属项目的认知与维护者，汇总证据、判断范围及优先级，再安排建设 |
| 下一步是什么 | 形成准确候选，真实运行与比较，再决定采用 | 可记录为仓库 issue，经过归因、去重、方案与排期；不因发现或提交就自动开始实现 |
| 怎样证明改善 | 业务质量、可靠性、人工负担和代价的比较 | 项目变更自身检查，加回到原业务场景的复验；需要时覆盖其他受影响消费者 |

**分界在责任与影响范围，不在“今天能不能改完”。** 一处很小的共享存储缺陷仍属于项目问题；一项复杂的流程重构仍可能属于业务方法调优。选择项目已经支持的 SDK 执行器可以是 workflow 配置变化，实现一种尚未支持的 SDK 接入则是项目建设。症状不足以确定归属时，先保留原因假设与证据，不急于替问题定层级。

Dogfood issue 至少应让接手者知道：哪个真实任务遇到了什么，期望与实际有何差异，证据在哪里，影响什么工作，有无临时处理办法，以及怎样验证解决。这些信息可落在现有仓库 issue 中，无需先建立新的产品模块。提出统一存储等方案时，还应保留其所要解决的问题，避免方案名称取代问题本身。

两条路径彼此连接：workflow 调优可以发现并引用 dogfood issue；项目改进交付后，回到相关 workflow 的真实任务复验，并记录新的环境条件。若问题不阻塞当前目标，可以记录后继续已有能力范围内的工作；若确实阻塞，则说明依赖和影响，决定等待、缩小范围或采用有记录的临时方案。不能为了继续试验，用不断增加 Prompt 掩盖平台缺口；也不能每发现一个缺口就把业务调优扩大成平台重构。

## 怎样判断下一步值得做

产品要积累的是**有业务范围、有准确版本、有实际结果和改进依据的工作方法**。设计 Agent 形成方法，执行环境使它成为真实行为，评价与观察判断它是否兑现目标，再决定改变方法或继续使用。这几个转换任何一处不成立，增加版本、资产或功能数量都不能证明产品正在学会更好地完成业务。

因此下一步先寻找最妨碍判断的缺口：方法没有专业做法，就检查业务判断、信息、工具与交接如何完成；设计已经明确却无法按同一版本执行，就修部署与执行映射；有结果却不知道是否合格，就补准确标准、原文和评价校准；有失败与候选却不知道改法有效否，就做有边界的比较。已经成立的业务理解与阅读能力应复用，只复验被变化影响的部分，不把每次迭代都变成重新建设整个 Space。

Harness 应把身份、版本绑定、存储、预算计数、检索和恢复等可确定的工作承担起来，给 Agent 留出业务判断的空间。它的收益最终要回到同一任务：成果是否合格、是否减少流程外补做、能否定位失败、下一次是否少走弯路。命令数、返回字节、接口耗时和模型调用量用于解释代价；不能单独替代这些结果，也不能用未采集到的 token／费用算收益。保留未知比给一个虚假的“效率提升率”更有用。

**方法和运行环境一起变化时，必须拆开归因。** 在新环境中保留旧业务方法形成控制条件，与只改变业务方法的候选在相同输入、工具、模型和标准下比较。这个控制条件是迁移后的新版本，不能冒充旧准确版本重跑；旧历史仍保留。若做不到可比，结果可以说明新组合是否可用，但不能据此把改善全部归给 Prompt 或 harness。

观察者和 Evaluator 也属于需要验证的方法。判断须能从具体结论回到被评正文、原始依据及当时标准；用已知正确、错误与证据不足的情形检查是否误判，分歧保留到有依据的处理决定。多 Agent 一致只增加一种观察，不能抵消共同误读；一次配对只支持其样本范围，采用与持续有效还需要未参与调优的案例和真实业务使用证据。

据此，近期建设应围绕一条可追溯的真实方法演化路径推进；基础设施和展示的改动分别说明解除哪项阻碍。当前批次、执行前置和停止条件统一见 [建设路线](../../vendor/agent-workflow/docs/harness-roadmap.md#下一轮先完成什么2026-10-12)，这里不维护第二套当前状态。

## 这一区分怎样影响布局

一次评价可以暴露多个问题，它们未必有同一个原因或去向。观察者需要先固定所依据的 Case、run、评价和处置修订，再逐个分开“实际哪里不同”与“可能为什么”。原因解释应有支持证据、反证和还缺的观察；空缺可以明确保留，不能由一个分类名称或流畅叙述补成已确认根因。研究中已有的信息在作者稿中消失，支持“交接后信息损失”的观察，但还不能单独区分输入装配、职责说明、生成取舍或判者要求等解释。

诊断的结束条件是能有依据地选择下一步，不是必须生成候选。修作品、补材料、校准评价、继续观察或暂不改变都应留下理由与复验条件；修改现有方法时才描述准确前驱、具体差异、预期收益、风险及什么结果会推翻预期。共享底座缺口进入 dogfood 线索，设计方法问题保留外层 session 引用，两者不自动转成当前 workflow 的 Prompt 修改。

因此，诊断就近从运行的评价与处置进入，在原画布上下文中展开阅读和编辑，返回时仍定位同一对象。既有验证计划 issue 与 iteration 继续承载计划中的问题和实际验证关系；诊断发生在候选和验证之前，不能为了复用这些记录而制造计划项、验证运行或方法版本。记录型诊断可使用共享不可变资产修订，保存准确证据和历史；候选草案不等于已登记准确方法，更不表示可执行、验证或采用。

原 Case、运行或资产旁保留发现的问题及项目引用；候选若依赖该问题，也能看到影响。业务侧关心的是“影响当前哪一步、可以怎样继续、是否待复验”，项目侧负责自己的归因、优先级和建设状态。可以使用已有仓库 issue；无需复制一套项目管理界面。

项目交付后，原业务显示待复验依据与可采取的后续动作。复验需要匹配已交付的配置或版本，并保存结果；未通过时继续记录业务未恢复，不能把 issue 关闭自动映射成 Case 成功。非阻塞问题不干扰正常业务，临时处置也不因此成为正式稳定方法。

方法候选的具体形式及验证见[方法形成与生命周期](lifecycle-and-methods.md)，这条跨层往返的使用路径见[场景走查](../product-design/walkthroughs.md)。
