# 场景、产品责任与对象

[返回产品认知](../product-understanding.md) · [进入产品设计](../product-design/README.md)

这一层说明业务目的怎样产生方法、方法怎样经真实使用改变，以及产品为此必须保留什么。它先于前端、路由和技术模块划分；具体呈现可以变化，因果关系不能只靠界面补造。

## 从业务目标到下一版方法

Space 承载长期业务目标。目标、样例、约束与未知支撑首版 workflow；首版声明要怎样完成业务、各关键 Agent 或步骤预计交出什么资产，再以具体 Case 真实执行。每次 run 留下实际路径、资产、失败与介入，评价者据用途阅读这些结果。分析这些证据后，可以修本次作品、调整输入或评价、保持现版、提出下一版方法，或把底座问题送入项目层。新版本的产生和某个范围内的采用是两项独立决定。

因此，**准确 workflow 版本是一份完整的、可被研究的方法**，不只是方法名下的一个筛选值。理解某版，至少要能找回它的版本号、设计目标、要解决前版什么问题及其证据、完整方法与预期产物、该版实际跑过的全部 Case 和每个 Case 的全部 run、各次实际资产与关系、评价与局限，以及这些分析怎样引出后继版本。首版没有前驱时，应说明其目标与设计假设；没有运行时也可研究预期方法，但不能虚构实际效果。版本越多，越需要保留前驱、分支、改动、验证与采用范围，而不是只按时间排一列版本号。

同一个 Case 是一项持续可辨的业务要求，可以在多个 workflow 版本上处理，每版也可以多次运行。Case 的业务身份与每次 run 的准确输入快照、方法版本、执行条件和输出必须分开。这样既能在一版内部读全它对某 Case 的所有尝试，也能沿同一 Case 比较不同版本；Case 的最新结果不覆盖旧运行，某版预期输出的资产类型也不冒充实际生成的资产。

## 谁在什么情境下使用

同一人可以承担不同责任，Agent 也可以在授权内承担其中一部分。以当前要完成的任务区分，不能先按岗位建几个互不相通的后台。

| 情境与责任 | 需要作的关键判断 | 结束时留下什么 |
| --- | --- | --- |
| 新业务提出者与方法设计者 | 目标、样例与约束是否足够；首版怎样划分职责、预期资产和评价；哪些仍未知 | 有理由的首版方法与首个 Case，或需要补齐的具体信息 |
| 日常业务操作者 | 本次输入是否齐全，采用哪一准确版本，现有成果怎样处理 | 可用成果、明确的处理决定与反馈，归于准确 Case 和 run |
| 方法维护者与认知 Agent | 一版的完整证据显示差异来自哪里；修作品、改方法还是提出项目问题；什么试验能区分原因 | 问题依据、候选版本或不改的决定、验证条件与前驱关系 |
| 独立评价者与采用决定者 | 成果对用途是否有效；改法是否改善且没有不可接受的退化；适用什么范围 | 针对准确对象的评价与分歧、验证结果、按授权作出的采用或停止决定 |
| 持续服务负责人 | 当前采用版在实际范围内是否仍可靠；反复问题是否值得调优 | 明确观察范围、复盘与后续安排，正常生产可继续 |
| 资产使用者与接手者 | 内容能否用于这次目的；来源、版本与使用条件是否可信；工作怎样继续 | 准确引用与新用途、可恢复的工作上下文 |
| 共享项目维护者 | Dogfood 证据是否成立，影响哪些消费者，何时建设与怎样复验 | 项目取舍及交付，关联原业务验证结果 |

角色、场景与生命周期交叉存在：采用版可持续产出，维护者同时做候选试验；一次成果失败也可能只需修订这次作品。独立评价者可以提出意见，却不会因此获得方法采用权。

## 产品需要持续保留什么

| 认知依据 | 产品责任与机制 | 后续用途 |
| --- | --- | --- |
| 方法从业务目的与假设产生 | 关联目标、标准、设计理由、完整步骤与预期资产；首版也记录未解决假设 | 没有 run 时理解方法；后续区分目标改变与方法失效 |
| 每版方法需要整体检验 | 保留准确版本、前驱与变更依据，聚合该版的全部 Case、run、资产、评价和分析 | 复原版本效果及局限，说明后继版本从何而来 |
| Agent 在明确边界内自主工作 | 让节点职责、Prompt、输入、上下文、可选 skill、工具、执行器和结束条件可定义、装配并记录 | 判断方法声明与实际执行是否一致，知道该改哪个层次 |
| 真实业务应由方法实际完成 | 准确版本、部署条件、Case 与输入形成 run；记录节点实例、真实路径、资产和介入 | 成果有归属，失败可见，历史可读不被误认成历史可重跑 |
| 评价需要真实内容和明确条件 | 阶段与最终资产可阅读、评价和比较，保留判者、标准、可见材料与分歧 | 技术成功、业务质量、用户接受分别判断；版本总评分机制仍待讨论 |
| 改进需要检验因果 | 问题与假设连接改动、候选版本、基线、案例集合和比较，记录方法及相关环境的有效配置 | 可解释为什么改、改得怎样；条件变化可见，不默认候选必须是 skill |
| 稳定服务与研发并行 | 正在查看、已发布、可执行、候选和当前采用分别表达；采用有范围和明确决定 | 试验不会静默改生产，必要时限制范围或回退 |
| 经验要影响后续工作才有价值 | 资产可跨案例引用，经过判断的知识进入 skill／配置，保留来源和使用关系 | 避免重复搬运；修改经验后知道需复验哪些消费者 |
| 稳定使用产生新证据 | 按范围记录业务、失败、人工负担、评价覆盖和反馈，形成复盘决定 | 决定继续使用或再调优，不用零散成功记录宣称成熟 |
| 人与 Agent 都需继续工作 | 工作台与 skill + CLI／tool 读取同一批持久事实并执行有权限的动作，保存判断和接手位置 | 认知不依赖单个聊天，Agent 和界面不各自维护一套状态 |
| 真实任务也会暴露产品缺口 | 将 dogfood issue 关联发现它的任务、证据、影响和依赖，交由所属项目判断优先级 | 记录、排期、交付与原业务复验分别表达，不把发现缺口等同立即开工 |

## 共同对象与三种不同的图

Space 维持业务目的；workflow 保持方法身份，其准确版本承载完整定义与演化依据。skill 是某版方法可能使用的依赖。Case 是业务要求；run 是该 Case 使用某一准确版本和输入、配置的执行尝试。节点实例产生可追溯的实际资产。评价针对明确的 run、资产或版本及用途；比较连接明确条件下的结果；iteration 连接问题、改动和验证；采用决定哪些版本在什么范围服务。

这些关系对应三种要能互相追溯、却不能合并的图：

| 图 | 回答什么 | 必须保留的区分 |
| --- | --- | --- |
| 方法与预期产出图 | 这一准确版本计划怎样做；关键 Agent／步骤读什么、判断什么、预计交出什么资产 | 设计的流程、条件和资产类型不是已经发生的路径或资产实例 |
| Case 的实际资产关系图 | 这一 Case 在所选版本的每次 run 中实际发生了什么；资产由谁生产、交付给谁，存在哪些读取、依赖、修订或评价证据 | 多次 run 不能合成一次；输入绑定不等于实际引用或理解；时间先后不能自动画成因果；可跨版本追到同一 Case |
| workflow 版本遗传图谱 | 版本从哪版、哪项问题与证据产生，改了什么，如何验证，后来是否在哪个范围被采用 | 版本产生、评价意见和采用决定是不同事实；分支与回退也不能被最新版本号抹平 |

Dogfood issue 是跨到项目层的问题记录，可关联原 Case、run、资产或使用任务，再关联后续项目变更与复验。它不必成为 Space 内的一种新数据库对象；现有仓库 issue 加准确证据引用就可以承载。它的关闭也不能代替某个 workflow 候选的采用决定。

因此不能按存储表逐项造菜单，也不能只保存最后一份稿件。来源、前驱、生产、消费、评价、修订和采用是不同关系：最新稿不等于已接受稿；候选评价较好，也不自动成为生产方法。正式对象合同见[产品定义](../../vendor/agent-workflow/docs/product.md)，执行与资产关系见[流程与资产](../../vendor/agent-workflow/docs/workflow-process-assets.md)。

关系还需要交代成立依据与作用范围：实际跑过的 Case 不能代替计划中应验证的集合；资产边要区分交付、读取事件、声明和核查；采用记录要说明未来业务怎样选择准确版本。具体规则及当前证据边界见[判断、执行与证据](decisions-and-evidence.md)，不能从对象存在直接推定这些规则已经实现。

## 人与 Agent 如何形成同一范围的认知

负责业务或方法的 Agent 应借助适合其任务的 skill 与 CLI／tool 查询准确版本、Case、run、资产和评价，并在权限内记录诊断、试验与决定。工具提供可追溯事实与动作，不会替 Agent 判断业务质量；保存全部历史也不意味着把全部历史装入一次上下文。

还需要一个 Agent 代用户**实际使用前端**完成同一类阅读、比较和继续工作的任务，取得与用户相同范围的材料，再报告哪些信息找不到、关系看不懂或动作做不下去。它的主观结论不保证与用户一致，正因此要留下所见材料、路径与分歧。CLI 查询数据库能核对事实，却不能代替前端走通；前端好看也不能证明底层事实完整。这项职责用于产品认知和验证，不预设为一个新的前端功能。

## 从机制转到使用结构

人进入产品时并不总处于同一阶段。日常完成业务时，中心是 Case、输入与成果；开发和维护方法时，中心是准确 workflow 版本的完整定义、试跑证据与演化；跨案例找资料时，中心是资产及其用途。这些工作方向共用事实，并能从版本到 Case、从 Case 到 run、从实际资产回到产生它的版本与后继判断。

由此可以推导工作台的观察范围和信息层级：Space 保持业务目标，workflow 容纳方法演化；查看某一版本时应能读全该版，跨版本时应能看见遗传关系和同一 Case 的比较。具体导航、画布和展开方式交给[布局设计](../product-design/layout.md)决定。项目层 dogfood issue 可从发现它的业务证据处关联出去，不必为此复制整个 issue 管理系统。

2026-10-09 的[交互走查](../product-design/prototype-round.md)进一步发现：静态页面能读清对象，仍可能在下一步动作中丢失身份。原型从新业务草案创建委托时曾默认回到旧 CONTENT v1，造成业务目标与方法脱节。因此发起下一步必须携带准确对象与目的，保存后还能核对；后续编辑草案不改变已关联委托的原方法。这是对象关系对交互的约束，不能仅靠详情里显示版本号满足。
