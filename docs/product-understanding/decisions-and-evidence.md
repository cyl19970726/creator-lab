# 判断、执行与证据：还需要补齐的产品规则

[返回产品认知](../product-understanding.md) · [对象关系](responsibilities-and-objects.md) · [对应设计](../product-design/decisions-and-states.md)

**已有认知解释了对象怎样相连，还需要解释：什么条件下可以作出什么判断，这项决定究竟会改变什么。** 如果只把版本、案例、评价、采用连接起来，人仍可能把“记录完整”当成“方法有效”，把“评价较好”当成“可以接管业务”。

2026-10-08 的这轮推导没有推翻业务目标、完整版本对象或双重改进路径。正式文档已有合同内自主、验证分母、采用范围等原则；缺口主要是这些原则尚未落实为冲突情况下的处理规则和连续操作。下文的具体规则属于设计建议；源码核对只说明当前记录能支持哪些断言，不代表已经完成运行验证或新增能力。

## 1. 方法提供边界，也必须容纳执行中才发现的问题

Agent 的价值包含发现原计划没想到的材料、解释和改法。如果把所有选择预先画成节点，就会失去这种价值；如果只给一个宽泛目标，又会重现长会话中依靠临时救场的方式。因此需要让人看懂：**哪些判断交给节点，哪些改变了原委托，哪些应回到方法或项目层。**

| 执行中的发现 | 建议的归属与处理 | 后续怎样理解这次结果 |
| --- | --- | --- |
| 在允许的材料、工具与资源范围内探索，选择另一种表达或推理路线 | 留在同一节点职责内；记录影响结果的选择和新增材料来源，不把每个思考步骤都变成节点 | 原方法允许的探索，能追到实际交付材料与产物 |
| 缺少完成业务必需的输入，且合同不允许自行取得 | 返回具体缺口，按该流程支持的等待、补充或终止路径处理；需要人决定时说明决定对象 | 缺材料不是质量零分；补充后保留原输入与追加记录，不能改写历史 |
| 想换业务目标、超出工具／资源范围，或需要未获授权的外部动作 | 在越界动作前交给有权者决定；已有授权仍在范围内有效，不反复请求 | 记录选择、决定者及条件；已封存 run 的输入或方法不应被悄悄替换 |
| 发现通用方法缺陷，或执行器／共享资产能力不足 | 本次处置与后续改进分开；前者关联本次 run，后者进入方法候选或 dogfood issue | 人工救场的成功不能直接算作原方法独立完成 |

当前 [CONTENT 工作台入口](../../workbenches/creation/src/spaces/content-runner.ts)拒绝联网研究请求，所以“发现材料不足”不授予搜索权。未来允许检索的节点可以在合同内取得新来源，但这些来源仍要进入实际证据。是否能暂停后续跑、是否需要新 run，取决于执行器已支持的语义；设计不能假装两种运行方式天然具有相同的恢复能力。

这要求方法图的节点详情表达允许自主决定的事项、工具与材料范围、资源约束、交付和升级条件；运行详情表达实际选择、影响结果的介入及未解决缺口。不是保存不可观察的内部思维，而是保存业务判断所需的可观察行为与决定。

## 2. 一版方法、可执行的实现和本次执行，是三个观察层次

准确版本回答“原本设计成什么”；执行绑定回答“当前有什么实现能够执行它”；本次 run／节点记录回答“这次报告了哪些输入、配置和行为”。它们应该相互核对，但不是天然相同。

本轮源码核对发现：版本定义会做内容指纹和同 ID 防修改检查；执行器注册绑定准确版本与入口，但实际资源核验可选；run 保存有效配置，节点保存交付输入、指令及部分配置记录。不能据此宣称所有外部 skill、工具实现、依赖和部署资源均已封存，或仅凭历史版本即可原样重跑。

因此“候选更好”至少要交代变化发生在哪一层。只换了部署或输入，不应被解释成 Prompt 改动已奏效；流程不变但执行条件改变，也可能需要重新验证。缺少条件记录时结论应收窄为“在已知条件下观察到”，不是补出一份不存在的完整还原。

对应设计采用同一节点的“设计声明／执行绑定／本次记录”对照，明确差异和未知。它不要求另造三个一级菜单，也不要求把全部技术参数默认呈现给业务委托者。

## 3. 资产关系必须说明关系是怎样知道的

统一存储解决身份和交接问题，仍需避免把“有一条边”误读为“模型确实理解并使用了这份资料”。本轮核对中，`consumed-by` 来自节点输入绑定；输出依赖可来自声明的输入槽位，部分关系可由合同映射生成。这些有价值，但其证据强度不同。

| 可以保留的事实 | 支持什么判断 | 尚不能证明什么 |
| --- | --- | --- |
| 方法声明预期读取某类资产 | 设计意图 | 这次已取得资产 |
| 某准确资产或投影被交付给节点 | 输入交接及交付范围；可核对原文、摘要或投影 | 模型已读全文、理解或据此作答 |
| 有工具读取事件 | 这次通过该工具返回了哪些材料 | 所有读入途径都被该事件覆盖，或模型理解了材料 |
| 输出声明依赖／引用某资产，或关系由合同映射产生 | 可追溯的声明或映射依据 | 引用准确、结论受到来源支持 |
| 评价者核对具体输出片段与来源 | 在该核对范围内支持引用或使用判断 | 整个结果全部正确 |

材料也可能直接装入模型输入，因此“没有读取工具事件”不能反过来断言它没收到材料。图要显示关系类别、产生依据和证据入口；没有核对时保留未知，而不全部命名为“已使用”。这是方法图、实际资产图以及认知 Agent 查询结果共同承担的语义。

## 4. “这一版怎么样”必须先明确想对什么范围下结论

同一版至少有三种集合：**系统已记录的实际运行、某个计划要求的验证、采用后某个业务窗口的表现。** 三者可以关联，但不能互作分母。

“完整历史”应明确准确版本与入口、截至时间、可见权限与筛选范围，区分唯一 Case 数和 run 次数。分页或只看成功样例时不能宣称已经读全。系统外未登记的委托仍是未知；数据库没记录不等于现实中没有发生。

验证计划还包含没有启动的项。未开始、执行失败、完成但未评、已评但不满足标准，是不同问题；“所有实际结果都不错”不能抹掉计划中尚未做的工作。现有共享文档已规定计划与覆盖分母，底座也保存计划项和尝试状态，缺的是把它接到版本阅读与采用判断中。

版本效果还受业务目标、输入群体、评价标准及运行条件约束。若用户改变用途或判者改了标准，历史评价仍成立于原范围，不自动代表新要求下的效果；需要明确哪些证据仍适用、哪些应重新检查。总评分机制尚未定义，这些范围和状态可以先表达，但不据此创造总分或采用阈值。

## 5. 采用是一项对未来工作的决定，需要明确作用范围和执行后果

选择查看 v2、试跑 v2、认为 v2 较好、采用 v2，是不同动作。采用还必须回答“供哪些业务、从何时开始、替代什么、由谁决定”。如果两个采用范围冲突、没有匹配规则，或所采用版本已不可执行，派发不能靠“最新可执行版本”猜测。

当前实现的采用记录是 Space 内具名 slot 的当前指针与历史，run 启动仍需明确提供版本。**记录采用本身并不会自动给新任务选择版本。** 结构化适用规则以及业务入口怎样消费采用决定，仍需设计；不能把自由命名的 slot 当作已经具备了完整业务路由策略。

建议先用最小明确规则：新业务说明适用的采用决定及最终版本；发起前核对该版本可执行。不能匹配或不可执行时保留委托与材料，指出缺哪项决定，可等待恢复或由有权者显式选择替代。候选可试跑，但不能因为它能跑就静默替代稳定版。已经开始的 run 保持原绑定；任何改派、补跑或回退都是可追溯的另一次决定，不重写旧结果。

## 6. 记录和认知最终要减少业务负担，并支持停止无效改进

完整追溯是形成可信判断的条件，不是业务价值本身。即使以上规则全部成立，也还不能断言成果可用、人工纠偏变少、维护更省，或第二业务能够复用底座。这些目标已在[目标与核心范式](goals-and-paradigm.md)中提出，需要真实任务检验。

两条循环需要不同的完成条件：当次业务以可用成果及明确处理决定结束；方法改进以有范围的判断与下一步决定结束。下一步可以是采用候选、继续旧版、补充证据、校准评价、处理项目依赖，或停止投入。不能让业务使用者为了提交一次任务承担一套实验管理，也不能因为评价提出问题就无限生成后继版本。

当前最值得验证的价值假设是：**一个受托操作者能否在明确边界内完成业务及必要判断，使用户少做重复解释和纠偏。** 应将成果用途、实际人工介入、等待和成本一起观察；阈值和哪些决定可委托尚需结合业务确定。界面可理解、runtime 真执行、业务有价值分别验收，不能相互替代。
