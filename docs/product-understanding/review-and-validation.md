# 认知审阅与验证

[返回产品认知](../product-understanding.md) · [进入产品设计](../product-design/README.md)

**多个 Agent 可以帮助发现盲点；认知是否可靠，最终取决于依据和现实检验。** 无法一次证明产品理解永远正确、毫无遗漏。可以做到的是：明确当前判断所依赖的事实、主动找反例、尽早检验会影响设计的假设，并在新证据出现时修正。

## 首先分清正在判断什么

| 判断类型 | 有效依据 | 不能替代它的东西 |
| --- | --- | --- |
| 目标与偏好是否理解正确 | 用户明确表达、真实任务中的取舍及后续澄清 | Agent 多数票、行业惯例 |
| 当前产品实际能做什么 | 当前实现、准确配置、可追溯的实际操作与产物 | 目标文档、设计稿、历史局部通过 |
| 原因解释是否可信 | 能区分竞争解释的案例、过程与结果；必要时对照试验 | 一个流畅故事，执行者或评价者的单次自述 |
| 产品设计是否支持任务 | 从真实起点走到可用结果，检查中断、返回和交接；随后实际使用 | 导航齐全、线框漂亮、路由可访问 |
| 是否值得持续使用 | 代表性业务的效果、可靠性、人工负担、时间费用和持续反馈 | 单次成功、更多版本、更多日志 |

目标解释还需区分“用户明确说过”和“根据行为推断”。推断可以指导可逆设计，但有冲突时应修正或带着具体问题核对，不能当作用户已经同意。

## 怎样使用多个 Agent

本产品的整体认知牵涉业务、方法研发、共享底座与交互，值得分工审阅。通常由一个负责人整合，两位核对者分别承担不同责任即可；按风险和未知调整，不把人数设为每轮必过的仪式。

| 责任 | 看什么、交出什么 | 怎样减少共同盲点 |
| --- | --- | --- |
| 事实与边界核对 | 对照原始请求、现行合同、实际产物；指出误读、无依据结论和把目标当现状的位置 | 先读最小原始材料并形成判断，再对照作者总结；技术名词不能替代用户目标 |
| 场景与反例审阅 | 选择最可能使方案失效的完整任务，指出走不下去、归属不清、重复入口与遗漏决定 | 不要求“确认方案正确”；给具体起点和成功条件，允许提出另一种结构 |
| 负责人整合 | 判断争议影响哪些认知及下游设计，修订或保留假设，指定能解决争议的最小观察 | 按证据作决定，不按赞成票；保留未解决分歧与理由 |

不同模型可能提供不同视角，但换模型、换会话本身不等于独立证据。所有人只看同一份摘要，或都被告知作者的预期答案，仍可能重复同一个错误。特别重要的原因判断，先让核对者从原始材料独立推导，再比较差异。

每项审阅意见至少交代：**争议结论、依据或反例、对哪项用户任务有影响、怎样区分解释**。无依据的“感觉不完整”可以成为待查线索，不能直接变成新功能需求；有依据的反例不能被“另外两位都觉得没问题”压过去。

## 完善到什么程度，才可以继续设计

不以新增章节数量衡量完整度。围绕本轮要作的决定，检查两条方向：每个关键场景是否有足够机制支持；每个主要机制和入口是否有真实任务依据。再检查它们相接的位置：谁负责、输入是否足够、作什么判断、留下什么、后续如何使用。

对 Agent Workflow，当前至少用以下几类任务找遗漏：零历史业务形成首版；按准确版本读完整方法与全部实际证据；日常业务完成与成果处理；同一 Case 跨版本调优与比较；稳定服务与候选研发并行；运行失败与项目依赖；跨案例复用；离开后返回或换人接手。这是当前产品的风险覆盖，不是通用于所有产品的固定功能清单。详细路径见[场景走查](../product-design/walkthroughs.md)。

尤其要从一个反例反向审阅对象和界面：**Case A 在 v1 有两次 run，在 v2 有一次 run。** 从 v1 进入时，能否看到该版目标、与前版关系（若有）、完整方法与关键 Agent 的预期资产，以及 Case A 的两次尝试各自的输入、实际路径、全部资产、失败和评价？进入 v2 时，能否读出它针对 v1 哪项问题提出什么改动，看到 Case A 在 v2 的一次实际尝试，并沿同一 Case 对照三次 run 的条件与结果？若只剩每版一个最新成果、把两次 v1 run 合并、把预期资产画成已生产资产，或只给 v2 一个较高评价而看不到有权限者是否采用、在哪个范围采用，整条方法演化链就没有成立。此例检查关系与可读性，不预设评分办法或规定 v2 必须更好。

随后还要检验会改变下一步决定的情况：计划要求的尝试尚未开始、节点所需材料不足、采用版不可执行但候选可执行。完整版本的阅读样例不能代替这些任务；具体样例见[场景走查](../product-design/walkthroughs.md)，相应规则见[判断、执行与证据](decisions-and-evidence.md)。

对会决定后续结构的结论，保留简短记录：结论与适用范围、依据、可信状态、反例或未知、下一项检验、受影响设计。状态可以是“用户已确认”“观察支持”“待验证假设”“已被推翻”。不必为所有句子打分或另建数据库。

进入低保真设计前，需要目标没有明显冲突，关键对象和任务连接说得通，尚未验证的部分已明确。若两个解释会导向不同布局，就用一个小样例或并排草图区分；非阻塞未知可以保留。进入功能实现前，再根据任务走查和实际能力确定一段完整范围。不能为了追求认知绝对完备而停止一切验证，也不能用“边做边看”掩盖已经发现的结构矛盾。

## 审阅、走查与实用形成闭环

先用现有材料建立判断，交给核对者找事实冲突与反例；负责人处理后形成具体设计。接着用同一个真实任务走查布局，观察是否有足够信息完成决定。已有实现时实际操作并阅读成果；尚无实现时用明确标为模拟的原型，不声称业务闭环已通过。最后把结果回写到原认知与设计页，而不是再加一份互相冲突的总结。

一次失败也不直接证明认知全错。先区分目标、材料、方法、执行、评价和交互原因。一次成功同样只支持其覆盖范围；还需观察迁移、重复任务、维护代价与用户实际采用。若新发现属于项目能力缺口，进入 [dogfood 路径](learning-and-dogfood.md)，不把所有问题都变成当前 Prompt 修改。

## 本次实际审阅发现了什么

2026-10-08，以现行文档为材料进行了事实核对与独立场景审阅。本次没有运行新业务，也没有对新产品布局进行用户操作测试。

| 审阅发现 | 影响 | 本轮处理 | 还缺什么证据 |
| --- | --- | --- | --- |
| 旧稿描述了首版的内容，没有走完模糊要求如何变成可检查方法并试跑 | 真实设计仍可能依赖工作台外的长聊天与人工拼接 | [布局](../product-design/layout.md)补齐目标、样例、假设、方法、首个 Case 与回看的连接 | 操作者在低保真原型中能否完成零历史任务 |
| “案例与产物、运行与案例、稳定服务”重复容纳 Case，六个阶段被近似照搬成菜单 | 日常处理、研发试验和跨案例观察容易混淆 | 按任务重组，Case 共享同一身份；运行诊断就近展开，服务页负责跨案例判断 | 在稳定生产与候选试验并行时能否辨认范围、正确返回 |
| Dogfood 分流讲清了，但修复后返回原任务的状态与动作没有落地 | Issue 关闭可能被误认为业务已恢复 | 原任务保留依赖、临时处置、项目交付与待复验信息 | 修复后复验失败时能否继续保留问题、避免误报完成 |
| 上一稿已有版本、历史和资产关系，但没有持续把完整版本认知当成这轮设计的验收任务 | 字段存在仍不足以证明用户能连续认识某版及其后继，不能简单归因为完全没有版本设计 | 把完整版本对象及三种图落实为连续阅读和决定任务，保留对旧稿已有内容的准确描述 | 用 Case A 的 v1 两次 run／v2 一次 run 反例走查；再由 Agent 实际使用前端核对材料范围 |

这些结果说明审阅找到了结构性问题，不能说明修订后的布局已经正确。下一轮应让一个 Agent 代用户实际使用前端完成版本阅读、跨版本比较和继续工作的任务，记录其所见材料、路径、判断与分歧。它还应通过 skill + CLI 核对同一事实；CLI 查询不能冒充前端任务走通，Agent 的主观结论也不保证等同用户结论。这里检验的是产品认知与可用性，不是提出一个前端 Agent 功能。

同日继续推导时，两位核对者分别审阅[判断与证据](decisions-and-evidence.md)的源码依据、[决定与状态](../product-design/decisions-and-states.md)对业务目标的支撑。审阅促使我们把未开始计划项明确写成“实际 run 0”，并分开低保真识别能力与实际节点行为的验证。版本定义、输入绑定、计划覆盖和采用记录的解释经只读源码核对；本轮没有运行新业务，也没有证明这些提案已实现。后续验收增加材料不足、计划缺项和采用版不可执行三个反例，同时仍需检验真实成果与人工负担。

## 对此前失败，证据允许我们说到哪里

后续会话核对修正了早先过强的解释：完整版本、案例、资产、评价与后继关系在较早记录中已经被说出，旧布局也并非完全没有版本和关系。因此较有支持的判断是：**已知目标没有持续变成具体设计的验收任务**，而非用户没有提供目标，或作者始终不懂这些对象。

前端框架牵引、审阅者共享同一范围、上下文遗失和能力不足都可以是竞争解释，但目前证据不足以把其中一项写成已经证明的唯一原因。也不能从审阅没有发现问题倒推出每位 Agent 的实际推理过程。进一步区分需要冻结材料、独立任务和能区分解释的观察。

认知 skill 因此改为从价值、机制、持久对象、关键判断、证据、动作和反馈建立因果模型，并要求布局前选定验收任务。但目前有限的同题与迁移检查没有证明修改后的 skill 稳定优于旧版。格式验证只证明文件可用；多人同意也不建立因果。下一步应记录它能否在真实任务中主动推导有效关系、作出有依据的取舍，并减少用户补充和纠偏，而不把这次修订当作能力已达标。
