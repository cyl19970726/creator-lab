# 产品认知与整体设计

认知负责人要能解释产品怎样产生价值、主动发现尚未被逐条提出的必要关系，并让这些认识持续影响设计与取舍。可交付的理解应当支持预测和判断：条件变化后，哪些结论需要改变，为什么；不能以文章完整、功能齐全或审阅一致证明已经理解。

## 建立能够推导的模型

先确定本轮需要作的判断，沿用用户确认的目标和边界。读现行产品定义及有关原始请求、业务样本或实际成果；把既有界面、工程拆分和自己上轮的方案作为待检验方案，不能让它们自动决定产品主线。

整体认知或设计先读 [业务因果与判断模型](references/mental-model.md)。建立一份相互连接的解释，而非分别填写目标、角色、场景和对象栏目：

**业务结果为什么值得获得 → 通过什么机制产生 → 什么对象承载工作与积累 → 谁在什么条件下作什么判断 → 判断依赖哪些准确事实 → 行动改变什么 → 新证据如何修正方法或目标。**

模型至少能完成下面三种推导；其结果可用短文、关系草图或现有文档表达，不强制新建表格：

- **从结果向前追。** 要达到目标，哪些机制与交接必须成立？每次转换由谁决定、依据什么、留下什么，下次工作怎样使用？区分期望发生、实际发生与事后解释。
- **从判断向后追。** 先独立找出使用者必须作的关键判断，再逆推证据的对象、范围、来源和条件。覆盖完成眼前工作，也覆盖理解、比较、诊断、接手、改变或继续不改；按业务重要性选择，不能只从现有按钮推任务。
- **从对象和变化检验。** 对关键的长期工作对象，检查它能否被完整认识，以及一个对象与多次使用、多个版本或并存结果怎样关联。改变一个条件后，哪些依据仍成立、哪些失效、哪些历史必须保留？用这些关系发现遗漏，不把每个对象都建成页面。

每项重要推论说明一个可核查理由：**缺少这项关系，会使哪个已确认的目标或必要判断无法成立，或使什么事实发生误归属？** 若没有这种后果，就可能只是有用提案，不能包装为必需功能。必要信息关系不直接规定数据库、侧栏或自动化方案；价值取舍和缺失事实仍应标为待确认。

整体产品请求先形成可独立阅读的认知章节，说明上述模型、主要张力及证据；写作方式见 [认知章节](references/product-cognition-chapter.md)。已有产品只更新被新证据影响的部分。更深的认知可以超出本轮建设范围，但要区分已支持、需要验证和暂缓建设。

## 让模型约束当前设计

在画布局前，从模型中选出当前必须支持的关键任务，说明结束时使用者能作什么有依据的判断、需要保留哪个对象范围。随后才读 [从外壳到交互](references/product-design-derivation.md)，逐层推导形态、导航、主体和操作。

每个重要入口需要有任务依据；每项关键任务需要有连续的信息和行为路径。选择本轮建设范围时，其他已确认的重要任务应保留其支持位置或暂缓理由，不能因不在本轮菜单中就从产品理解中消失。换一种组织方案也必须接受同一组任务检验。

场景从关系与决定中产生，不能只挑作者方案已经方便完成的路径。读 [任务选择与检验](references/scenario-reasoning.md) 找出会区分方案的任务。理解一个完整对象本身可以是任务，不必先要求用户启动、编辑或调优它；是否需要独立入口，由频率、阅读范围和切换成本判断。

## 依据结果修正认识

已有实现应亲自完成相关用户任务、阅读实际成果；没有实现则用可审阅的方案推演，说明验证边界。记录用户从这些材料能知道什么、仍不知道什么、能作何判断；页面存在、底层可查、运行成功分别不能代替这一结果。

发现问题，先区分新事实或目标变化、已知关系未用于决策、模型假设错误与执行/呈现故障。修正被影响的解释和取舍；不能每次将用户纠正都视为新需求并追加章节。对重要原因保留有依据的竞争解释，找能区分它们的观察；评价者的结论同样需要检查。

重要整体判断可让一位独立核对者先看原始目标和证据，自己提出关键判断与关系，再对照方案；不要先把作者的目录和答案给他作为审阅边界。审阅发现什么、实际任务完成怎样、长期效果如何分别说明；普通局部修改不强制多 Agent。

当任务包括改进本 skill 或验证独立推导能力时，区分两类验证：已暴露的失败用于回归，未透露答案的不同情景用于检查迁移。先冻结独立回答，再揭示核对点，同时记录有据遗漏和无据扩张。被提示后补齐只证明能处理明确要求；单次试答改善不证明已稳定具备这种能力。测试本身不应变成每次产品工作的固定仪式。

## 决定优先级并保持认识

比较真正竞争的方向：各自影响什么业务结果和关键判断、是否解除依赖、证据有多强、代价与未知是什么。局部成功不自动决定下一阶段；允许保持现状、修内容、补证据或撤销假设。完整理解不要求一次实现全部场景。

基础能力或展示也可以作为有边界的独立交付，说明它解除什么依赖、后续任务还缺什么；不强制每一阶段完成全部端到端业务，也不把基础交付当成最终使用成功。

交给执行者的是具体任务、设计理由、已有能力、边界与可观察结束条件。交付后核对相同任务，并说明哪些判断被支持、被推翻或仍未知。技术通过、任务可用、业务价值与用户接受分别成立。

优先在现有产品文档里保留当前模型、关键判断、证据范围、重要取舍和未知。跨回合接续时恢复这些约束，而不只恢复待办；重排主线时同步修改依赖它的设计和验证。只保存会影响后续决定的信息，避免为认知再建一套平级真相或逐回合长报告。

本 skill 不额外授权外发、付费模型调用、删除或部署。新发现属于认知范围，不等于已获实施授权。

## 在 Creator Lab 中使用

项目任务按需读 [项目入口与已确认关系](references/creator-lab.md)，核实共享底座与业务扩展的职责、workflow 调优和 dogfood issue 的区别，以及人和 Agent 获取证据的方式。这里保存的是本项目已确认约束；不能把 CONTENT、版本树、固定评分或某种界面形态推广为所有产品的标准答案。
