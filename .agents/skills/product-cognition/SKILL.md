# 产品认知与整体设计

对产品负责的 Agent 要维护一份能解释设计与取舍的产品理解：它为谁解决什么问题，人怎样在不同情境中完成工作，各部分为何这样关联，实际效果又如何改变原先判断。将这种理解用于决策；格式完整、功能增多、检查通过本身都不能证明认知成立。

## 先确定当前需要作的判断

沿用用户已确认的目的、边界和术语，读现行产品定义与必要业务材料。先说明本轮要决定什么、处于哪个阶段。既有工程拆分或最近一个报错不自动决定产品主线。

新产品可从业务样本、现有替代做法和场景推演开始；已有产品应亲自完成有关用户任务并读实际成果。增量问题只更新受影响的关系和结论，不强制每轮重写全部产品定义或重跑全部场景。资料不足时标出会改变决策的未知，继续可逆工作；只有确实影响正确性或授权的缺口才需要询问。

## 建立连贯的产品模型

整体产品请求先形成可独立阅读的“产品认知”章节，再进入“产品设计”。认知要解释更深的目标、产品相信怎样的工作范式、用户从现有做法转向什么工作方式、价值如何产生与积累、宏观目标如何落到具体任务，以及什么结果会推翻判断。不能用一句定位、功能清单或待办表代替这一章。读 [设计之前的产品认知](references/product-cognition-chapter.md)；按问题组织连贯论证，不照抄固定问卷。

按需要往返推理下面几层。重点是解释相互关系，不是逐项填表。

| 层次 | 需要形成的理解 | 对下一层的影响 |
| --- | --- | --- |
| 目的与价值 | 用户要获得什么结果，目前怎样做，困难与代价是什么；产品替其承担哪些工作和判断 | 决定服务对象、边界与成功标准，避免从已有功能反推需求 |
| 核心范式与机制 | 产品相信什么方式能够产生结果；关键能力怎样形成、工作、接受反馈和演化；哪些由人、Agent 或程序承担 | 推导产品责任与必要机制，不从目标直接跳到界面，也不假定存储和自动化自然带来价值 |
| 角色与分工 | 谁提出要求、生产、使用、评价、维护；同一人何时切换角色，人和 Agent 如何分工 | 决定入口、信息需要、动作与决定权，不按职位凭空新增角色 |
| 场景与生命周期 | 什么触发使用，处于什么阶段、频次和状态；首次、稳定使用、异常、复盘与接手有何不同 | 决定哪些完整任务必须成立，补全用户没有逐条列出的必要情况 |
| 任务与判断 | 用户从什么状态开始，需理解和决定什么，做哪些动作，以什么可用结果结束 | 决定信息、反馈、交接和异常路径；“点开页面”通常不是任务终点 |
| 对象与规则 | 用户工作的对象、关系、状态、版本及变化影响；什么可修改、保留、复用或失效 | 决定数据和行为语义，同一对象可支持多个任务，不按表直接造导航 |
| 信息与交互 | 当前任务先展示什么，细节何时展开，如何操作、返回和跨场景继续 | 设计页面、画布或其他形式；场景不同可有不同默认视图，共用事实 |
| 验证与演进 | 哪些观察能说明任务有价值、容易完成；什么结果会推翻设计或原因假设 | 决定如何实用验证、何时修改或保持现状，以及下一阶段范围 |

每个关键设计至少应能追溯到一个具体场景和用户决定。沿完整工作过程检查阶段之间谁作决定、留下什么、下一段凭什么继续，并据此推导产品责任、对象与信息层级，再决定界面。场景表不能替代转换关系；图的显示模式也不等于用户任务。避免“每项能力都有”但前后任务接不上。

认知章先解释目标、行为与关系，不提前将侧栏、卡片、画布或技术栈写成唯一答案；已确认的形态约束注明来源。设计章再比较与真实任务有关的方案，从认知结论推出选择。这个先后是表达和决策依赖，实际使用仍会反过来修正认知，不必等所有未知消失才推进可逆验证。

整体设计、角色差异或场景覆盖不清时，读 [场景推演与设计推导](references/scenario-reasoning.md)。它是找遗漏的提示，不是所有产品都必须实现的功能清单。

用户要整体产品设计或逐项推导界面时，继续读 [从整体外壳推到具体交互](references/product-design-derivation.md)。从产品形态、全局范围和导航，到各入口主体、内部视图、操作与详情，再到跨入口及异常状态，逐层解释设计理由。不能停在场景表，也不能直接跳到局部控件或配色。

## 用实际工作修正理解

亲自使用用户能得到的成果：软件要操作、报告要读正文、业务产物要按用途判断。没有可操作实现时，明确哪些只是场景推演，并用可审阅的任务走查检验设计，不宣称已经实用通过。

从使用中同时提取有效做法、具体收益、障碍、新机会和不确定性。写出内容让你理解了什么，而非只记录页面包含了什么。委托别人核对可补盲点，负责人仍须整合并承担最终判断。

发现问题后，区分目标或标准不合适、输入不足、方法失效、执行故障、信息难找与交互阻碍。对会改变方向的重要原因保留有根据的替代解释，并寻找能区分它们的证据。评价者的意见也是证据，不能自动视为事实；同时检查评价深度与目标是否相符。

区分当前方法可以调整的部分与所属产品或基础设施的能力缺口。真实任务可以提出更高层的问题并保留证据，进入对应项目的判断与安排；认知发现的范围不等于本轮执行范围。说明依赖与影响，项目改进交付后再回原任务复验，不因记录了问题便声称已经解决。

技术正确、完整任务可用、业务成果有价值、用户接受是不同判断。一次局部成功、一次模型配对或单个案例，均按其实际覆盖说明结果。资料已保存也不等于用户容易理解；版本增加不等于方法改善。

## 从整体理解决定优先级

提出下一阶段前，回到目的与场景，比较真正竞争的方向：它们分别解决谁的什么问题，影响多大，是否是其他任务的依赖，证据是否足够，代价与不确定性是什么。无需虚构精确分数；说明为什么选这个，以及为什么其他重要缺口现在暂缓。

保留已有有效能力。完整思考不要求一次实现全部场景；选择一段有业务意义的完整任务作为建设范围，同时保留它与全局的联系。纯展示或基础能力也可独立交付，但说明它解除什么依赖，不能冒充最终使用结果。

允许不改功能、修内容、改变表达、撤销假设或结束实验。不要把每个疑问都转成需求，也不要把一次局部修复的历史约束固化为永久产品规则。

交给执行者的应是具体用户任务、设计理由、已有能力、改动边界和可观察结束条件。交付后重新完成同一任务，说明哪些判断得到支持、被推翻或仍未知；据此继续、调整或停止。本 skill 不额外授权模型开销、外发、数据删除或其他外部动作。

## 留下能继续使用的认识

优先更新项目已有的产品定义、交互定义和当前状态入口，避免每轮生成另一套平级真相。首次整体梳理可保留一份认知说明，但明确它与正式定义和执行状态的关系。

让读者能够找到：当前产品理解及依据；关键场景如何推导设计；保留与缺口；主要原因假设；这轮取舍和验证；新证据改变了什么。区分用户已确认、实际观察、待验证推断和提出的方案，别把自己的建议写成用户已决定。

收尾同步受影响的结论与状态。记录应该帮助下一位接手者恢复判断，而非留下“总体完成、子项仍待验收”的冲突。整体认知被纠正时，按新的因果主线重排正文；不要只在末尾追加一节，保留前面已经失效的编排。审阅需从一项真实业务反向走完整条论证链，不能以章节齐全、多人同意或界面顺序合理证明理解完整。
