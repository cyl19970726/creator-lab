# 场景推演与设计推导

在整体设计或持续“不好用”时使用。围绕真实业务选择相关维度，不做所有组合的穷举，也不因能想象一个情况就决定建设它。

## 怎样把场景说具体

描述谁在什么触发和阶段下，带着什么已有材料与约束进入，要理解或决定什么，以什么结果离开。再看它与前后任务怎样连接，以及失败或中断后怎样继续。

工具产品常见的变化维度：

- 时间：首次建立、首次使用、重复使用、积累一段时间、升级、停止、回来接手。
- 工作规模：一个对象与多个对象；单项判断与集中比较；当前成果与历史并存。
- 角色：生产、使用、评价、维护；同一个人切换这些责任。
- 状态：尚无数据、正在进行、成功、部分完成、失败、等待人处理、已有成果但最新尝试失败。
- 信息需要：理解原理、快速办事、阅读结果、查找复用、解释原因、判断要不要改变。

资产查找、协作和复盘可能贯穿多个阶段，并非流程最后附加的页面。对某个产品不重要的维度可以暂缓，说明原因即可。

## 将一个场景推导成设计

例如：“成熟方法连续处理业务，一段时间后集中复盘”。这通常意味着：

| 场景中的需要 | 对产品设计的影响 |
| --- | --- |
| 平时尽快完成一件事 | 从业务要求或待办进入，给出可信的可用方法；无需先做对照实验 |
| 以后知道每次用了什么 | 保存准确输入、方法和结果的关系；后来的配置变化不改写过去 |
| 集中找反复发生的问题 | 支持按方法、阶段、案例或时间查看相关成果；保留无评价和失败样本 |
| 判断改法是否值得 | 将证据、原因假设、改动和比较联系起来，允许继续使用原版 |

这些是从场景得出的设计约束；并不意味着现在必须新增一个数据库、评分榜或运营大屏。

另一个例子：方法开发者需要理解节点合同与配置；业务使用者需要知道本次要求、成果与下一步。同一事实可投影为方法图和案例成果图。不能因为底层由工作流执行，就要求所有人先进入方法配置。

## 检查关系而不只检查页面

挑选最能影响当前决定的几个任务走查：

- 从空白开始，用户能否理解能做什么、如何开始？
- 从已有成果回来，能否找到准确对象并继续处理？
- 一次失败之后，之前可用的成果是否仍可读，下一步是否明确？
- 多个版本或案例并存时，是否能辨认并作有依据的选择？
- 一项评价如何改变这份成果、后续工作或方法，三者是否混淆？

发现断点后，追问是对象关系缺失、规则不清、动作未接通还是呈现负担。用原因决定改动，不先决定加哪个页面。
