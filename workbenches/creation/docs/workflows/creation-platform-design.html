Creation：可组合的创作工作流与共享工作台

设计修订：2026-09-29 · v0.4 首个实现 PR。本文保留完整平台目标；当前实现范围为 P1/P2 文章闭环，视频生产与方法有效性验证仍待后续。验证结果见 实施记录。

本文是设计与迁移的主入口。Markdown 是文字正本，旁边的 HTML 是同一内容生成的离线图文阅读版。旧运行、私有作品和历史证据保全；新实现不承担旧 UI、API、CLI、目录布局或数据库的兼容义务。旧实现可在新实现接管后退出，不通过改名或重新分类证明新方法有效。

1. 我们要构建什么，以及本轮交付到哪里

长期目标是一个可以持续协作、支持多种内容目的和载体的创作平台。它把创作者的目的、受众问题、材料、实际作品、审阅、修订和交付放在同一份可恢复上下文里，让用户隔一段时间回来仍能看懂：为什么做、做到了哪里、发生了什么变化、接下来做什么。

本轮在设计基础上实现第一条完整文章路线：新工作台、API、持久 worker、真实 agent-workflow 创作与审阅、按精确稿件反馈修订。完整平台图仍包含未来能力；视频生产、私有数据导入、平台发布与跨内容方法验证不属于此 PR。技术验证与真实模型验收分别记录，不能互相替代。

用户本轮明确取消旧实现兼容约束，允许全新实现，并允许必要时修改 agent-workflow。建议采用 TypeScript、React / Vite、Fastify API 与独立执行进程；保持 Node 24、根 pnpm workspace 和唯一的 vendor/agent-workflow。研究、分析、创作三个工作台独立；不因重建 creation 强制改造兄弟工作台。技术选型与替代方案详见第 7 节。

2. 认识怎样变化：保留设计理由，不保留错误前提

以下是本次讨论形成的公开设计依据。表中历史实现问题指此前被审会话与实验工作树；其他行是本次讨论检验过的设计假设，不表示用户曾要求那些做法，也不表示主目录已经实现 B1/B3。详细历史案例与原始执行证据保持私有，不复制到设计文档。后来的目标澄清用于下一次工作，不能倒推执行者在更早时已经收到相同信息。

早先的理解或做法 暴露的问题 本次取舍
沿 B1→B2→B3 顺序建设三个入口 入口与目录存在，不证明业务步骤确实执行，也不证明流程覆盖完整。 把定义、实际执行、作品质量、接受与交付分别呈现。
把 B1 主要做成事实边界清单 能避免错误陈述，却未必说明内容为何值得做；材料容易反过来决定主题。 B1 形成创作判断：价值、受众变化、证据、可行性及关键未知。
每听到一个因素，就增加字段和审核 字段齐全不等于关键假设被检验，流程容易越做越重。 按关键不确定性选择工作；能复用就复用，不把全部分析设为每篇必做。
把热度直接理解为需求，把内容少直接理解为空缺 有关注不代表需要某种解释，供给少也可能意味着需求弱。 区分关注信号、具体疑问、已有解释、未满足部分及判断置信度。
把用户提出的问题直接当成技术结论 问题可能含有待验证的因果前提；过度纠错又会丢掉有价值的困惑。 保留创作目的，检验问题结构；事实依证据，价值取舍沿用用户授权。
为所有内容固定三个独立工作流 文字写作的设计与制作可能是同一个动作，视频则常需要单独样片。 保留三种职责，执行单元按独立判断价值与修改成本组合。
先把设计“完全审过”才能接触真实媒介 某些理解、声音和动态问题只有原型才能暴露。 允许 B2 调用低成本制作原型，必要时回到 B1；完整媒体检查不被原型结果替代。
B3 只接已有媒体、检查回执 实际制作与返工留在 Host 自由调度中，恢复与追踪有缺口。 将需要恢复、复用、控制副作用的制作动作接入工作流；外部工具仍负责实际渲染等能力。

决策记录

  • D01 保留职责，组合执行。 取消固定三个执行单元的要求，保留内容定义、表达创作、制作验证之间的错误归属。替代方案“全部合成一次生成”缺少返工定位；“每篇三个批准点”增加无必要交接。
  • D02 以实际资产作为交接。 同一资产可以服务多个职责，不为阶段数量复制文件；复核记录精确绑定版本和范围。
  • D03 先解决必要的不确定性。 趋势扫描、补研究、读者试读和样片都按需要触发。削减工作的下限是关键事实、核心承诺、实际媒介质量及授权边界仍被检查。
  • D04 保留内容目的与载体两个维度。 “机制解释×文章”与“机制解释×视频”共享部分方法；“机制解释×视频”与“人物故事×视频”共享媒体能力但不共享整套内容标准。
  • D05 共享执行能力可以改。 业务方法、资产和创作决定属于 creation；通用执行缺陷或能力缺口可以在 agent-workflow 修正。不复制其源码，也不让宿主和共享库同时拥有两套任务队列。
  • D06 全新实现，替代旧产品结构。 v0.2 的“保留旧栈、旧导航和旧路径”约束已被用户本轮明确撤销。新 UI、API、运行入口和数据模型按目标设计，不维护双轨兼容层；采用分批完成新功能的方式控制重建风险。
  • D07 保全成果，退出旧代码。 数据保护与代码兼容分别处理。保存真实作品、来源、决定和运行证据；旧文件扫描规则、CLI、页面和数据库结构不自动进入新系统。
  • D08 用 TypeScript 明确边界。 新产品代码统一类型与运行时输入校验；文档生成等简单脚本仍可用 .mjs。改扩展名不算重构完成，领域关系、执行边界与实际交互必须一起改。

3. 三种职责与实际执行单元

职责 核心问题 主产物 何时足以向前 典型退回原因
B1 内容定义 什么值得做、为谁、产生什么变化、凭什么能兑现？ 当前内容定义与决策依据 重要假设已有处置，承诺有证据与可行路径；其余未知显式保留 核心问题不成立、价值不清、账号冲突、材料不支持承诺
B2 创作与表达设计 用怎样的实际内容组织与表达，兑现承诺？ 可阅读/观看/试听的草案及必要制作说明 核心表达有可审资产，已处理影响理解或价值的缺陷，后续投入合理 讲法、结构、证据使用、节奏、图文关系失败
B3 制作与成品验证 如何把方案做成实际成品，并确认适用质量？ 实际成品、适用工程与检查记录 对当前完整版本完成适用检查；交付选择与发布授权另记 媒体/排版/导出缺陷，或原型揭示上游方向与表达问题

职责不等于页面、目录、Agent、skill 或 run。一个执行步骤可以覆盖 B2 与 B3；工作台须显示“合并执行”，不能显示“B3 未做”或伪造一个 B3 run。必要的质量责任没有因为合并而消失。

什么时候拆，什么时候合

当中间结果有独立判断/复用价值，或能显著降低下一段返工成本时拆开；当设计与制作是同一动作且没有独立交接价值时合并。耗时、外部费用、不可逆副作用、媒介检查能力和已有资产均影响选择，不按字数或模型数量机械决定。

示例配置 适用执行路线 保留的检查
观点×短文字 简要 B1 → 写作/修订（B2+B3） 适用事实、表达承诺、最终正文与发布视图
机制解释×文章 B1 → 核心解释/全文（B2）→ 排版检查（可与 B2 合并） 因果证据、阅读理解、全文一致性、适用渲染
机制解释×图解 B1 → 代表图文（B2，必要时含制作）→ 整组图（B3） 图中关系、可读性、顺序、完整组与目标渠道
机制解释×动画视频 B1 → 核心声画草案（B2）↔ 实际原型 → 全片制作/检查（B3） 事实与理解、动态、听感、同步、完整版本与适用渠道

这些是起始配置，不是证明全部组合已经有效。首轮只验证文章与视频两条差异明显的路径，不预建全部目的×载体的笛卡尔积。

4. B1：形成可检验的创作决定

B1 连接创作者目的、受众状态、现有内容、证据与交付能力。它不承担长期账号定位的擅自变更；已确认主题不必重新征题，但其中的因果前提仍可被证据挑战。问题有价值但材料不足时，补相关依据或显式调整范围，不能悄悄换成更容易讲的题。

输入与资产

输入 用途 不能推断什么
当前请求、已有决定、账号定位版本 确定目标、价值取舍、受众与授权边界 用户判断不自动成为技术事实或市场事实
可选热度/提问/同题内容与旧作反馈 判断关注窗口、具体困惑、已有覆盖和缺口 搜索排序不等于全网热度，内容少不等于需求旺
原始材料、研究/分析资产、来源位置与版本 匹配承诺与证据，区分案例、依据和启发 原文有组件不等于解释了完整因果机制
载体、渠道、时效与可用能力 确定承载量和可行性 不必在 B1 固定镜头数、台词或逐像素布局

B1 主资产是 content-definition（新合同提案名；历史 content-brief 需要复用时显式导入，不设常驻兼容 reader），包含：目的与受众变化、主问题/承诺、账号适配理由、材料用途与关键依据、范围取舍、交付意向、关键假设/未知及处置、当前决定及来源。热度分析不适用时记录原因，未知不能填为零。系统元数据另保留工作区、资产版本、schema、输入依赖与生产者；主界面不展示长指纹。

内部步骤

  1. 恢复上下文。 将已确认要求、候选解释与未知分开；冻结本次实际使用的输入版本。已有内容定义可直接进入差异检查。
  2. 找关键不确定性。 判断需要需求/供给观察、材料核验、账号适配取舍或小样验证中的哪几项；记录不执行某项的理由。机会与证据检查可并行，能相互修正。
  3. 形成内容定义。 提出一个有理由的主要方案；只有存在实质取舍才比较备选，不固定“三个选题”。写清材料最终用来产出什么理解或体验。
  4. 挑战与修订。 检查问题前提、价值和证据是否相称。证据不足回相关材料；方向冲突保留可比较取舍；表达难度不明可请求 B2 原型，而非无限润色定义。
  5. 选择当前版本。 按已有授权记录推进/补依据/调整/暂缓及理由，交给 B2。普通修复不新增人工批准点；重大目标或授权变化才集中向用户确认。

结束条件与验证边界

下一步能明确需要解决什么，并知道关键依赖与未知；不能用字段齐全替代这一判断。需求成立、事实成立、作品可理解各用适合的证据。内容机会仍是假设时允许范围受控的探索，不能把潜在热度写成效果保证。

用当前 Kimi / GLM 题目检验这套设计

本次用户捕捉到的创作问题是：“AI 怎么通过更弱的模型训练出更强的模型？” Kimi / GLM 的后训练流水线材料服务于这个问题的解释与检验；分别复述两套流水线，不能自动兑现该内容承诺。这是本题的边界，不应被写成所有选题的默认目标。

“大家有兴趣、但有内容空缺”目前是用户提供的机会线索。B1 应进一步区分：人们具体困惑什么、现有内容解释到哪里、缺少的是哪一段理解，以及观察覆盖的渠道和时间；本文没有完成市场调查，不把该线索写成已验证的市场结论。

还应把“弱”和“强”展开为待核问题：比较的是哪种能力、在哪一环参与、提供什么训练或评价信号、最终改善由什么证据支持？材料如果涉及弱监督、验证、蒸馏或强化学习等不同机制，须逐项核对角色和依据，不能只因都出现模型就统称同一个因果过程。这里列的是研究问题，没有断言两家实际采用了哪些机制。

本题资产 应包含什么 合理归属与去向
两家流水线的来源与研究结果 原始依据、参与者角色、可支持的主张、未支持之处；保留来源位置 可复用的输入资产；由来源工作区持有，在本作品显式引用或冻结导入，避免为 B1 复制两份研究档案
本题内容定义 观众困惑、理解后的变化、账号适配、核心问题、材料分工、事实边界和交付意向 本作品的 B1 主资产；一个综合定义即可，两家公司不是两个强制 B1
本题实际表达草案 真正解释角色、信号和能力变化关系的正文 / 图 / 声画草案；限定与反例随关键主张出现 B2 资产；可按受众与媒介选择案例，不要求平均介绍两家公司
实际成品与检查 当前完整文章、图文或视频，以及对应范围的实际复验 B3 或 B2+B3 合并产物；不会因来源研究完整就自动通过

这些是本题下一轮应形成或引用的资产关系，不是假装已经生成的文件路径。当前主目录没有该题的材料与作品；历史资产继续留在原工作树，后续逐项登记来源和版本，再进入新路线。若未来同时做文章和视频，可共享仍适用的内容定义及证据，但各自的表达与媒介检查单独成立。

5. B2：用实际草案检验表达

B2 的产物已经包含内容本身。文章正文、图文代表页、视频口播和草图可以直接审阅；“后面这里讲原理”这种说明不能代替实际内容。B2 不强制每种内容都有声画表、封面、首十秒或时长字段。

输入与资产

输入为当前内容定义、精确版本的来源/参考资产、目的方法、载体要求和既有草案。主资产是 creative-draft：观众可见内容、必要的结构/表达说明、关键主张与依据、素材依赖与可用性、未解决问题。载体扩展分别保存正文、图文页、声音/镜头或交互说明，不用空字段伪装统一。

内部步骤

  1. 选择最值得先验证的表达。 依据风险选代表性内容；不固定每题必须开头+难段或相同图数。简单内容可直接形成完整稿。
  2. 产出真实草案。 写、画或试读到足以暴露问题；已有有效资产按用途与版本复用，明确人工稿、模型稿和导入稿的来源。
  3. 审实际内容。 适用事实/推理检查与表达/读者反馈可以分工；读者只收到观众可见内容及必要读者背景，不提前获得作者答案。模拟反馈必须标身份，不等于真实传播。
  4. 按原因修改。 概念或价值失败回 B1；依据缺失回相关材料；局部表达失败改草案；必要时调用制作适配器验证真实媒介。
  5. 扩展与交接。 核心表达成立后完成适用全文/整组/全片设计，检查新增部分及相邻关系。输出当前版本和制作依赖；简单文字可在同一步完成成品检查并覆盖 B3 职责。

B2/B3 的接缝

“昂贵制作前有可审表达”是原则；“任何真实声音或图像都必须等 B2 全部通过”不是原则。原型是为了获得证据，不默认扩成全片。未改变的原型可在核对版本、范围和制作规格后复用；完整成品仍要按完整范围检查。

6. B3：把实际制作纳入可恢复执行

B3 可以使用现有外部渲染、配音、绘图或排版能力，但需要由业务工作流记录必要输入、调用、输出文件身份、失败与修订。无需框架自己提供媒体模型，也不允许仅增加“已制作”叙述而没有真实执行和文件。

输入与资产

输入为当前可制作草案、素材与许可/使用条件、适用规格及授权。输出为 deliverable：实际文件、适用源工程、内容和媒介检查、渠道预览、当前选择及遗留限制。文章可只有正文与渲染检查；图文不要求音频；视频对声音和同步是否适用须显式判断。

内部步骤

  1. 计划实际制作。 确定能力与依赖是否可用；按成本/风险选择原型或完整制作。不能一直等待一个当前执行环境拿不到的检查能力而没有处置。
  2. 执行工具步骤。 必须可恢复的动作进入 ctx.task 或适用子 workflow，保存幂等键、工具版本、输入资产、输出文件哈希和实际结果。人工/外部检查另记待交接任务，不伪装成模型运行。
  3. 直接检查适用成品。 技术检查与实际看、听、读分别记录范围。转写不能替代听感，抽帧不能覆盖连续动态；报告缺口时说明具体缺什么、由什么能力补足。
  4. 修复并传播影响。 制作问题回对应工具/资产，表达问题回 B2，承诺问题回 B1；不因改一处就全量重做，也不让旧版本审阅自动覆盖新版。
  5. 形成可交付候选。 当前完整资产有适用检查；正式接受、交付选择与公开发布是独立事实。C1/C2 保留在外围生命周期中，不合并成 B3 自动发布。

原型是否必要由本次风险决定。已有验证过的路径可以更短，但不能省掉对本次真实成品的必要检查。技术测试只证明工具与控制流，不证明作品好看、好听或易懂。

7. 新架构与 agent-workflow 的边界

为什么换实现，以及 .mjs 到底是不是问题

.mjs 是 JavaScript 模块文件形式，不决定是否有清晰架构。原生 JavaScript 也可以做好模块化、验证和测试；当前真正不适配的是以视频文件分类组织产品、依赖固定阶段与路径、HTTP 服务与工作流缺少完整执行连接，以及不断增加的资产/状态关系没有统一领域模型。只把 .mjs 改成 .ts 会保留这些问题。

新平台要长期处理多内容、多版本、不同媒介、人工反馈、Agent 执行和中断恢复。建议主动重建为 TypeScript 的模块化单体，分 web、API、worker 三个运行入口：业务代码在一个 creation 项目中维护，HTTP 进程不承担长时间模型调用；无需起步就拆微服务或建立插件市场。

层 选型与责任 选择理由与代价
交互前端 React + TypeScript + Vite；作品、资产、审阅和运行的独立组件 适合持续变化的多区域状态与交互；增加构建与前端状态管理要求，不靠框架自动解决产品设计
HTTP / 应用入口 Fastify + TypeScript；显式业务命令、查询、事件读取 请求校验与响应结构可集中约束；业务逻辑不堆在路由里。首版使用增量轮询，必要时加 SSE
业务领域与合同 TypeScript 严格类型；统一运行时 schema 及版本标记 类型帮助约束代码内关系；模型、HTTP、文件输入仍必须运行时校验，避免三处手写互相漂移的 DTO
执行宿主 独立 Node worker；持久任务、互斥/租约、恢复、取消与能力适配 进程重启与浏览器关闭不应让作品任务消失；初版单机单 worker，但任务身份和领取规则明确
工作流内核 根 agent-workflow 的 TypeScript 包；必要时有针对性修改 继续使用真实执行账本、模型调用、任务与恢复语义；通用问题在共享层解决，业务决策留在 creation
状态与产物 私有 SQLite + 真实资产文件；新库、新 schema、可追溯版本 当前本地使用无需先引入数据库服务。大文件不放数据库；锁竞争与跨库一致性在验收中验证

选型依据：仓库 research 已采用 React/Vite、Fastify 与 TypeScript，analysis 也有 TypeScript、React 和独立 worker，vendor 核心已有 TypeScript 类型。复用团队熟悉的工具链可以减少额外认知成本，但三个工作台仍独立，不复制它们的业务实现。官方机制参考：TypeScript 静态类型检查、React 组件与状态、Vite 构建入口、Fastify 校验与序列化。这里是项目选型判断，不是这些工具优于所有替代方案的结论；实施时核现有锁文件和支持范围，不顺手升级整个仓库。

继续 vanilla JS + JSDoc、Vue/Svelte、其他 Node HTTP 框架都能完成任务。选择 React/TypeScript 是因为本项目的状态与协作复杂度、现有工具链和后续维护成本；当前没有服务端页面渲染需求，不为一个本地创作工作台引入 Next.js 全栈约定。媒体适配器可以调用 Python 或其他工具，不强求所有能力改写成 TypeScript。

领域模型先于页面与文件夹

核心对象 保存的事实 不混同什么
Workspace / AccountContext 创作者定位、渠道与授权上下文的版本 不等于某个运行目录或默认历史账号
Work 一份创作的目标、目的、载体、当前选择与工作状态 不强制一份 Work 对应三个阶段、一个 run 或一个视频
ArtifactRevision 不可变内容版本、类型、文件身份、依赖、生产来源 路径、文件存在、最近修改时间不能代替版本选择
Review / Decision 对精确资产和范围的意见、评估、选择及授权来源 审阅 pass 不等于用户接受，接受不等于发布
ExecutionBinding Work 与原生 run、实际步骤、职责覆盖、方法版本的关联 业务状态不能覆盖原生执行事实

依赖方向固定：web 使用安全合同；API 调用应用服务；应用服务操作领域对象与持久接口并发出任务；worker 读取冻结任务并调用业务 workflow；workflow 通过 vendor 和适配器执行。UI 与模型不得直接修改执行账本，媒体适配器不决定选稿，workflow 不拼页面 HTML。

执行闭环从首条路线就成立

  1. API 接受一次明确命令，校验 Work、输入版本、能力和预算，以幂等命令 ID 写入业务变更及持久待执行记录；响应返回可查询的任务身份。
  2. worker 原子领取任务，核对 workflow ID/revision 与输入快照，调用 vendor。首版采用操作系统持有的单 worker 排他锁；进程退出后任务仍在，确认前驱退出并取得锁后才恢复。超时仅标为需检查，不能直接让新 worker 抢占仍可能存活的旧进程。P1 必须验证崩溃释放锁、暂停进程仍持锁、重复启动被拒绝；不能只靠 PID 文件或任务表租约宣称安全。
  3. 作者、审阅、制作都产生真实记录与精确资产身份。文件落盘、vendor 发布与业务登记无法假定一次原子事务完成：使用稳定键、登记待办与可重放核对，处理“文件已写但记录未齐”的中断窗口。
  4. 等待人工意见或外部检查时保存明确事项、资产版本、范围、原因与接续动作，释放执行资源。反馈改变创作输入时建立显式修订任务和新版本；不能把已终止的运行状态改成成功。
  5. worker 重启仅重入版本一致的运行；业务方向或冻结输入改变时启动有关联的新修订运行。取消由宿主持久记录并传播给正在执行的 signal、工具和适用子任务；工具不能即时取消时显示真实状态。
  6. 页面从领域资产/决定与 vendor 运行投影读取进展；初稿在总流程结束前即可查看。人工选择、实际质量与执行终态分别显示。

首版 worker 只承担当前两条业务路线需要的调度，不做分布式通用平台。子 workflow 可先内联调用；真正需要跨进程子任务时，再实现与同一任务表衔接的 dispatcher。现有库不提供完整宿主，任务队列、租约、HTTP 和跨进程取消当前仍由宿主负责。当前宿主集成边界

当前 RunStore/SQLite 写入没有 owner epoch 或条件写入校验，业务任务表的一张租约不能阻止旧 worker 继续写原生账本。因此首版不承诺失联后自动抢占；将来需要抢占、多 worker 或跨进程持久子任务时，先落实覆盖账本写入与资产提交的所有权校验，再允许重领。验证必须包含“旧 worker 暂停→尝试接管→旧 worker 恢复”的场景。外部工具在宿主退出后仍可能运行，恢复时另行核对操作回执，不把进程退出当作工具已取消。

上述共享改造项是评估范围，不是已确认缺陷清单。当前已可用的能力包括 ctx.agent、ctx.task、ctx.call、ctx.phase、有界并行、资产发布和原生读模型；它们不因重建而全部推倒。API 依据：执行 API、前端投影。

本次只读源码核查还收窄了三个应优先做测试的共享问题：

已观察到的语义 对新平台的影响 最小决策与验证
当前 waiting 对应未完成的持久子流程；needs_review 是运行终态，没有通用外部信号等待接口 不能直接把“等用户”标成一个原生 waiting 并期待库自动唤醒 首条路线以宿主 ReviewRequest 保存待办，阶段运行结束后由决定触发显式关联的继续/修订运行。若确需同 run 的外部等待，再设计共享 suspend/wake，测试重复唤醒与重启；不将“待审批”结果放进会被成功缓存的普通 task
ctx.task 当前幂等键形如 runId + stepKey；相同 key 的输入变化不体现在该键中 外部工具不能只用该键判断语义上是否同一操作，工具成功到步骤落账之间也存在中断窗口 适配器使用明确操作 ID、输入摘要与回执核对；故障注入后判断是否需要在共享合同提供更合适的语义键
发布资产会创建新的资产 ID；尚无明确唯一发布键 发布已成功、控制步骤尚未记成功时崩溃，重放可能重复登记 复现该窗口，再决定共享幂等发布接口及存储唯一约束；不能在 UI 中按文件名合并来掩盖重复执行

这些观察来自当前 core runtime、执行合同 与 SQLite store；设计时未将它们全部判定为必须修改 core 的缺陷。首版已通过 creation 存储适配器处理 run 与 job 同事务绑定、相同发布复用、文件与业务记录恢复，并加入故障测试。实际实现优先验证恢复正确性，不追求表面上所有动作都挂在同一个 run 下。

用户已授权必要时修改共享库。修改须留在唯一子模块，记录对应 revision；涉及破坏性合同变化时，同步更新受影响消费者并运行 research/analysis 的相关集成检查。取消 creation 旧实现兼容，不等于可以让另外两个工作台失效。首个实现 PR 使用现有 vendor 接口，未修改子模块；creation 的恢复适配器不被宣称为共享库新增能力。

最小组合与真实性

首轮用 TypeScript 代码维护文章、视频两条路线，共享资产合同与必要步骤；一次执行记录 purpose、medium、methodRevision、inputRefs、stopAt，以及实际步骤覆盖的职责。B2+B3 可以映射为一个操作。不为了可配置预建拖拽 DAG 或一门新 DSL。

文件是实际内容，业务库记录归属与选择，协作记录保存意见/决定，vendor 保存执行事实。审阅、选择、交付与发布绑定精确版本；来源变化只影响有关依赖，旧记录原样保留。复用完成步骤必须核对冻结输入与输出，未知用量不填零。以上约束需要测试与真实作品建立，TypeScript 不能代替这些证据。

8. 工作台：让人接回工作，而不是读运行日志

重新实现工作区、资产阅读器、版本和协作界面，直接围绕作品与实际执行设计。旧实现中有效的业务约束作为新测试来源，不要求复用其页面或状态管理代码。第一屏首先回答“为什么做、现在有什么、为什么停、下一步”，原生 run/step/attempt 放在按需展开的运行详情中。

状态不挤进一个“完成”

内部沿用各自事实来源：执行、结构校验、质量复核、正式接受、交付选择/发布。用户只看到与当前动作有关的简短组合，例如“稿件已生成；核心解释需修”“视频已导出；声音尚未检查”“当前版本已接受；尚未发布”。点击后能看各项范围与依据。

用户当前要求与正式决定确定目标和推进授权；文件与哈希证实内容身份，ArtifactRevision 与显式选择决定当前版本；vendor 账本确定执行事实。协作摘要仅是带来源和更新时间的导览，不能覆盖这些依据。摘要引用的目标、资产或 run 已过期、缺来源或相互冲突时显示“待核对”；编辑摘要不能改写正式接受或运行终态。用户看得到冲突的具体对象，再按授权范围接续。

“B2+B3 合并执行”不等于 B3 跳过；不适用检查需有原因；未运行、未到达、受阻和无法判断不能共用灰色而无文字解释。新链接使用作品、资产版本、执行与审阅的显式 ID；不要求兼容旧 group 或深链接。导入历史决定时保留原始范围，不通过改标签扩大接受含义。

交互范围

新工作台从第一条路线就连接实际创作与协作。开始、继续、取消均为明确命令，经服务端检查工作区、版本、预算、能力与授权；页面刷新/轮询不产生副作用。与执行入口同时交付等待、取消和恢复说明；不先做一套只能显示假状态的完整 UI。

工作台可以管理多种目的和载体，但不预造庞大的模板商城、低代码编排器或多用户云服务。现有本地工作区隔离也不冒充已实现多租户鉴权。

9. 当前目录盘点与全新实现的处置

当前目录未明显膨胀，但它来自迁移目标，已经不再约束新产品。 v0.2 以保留旧实现为前提，得出“原位渐进改造”；用户本轮明确取消此前提。新版按新职责建目录，不做常驻兼容层，不承诺旧 URL、CLI 参数、文件发现逻辑或数据库 schema 继续工作。

盘点基线为前轮修改前的 102 个 Git 追踪文件。默认选题、渠道及作品清单为空。另一个实验工作树在同一基线上有 30 个追踪文件修改及 603 个未忽略新增文件；它不是已合并版本，不整体覆盖主目录。依赖、构建输出、私有状态不算源码膨胀。

data/ 4 新业务 schema 与私有状态独立建立；旧库不自动作为新库打开。需要的历史事实按明确导入映射处理
episodes/、research/ 各 1 新系统不依赖这些空目录或前缀；旧发现实现退出时一并移除占位。历史材料按资产登记进入，不伪造研究前置
media/、videos/ 当前不存在 新作品在配置的资产根管理；不复制旧工程作为通用运行时

旧目录所体现的有效约束仍有价值：工作区归属、精确版本、审阅范围、跨账号导入、私有文件边界。新实现继承这些业务判断，不必继承实现方式。盘点时旧实现没有运行启动 API，B2 也未自动登记；新实现已将显式命令、执行与资产登记接通。

迁移基线证据（旧代码已退出，链接指向 Git 历史）：路径配置、旧目录发现、旧固定路线、既有范围校验、B2 配置。它们用于本次盘点，旧实现退出后不再要求作为线上接口保留。

目标目录：一个产品，三个运行入口

这是完整目标布局；首版已创建 web/API/worker、contracts/application/workflows/infrastructure，未单设无实际职责的 domain 层，也未创建视频空壳。文件随实现出现，不预建几十个空目录。源码不承载作品媒体；资产根由配置确定，可独立于私有数据库根。新作品使用显式 Work 与 ArtifactRevision 登记，文件夹名字不决定阶段或接受状态。

清理与切换

先记录当前代码基线并保存未提交成果；私有文件不依赖 Git 兜底，需要时单独备份并验证可读。新实现使用独立状态路径，不双写旧库，不双轨维护状态。实现期间可以暂时存在两个目录，目的只是完成替换，不作为永久兼容功能。

新文章路线和基本工作台通过后切换默认入口；视频相关旧实现仅在对应能力接管、或明确排除旧能力且保存必要成果后退出。发布助手可作为外部能力单独处置，不强迫首版完成所有旧功能。旧 URL 与 CLI 不做适配承诺；入口文档指向新产品，删除旧业务入口和已停用代码。

历史作品若需要继续使用，只导入明确选中的资产、来源与必要决定。保留原文和原始范围，缺少来源的历史接受不得伪装成新版本接受。导入是有边界的数据工作，不在新系统里长期养一套旧业务逻辑。另一实验工作树不自动删除或整树合入。

10. 按完整功能交付的实施计划

B1/B2/B3 的业务设计保持不变；以下是全新产品的建设顺序，不是每篇作品的固定流程。每一步产生可运行的纵向功能，避免先造庞大基础平台再找内容验证。

阶段 输出 完成依据 退出/回退方式
P0 架构修订 本文 v0.3、新栈与共享库边界、目录处置、新项目指导 旧兼容要求已撤销；现状和提案分开，图文一致 文档修订保留决策原因
P1 最小产品与执行底座 新 web/API/worker 骨架；Work、资产版本、决定合同；私有新库、持久任务与 vendor 接入 页面/命令到测试资产可读；重复命令、单 worker 排他、确认退出后恢复、取消；文件已写/发布已成/登记未齐的中断窗口均核验，模拟产物明确标识 新状态独立；可停 worker，旧库原样保全；不要求 UI 兼容
P2 文章完整闭环 B1+合并创作/成品检查；实际模型调用、初稿阅读、用户意见、定向修订、复验与选择 新工作台完成目标→初稿→精确意见→修订/筛选→复验；人工等待跨重启继续；文章文件、vendor 产物与业务登记一致；执行、质量和接受不混同 方法有版本；失败样本保存；反馈改变输入启动关联修订，不改旧运行事实
P3 视频完整闭环 实际声画草案、按需原型、工具制作、完整检查、定向返工与异步接续 真实工具进入账本；文件/记录中断可核对；媒体改动使相关检查失效；缺能力有真实待办 工程/输出版本独立，外部工具副作用逐项核对；不覆盖旧媒体
P4 替换与收敛 新默认入口；移除停用的旧 UI、旧 B2 CLI、旧扫描规则和占位；必要资产显式导入 新入口覆盖声明支持的功能；无遗留运行依赖；数据备份可读；无永久双轨适配 保存的旧源码可恢复，但不把恢复旧进程作为新系统正常路径
P5 方法与跨内容验证 独立题目或另一内容目的；文章/视频的比较案例；按证据调整步骤 质量、投入、协作负担分开评价；共享库变更通过受影响工作台验证 方法可回到已验证版本；框架更新与业务实验分别记录

P1 只实现文章闭环需要的基础能力。当前内核已能表达的能力先使用；发现共享缺口时，以故障用例驱动小范围改动，再继续业务路线，不把“允许修改 vendor”变成先重写引擎的任务。工作台不是最后一阶段才出现的展示壳，P2 就必须让人接回真实创作。

第一批具体工作

  1. 建立新 TypeScript 项目边界与合同，明确 Work / ArtifactRevision / Review / Decision / ExecutionBinding；不机械翻译旧 app。
  2. 打通命令落库、worker 领取、vendor 调用、资产登记和页面阅读；从第一天测试重复执行与中断窗口。
  3. 以文章路线实现真实作者/审阅/修订；所有实际生产者都显式记录，不能把主会话补写冒记成子 Agent 作者。
  4. 对人工等待、外部工具幂等和取消做故障注入；能由宿主正确表达的留在宿主，确有通用缺口再改共享包并验证消费者。
  5. 用真实作品与一次跨会话用户接续验证新工作台；通过后切新默认入口，按能力归属退出旧代码，再扩媒体路线。

11. 如何验收：四种成果分别证明

检查层 需要的证据 不能代替
工程与边界 schema/分支/中断恢复/取消/幂等/跨区拒绝/路径与版本检查；共享库变更后的消费者检查 内容正确、表达有效
工作台协作 不看 session 的用户复述目标与进展、打开正确版本、追溯一条意见和修订、理解下一步 仅截图好看、按钮返回 200
作品质量 独立核事实与实际表达；适用媒介直接检查；接受绑定当前版本和范围 模型运行成功、模拟读者自称理解
方法效果 固定需求时点、输入、方法/模型、预算与比较节点；新旧真实产物、返工及用户介入记录 把旧稿换目录、把新增用户答案只给新方法

最小验证组合

  • 文章路线验证 B2/B3 合并是否减少重复交接且不漏全文检查；包含一处影响主线的事实/理解缺陷和一处局部问题，观察是否正确退回。
  • 视频路线验证 B2 原型与 B3 制作接缝；包含媒体修改后旧检查失效、工具中断恢复及缺少实际听看能力的诚实停止。
  • 独立迁移案例改变内容目的或载体中的至少一项，不把该题的答案提前写进方法；仅换主题不等于完整覆盖另一种内容。
  • 新旧输入无法对齐时，将结果记为有条件案例，不把全部改善归因于方法。质量达不到底线，调用更少不算成功。
  • 实际运行前固定范围、停止资产、模型与预算；预算不是本文虚构的工时估计。记录模型真实解析值、工具、首次产物、修订、用户诊断与帮助；未测成本为未知。
  • 评价器使用正确、合理不同表述、关键删漏、证据错绑、媒介未评估等案例；被测流程自己的 Reviewer 也是被评对象，不用其 pass 自证评价器有效。
