# 创作的核心思想

目标是**让 workflow 逐渐完成从内容到成品的创作，减少创作者必须亲自介入的工作**。减少人审是经过校准后的结果。眼下创作者仍要验收完整内容和成品，并把判断写成下一轮能检验的标准。

共享 [agent-workflow 的产品动机](../../../vendor/agent-workflow/docs/product.md)解释为什么需要持续执行、记录、评价和迭代的底座；[调优循环](../../../vendor/agent-workflow/docs/tuning-loop.md)给出通用方法。本页只说明创作中的选择及其证据。

## 让完整稿检验内容决定

内容选题、研究与写作互相影响。完整初稿能暴露“问题没有答到”“解释缺一环”“篇幅不够”等缺口，编辑可以回到材料或内容主线再写。因此 2026-10-03 用户授权把原 B1/B2 合并为一个 `content` workflow，不再要求先接受大纲才能写稿。研究编辑、作者、冷读者、事实核查与主编保留各自职责，但每个职责不必成为独立的人工关口。旧 B1/B2 的运行和决定继续作为历史证据。

原始机会、读者收获和必答问题应持续可见。反直觉切入只是可选手段；篇幅由必要解释和真实约束决定。冷读者应报告实际理解和疑问，不能从作者的研究答案推测读者反应。

## 按作品设验收节点

| 交付 | 创作者判断 | 主资产 |
| --- | --- | --- |
| 完整内容 | 读者是否理解、问题是否答到、事实是否成立 | 完整稿、与稿一致的内容决定和证据 |
| B3 成品 | 声画能否清楚、准确地传达内容 | 视频、封面、快照与检查结果 |

完整内容通过后，程序从该次运行生成版本化[作品档案](03-architecture/brief-and-handoff.md)供 B3 使用。制作有自己的成品验收。内容人审若要进一步撤销，审阅者须同时在创作者认可的正例和不认可的反例上校准；能拒绝 MiMo 一份旧稿不等于已经校准。

## 用 workflow 产出内容，用真实案例改 workflow

稿件与媒体须由 workflow 内的 Agent 或程序步骤产出，记录生产者和确切版本。某一阶段失败，就修改该阶段、升版本，并在同一冻结输入上重跑；主 Agent 在流程外补出一个好作品不能算流程成功。历史上七版视频由主 Agent 在 workflow 外手工做完再登记，正说明这种捷径无法检验流程。

初版要可真跑，但测试通过只证明已测试的代码行为。历史 B1/B2 各调了七版，B3 后续调到十五版；一些问题只能从运行证据发现，例如内容角色曾读入约 1.8 万字工程规范，稿件出现汇报腔。具体证据和版本见[调优手册](05-tuning.md)。通用 trace、session、版本、四问评价和比较由共享底座负责，创作在此基础上判断稿件与视频好在哪里、缺什么。[共享路线图](../../../vendor/agent-workflow/docs/harness-roadmap.md)说明这些通用能力的目标和当前差距。

## 历史失败提醒我们检查什么

| 过去的表现 | 对创作流程的要求 |
| --- | --- |
| 用虚构“会议室预约规则”验收，真实题目零次运行 | 在真实内容上检查质量；工程检查另记 |
| B1 仅从研究摘记出发，问题被窄化 | 保留原机会和观众问题，让稿件检验是否答到 |
| 把创作判断翻成字段，却不看实际读者疑问 | 标准卡提出可检查的问题，冷读者独立看稿 |
| 内容不好便继续加平台和页面 | 固定输入，定位具体失败，逐版比较 |
| SDK 自带 Codex CLI 不支持所选模型，主 Agent 接手执行 | 跑前检查有效执行环境，失败留在流程记录里 |

工作台首先呈现主作品、决定与进度，再展开审阅和执行证据；创作者不需要先读原始 trace 才能判断作品。交付后再考虑 C1 发布和 C2 反馈，它们是独立生命周期事项，现有授权不等于自动发布。
