# 核心思想

目标一直没变：**把发内容的整条路径变成 workflow，让它逐渐不需要创作者参与。** “不需要人”是结果，不是起点：先让每个阶段停在人的关口，人的判断写回标准，等审阅 Agent 和人判断一致了，再撤掉那道关口。

下面七条是这套 workflow 的设计原则，每条都来自真实失败。最后一节说明以前为什么一直做不好。

## 1. workflow 是调出来的

第一版一定会错，错法事先猜不到。做法是：先做一个最简单、能真跑的版本，在同一份冻结输入上真跑，读 trace 和资产找到出问题的那一层，只改一处并升版本，再用同一输入重跑对比。历史 B1/B2 各调了 7 版，B3 后续调到 15 版，其中大部分问题只有在 trace 里才看得见（例如内容角色被灌进了约 1.8 万字的工程规范）。

通用方法见 agent-workflow 的[调优循环](../../../vendor/agent-workflow/docs/tuning-loop.md)，本项目的具体做法见[调优手册](05-tuning.md)。

## 2. 围绕可验收的交付设节点

| 交付 | 判断 | 主资产 |
| --- | --- | --- |
| 内容成立 | 是否兑现读者收获，必要解释是否在稿内成立 | 完整稿、与稿件一致的内容决定和证据 |
| 成品成立 | 声画是否准确、清楚、有效地传达稿件 | 视频、封面和快照 |

B1 的思考和 B2 的写作互相影响。先写出初稿，才能检验选题是否答得上、解释缺哪里、实际需要多少篇幅。2026-10-03 用户授权合并这两段，不再要求先接受大纲才能写作。职责仍然明确，但不把每一种职责都升级为独立 workflow 和人工关口。

## 3. 角色为具体问题服务

研究编辑对照原目的查找材料与缺口；作者同时调整内容决定和完整稿；冷读者只报告看完稿件理解了什么、哪里仍有疑问；事实核查检查是否说错；主编统一判断回到研究还是改稿。无需为了每个中间字段增加一个角色。

目的、读者收获和必答问题保持可见，原始意图不能在角色传递中被窄化为容易完成的替代题。反直觉切入是可选手段。篇幅由解释需要和实际约束决定，形式偏好不默认为硬时长。

## 4. 人工关口是学习入口

完整内容和成品分别交创作者判断：接受、要改或作废。通过一次内容验收生成一版可供制作的完整档案。原 B1/B2 关口合并是用户明确授权的设计调整，不代表审阅者已能替代创作者。

进一步减少人工验收需要**审阅者校准**：同时测试人已认可的正例与不认可的反例。MiMo 旧稿在新明确的读者目标下是反例；不能因为新主编会拒绝它，就宣称校准完成。

## 5. 内容必须是 workflow 做出来的

所有资产都由 workflow 里的 Agent 或程序步骤产出，每份资产都有生产者记录。主持的人或 Agent 只负责编排、审阅和改 workflow。某一阶段跑不出来，就修 workflow 再跑；主 Agent 代写一次，这一阶段就算失败。以前七版视频都是主 Agent 在 workflow 外手工做的，事后再登记进 workflow，所以 workflow 从来没有被真正检验过。

## 6. 阶段之间用作品档案交接

内容 → B3 不靠会话里临时拼输入。内容迭代中的中间稿与研究都在同一个 run 内传递。创作者在关口判“通过”时，程序从这次运行自己的产出生成下一版作品档案；下一阶段从档案取，每个角色只拿自己需要的那一份（冷读者仍然隔离）。交接因此可复现、有版本。详见[作品档案与交接](03-architecture/brief-and-handoff.md)。

## 7. 给人看的东西，结论先行

工作台按阶段一行一行排：这一阶段的决定、当前采用的主资产、判决、进度、历史。先给结论和主资产，审阅细节放在可展开的审计层，原始 trace 不直接展示。一行一行地列，不用卡片墙。

## 以前为什么一直做不好

这是对 2026-09 之前多轮尝试的复盘，依据是当时的会话记录。

| 问题 | 表现 | 现在怎么防 |
| --- | --- | --- |
| 把 workflow 当一次性工程交付 | “测试通过、流程跑通”就算完成；验收题是虚构的“会议室预约规则”，真实题目零次运行 | 只在真实题目上评估；测试通过只说明代码没坏 |
| 目标被拆成两半交付 | “用 workflow 做出好内容”变成“workflow 能跑”加上“主 Agent 手工把内容做好” | 原则 5：内容只能由 workflow 产出 |
| 学习循环倒过来 | 视频不满意就加流程，流程不清就加工作台，最后重建平台；越来越难判断哪个改动真的有效 | 原则 1：同一输入、一次一处、前后对比 |
| B1 从材料出发 | B1 的输入只有研究摘记，问题写成“材料分别怎样展示……”，没有观众的疑问和热度判断 | 内容流程保留原机会、读者收获与必答问题，研究与稿件共同检验 |
| 创作判断被翻译成字段和状态 | 流程里有“核心问题”字段，却没人检验它是不是观众真正的疑问 | 标准卡把判断写成可检验的问题，审阅角色逐条判 |
| 环境问题被当成方法问题 | SDK 自带的 Codex CLI 拒绝新模型，三个会话因此由主 Agent 接手 | 开跑前模型探针；指定可执行文件 |

也有我们自己需要记住的一点：目标在对话里换过很多种说法（工作台、平台、PRD、workflow），但核心诉求一直是同一句话。每次换说法都让执行方重新开一摊。现在把这句话写在本页第一段，后续的改动都对照它来判断。
