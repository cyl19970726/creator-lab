## 2026-10-04 共享底座范围确认

用户确认，执行、工作流版本与迭代、四问评价、人或 Agent A 审阅、PostgreSQL 资产管理 harness、一般 Agent SDK、上下文和工具控制、trace／session 与通用工作台，均属于 agent-workflow 的目标能力。creation 直接接入，提供创作流程、工具、判据和展示扩展。共同动机和职责分别写入共享[产品](../../../vendor/agent-workflow/docs/product.md)与[架构](../../../vendor/agent-workflow/docs/architecture.md)。

这次确认来自此前重复出现的真实问题：产物与流程能力混淆、缺少稳定的逐轮比较、资产路径歧义、运行环境干扰、交接缺口，以及代理接受与用户价值判断不一致。它不否定过去已有的真实运行、审阅和局部修复；也不证明采用 PostgreSQL 或 SDK 后质量自然达标。

当前本地工作台的 SQLite、文件和 Codex 实现是原型，不满足全部共享目标。先补共享能力，再让创作接入并真跑验证；具体状态见[共享路线](../../../vendor/agent-workflow/docs/harness-roadmap.md)。临时 VM 当前暂不考虑，运行结束也不自动删除历史。具体一般 SDK、大媒体存储方式和进一步自动采用范围仍待设计。本次只更新文档，没有实现这些缺口。

以下记录保留当时条件；“先用静态页、不扩平台”等阶段策略已不能作为拒绝当前共享产品建设的依据。

## 2026-10-03：合并内容形成过程

用户明确授权将 B1/B2 合并为一个内容 workflow，保留 B3 制作。职责区分不能自动推出三段独立验收的必要性：完整初稿也是检验选题、研究和篇幅的工具。新版允许在同 run 回研究或调整主线，一次内容验收后才进入制作。

依据是 MiMo 的真人反馈与 trace：旧稿围绕“涨分为何仍卡住”自洽，但没有兑现普通读者理解训练过程和模型逐渐增强的目标。策划、挑战与代理审阅共同漏判，不能只归因于某一角色或一次 PDF 读取失败。此前短时长是主持方建议，用户没有要求锁死。

保留旧代理 accept 作为历史；它不等于后续真人接受。研究/分析工作台、共享执行库和历史生产资产不受此次流程合并影响。实现见[内容迭代](04-workflows/content.md)，验证见[调优手册](05-tuning.md)。

## 历史上否定过的做法及适用范围

| 做法 | 为什么不做 |
| --- | --- |
| 当时继续扩平台、先做完整网页工作台 | 当时先验证真实方法；2026-10-04 已确认需要共享迭代工作台，这条不再用于排除其建设，仍需避免用页面完成代替业务有效 |
| 用大规模多 Agent 编排（几十个 Agent 并行）做设计或评估 | 额度有限；这件事的瓶颈是真跑与读 trace，不是并行度 |
| workflow 跑不出来时由主 Agent 补内容 | 会把“workflow 不行”藏起来，这一轮调优也就没有意义 |
| 按阶段页面的 run 状态或测试数判断“做好了” | 执行完成、结构有效和内容合格是不同的事；内容以创作者关口和标准卡为准 |
